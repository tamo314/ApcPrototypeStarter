# Architecture Decision Log

Use this file for short decisions discovered during implementation. Do not rewrite history; append entries.

## ADR-0001 — Validate the learning loop before using a language model

**Status:** Accepted

**Decision:** Phase A uses synthetic symbolic tasks rather than a pretrained LLM.

**Reason:** The first scientific question is whether selective expansion, consolidation, release and reuse can form a stable closed loop. LLM scale would confound failures in routing, novelty detection, consolidation, continual learning and optimization.

**Consequence:** Early results demonstrate architecture behavior, not language capability.

---

## ADR-0002 — Use low-rank residual transforms as the first primitive type

**Status:** Accepted

**Decision:** Persistent and temporary primitives share a low-rank residual transform interface.

**Reason:** Low-rank transforms are cheap, differentiable, easy to count, easy to compress and compatible with sparse routing.

**Consequence:** Phase A may fail on operations needing richer computation. If so, add a richer primitive type only after proving the limitation experimentally.

---

## ADR-0003 — Rule-based meta-controller before learned controller

**Status:** Accepted

**Decision:** Use a finite-state controller with configurable thresholds and hysteresis in Phase A.

**Reason:** A learned RL controller would make failure attribution substantially harder.

**Consequence:** Controller optimality is not a Phase A claim.

---

## ADR-0004 — Stable primitives are frozen in the strict Phase A experiment

**Status:** Accepted

**Decision:** New learning occurs in temporary capacity. Existing persistent primitives do not update in the primary experiment.

**Reason:** This creates a clear forgetting boundary and makes consolidation effects measurable.

**Consequence:** Later phases must test controlled metaplastic updates because a permanently frozen bank may eventually become inefficient.

---

## ADR-0005 — Resource release requires shadow validation

**Status:** Accepted

**Decision:** Temporary capacity remains available until the consolidated candidate passes current-task and prior-task validation.

**Reason:** Immediate deletion can hide lossy consolidation and produce irreversible failures.

**Consequence:** Peak memory temporarily contains both candidate and temporary solutions.

---

## ADR-0006 — The Task 003 dense core does not generalize to unseen token content

**Status:** Accepted

**Decision:** Task 012's sequential benchmark evaluates novelty, the PLASTIC accuracy gate, and shadow validation's "current task" signal against the same fixed example set an event trains on, rather than a held-out split of fresh instances of the same task.

**Reason:** Measured while building Task 012: the fixed dense baseline (Task 003) does not generalize known-operation execution to token content it did not train on, at every data/model scale tried (16-512 training examples; d_model 32-192; 1-4 layers; 200-1500 steps) -- held-out exact match stays at chance (~0.02), no better than an untrained network, while train-set exact match reaches ~1.0. This is visible in the pre-existing `runs/phase_a_smoke` checkpoint too: its `composition_benchmark.json` shows `known` (held-out `test` split) exact match of 0.016, statistically indistinguishable from `novel_composition`. No task before 012 measured this, because Task 003's acceptance criterion is memorization of a fixed set and Tasks 006/009's benchmarks only require correct reporting mechanics, not a small generalization gap.

**Consequence:** A `K`/`C` event in the sequential benchmark can legitimately escalate through PLASTIC if the core cannot even fit its own small example set, which weakens (but does not fabricate around) H1's selective-expansion story within a single run; whether K/C reliably resolve via STABLE/SEARCH depends on future work improving core generalization (larger pretraining budgets, relative positional encoding, or a curriculum), not on anything Task 012 can fix by construction. Report generalization/novelty gaps as measured, including near-zero or negative ones.

## ADR-0007 — A permanent "null" routing candidate, calibrated after consolidation

**Status:** Accepted

**Decision:** The router's candidate set always includes a permanent, unassigned `NULL_PRIMITIVE_ID` alongside real bank primitives (`apc.core.execution`); after a primitive is consolidated, a short supervised step (`_calibrate_router` in `apc.evaluation.sequential_benchmark`) fits the router's query projection and every registered key so the primitive's own consolidation-batch hidden states route to it and replay-buffer hidden states route to null.

**Reason:** `apc.primitives.router.Router` normalizes scores via softmax over the candidate set; with only one or two real primitives in the bank, that softmax is either trivially 1.0 (one candidate: nothing to compare against) or an arbitrary, untrained split -- either way a persistent primitive would apply itself to every input regardless of relevance, corrupting known/composition tasks once anything is consolidated. Nothing in Tasks 005-011 trained the router's keys at all, since no prior task wired a real model through the bank.

**Consequence:** Selective reuse is only as good as this calibration step's data (the primitive's own consolidation batch vs. whatever is in the replay buffer at the time); it is a lightweight, explicitly-scoped addition for Task 012, not a general router-training procedure, and its failure mode (a recurrence event not being routed to the right primitive) shows up honestly as an unreused recurrence requiring a fresh PLASTIC cycle rather than as a crash or a hidden fabrication.

## ADR-0008 — Sequential benchmark stream drops Milestone A9's mixed known+novel composition event

**Status:** Accepted

**Decision:** `apc.evaluation.sequential_benchmark.default_task_stream` uses two independent novel operations (`SORT`, `REVERSE`) each followed by its own recurrence, instead of Milestone A9's illustrative "novel composition using X + old primitives" event.

**Reason:** `apc.environments.generator.TaskGenerator`'s `novel_operation` split is depth-1 only by construction (Task 009), so a novel operation can never be composed with known operations into a multi-step chain without new environment support. Building that support is an environment change, out of scope for Task 012.

**Consequence:** The stream cannot demonstrate a novel primitive being reused *inside* a new composition, only reused standalone (via `R` events). `docs/exec-plans/active/PHASE_A.md` Milestone A9's exact example stream is not literally reproduced; a future task should extend the generator before attempting that event.

## ADR-0009 — Router-selection fidelity degrades as the bank grows, tracing back to ADR-0006

**Status:** Accepted

**Decision:** No additional mechanism was added to compensate; Task 012 reports post-cycle token-level exact match and retention as measured, including the degradation, rather than engineering around it.

**Reason:** Measured while building Task 012's sequential benchmark: with the tuned defaults (`candidate_rank=14`, `max_retention_degradation=0.08`), every event in a 10-event dev-tier run completed a full learn/consolidate/release cycle with shadow validation genuinely passing (hidden-state task-score-ratio 0.95-0.99). But post-cycle token-level exact match, measured through the bank/router, was strong for the first consolidated primitive (0.9) and fell toward 0 for most later ones despite equally-passing shadow reports. The router's calibration step (`_calibrate_router`) classifies raw core hidden states per primitive, and per ADR-0006 those hidden states are not well-differentiated for content the core never generalized to; as more primitives (and anchors) accumulate, the classification problem the router must solve gets harder on an already low-information signal, so it increasingly mis-routes or under-weights the correct primitive for its own task.

**Consequence:** In this run's configuration, "at least two learn/consolidate/release cycles" (Task 012's stated acceptance) is satisfied on the shadow-validation definition of a cycle, but H3 (reuse reduces adaptation cost) and H5 (retention) are not demonstrated cleanly -- `SequentialBenchmarkReport.retention`/`num_reused_without_new_cycle` will often show large forgetting and zero measured reuse under these settings. This is one symptom of ADR-0006's root cause, not a separate bug in the router or consolidation code; improving it requires improving core generalization (or moving routing to a representation that survives it), which is future work, not a Task 012 fix.

## ADR-0010 — B1's fixed primitive bank is populated by one unconditional seed cycle, not left empty

**Status:** Accepted

**Decision:** `apc.evaluation.baselines.B1Runner` ("fixed sparse", Task 013) runs exactly one learn -> consolidate -> shadow cycle on a slice of known-operation data immediately after pretraining -- reusing `apc.consolidation.distill.consolidate`, `apc.consolidation.shadow.run_shadow_validation`, and `apc.evaluation.stream.calibrate_router`, the same functions B4's own cycle uses -- then freezes the bank and router for the rest of the run. The controller/novelty machinery is never invoked again regardless of event label. If that one shadow validation fails, B1 proceeds with whatever ended up in the bank (possibly still empty) rather than retrying.

**Reason:** `docs/EXPERIMENT_PLAN.md` section 5 defines B1 as "stable core + fixed primitive bank + router, no expansion" without specifying where the fixed bank's content comes from. A bank left empty routes over zero real candidates, which `apc.core.execution.apply_bank` treats as a no-op -- B1 would then be numerically identical to B0 (minus routing overhead), which is not an informative comparison point. Running one unconditional cycle gives B1 genuine (if never-updated) sparse capacity to contrast against B4's repeatedly-updated capacity.

**Consequence:** B1's reported behavior depends on whether that one seed cycle happens to pass shadow validation, which per ADR-0006/ADR-0009 is not guaranteed at these scales. `apc.evaluation.baselines` tests this baseline's "no expansion, ever" property structurally (identical persistent parameter count across every event, zero training steps per event) rather than asserting the seed cycle passes, since the pass/fail outcome itself is not the property Task 013 needs B1 to demonstrate.

## ADR-0011 — B2/B3 grow-only baselines bypass the primitive bank and router entirely

**Status:** Accepted

**Decision:** `apc.evaluation.baselines._GrowRunner` (B2, B3) does not use `apc.primitives.bank.PrimitiveBank` or `apc.primitives.router.Router`. Each event allocates a fresh batch of low-rank transforms (same `Allocator`/preset as B4), trains them, then freezes and permanently appends them to a plain `list[Primitive]` (`self.grown`) that is summed unconditionally into every forward pass via `apc.core.execution.sum_primitive_deltas` -- no routing, no gating, no consolidation. Growth happens for every event unconditionally, with no novelty-gated decision of whether to grow.

**Reason:** A "grow-only" baseline in the continual-learning literature (e.g. Progressive Neural Networks) adds an unconditionally-active block of capacity per task; there is no sparse-selection decision to make; that decision is exactly what APC's router/consolidation loop exists to make learnable in the first place. Wiring B2/B3's ever-growing, never-compressed capacity through a `Router` would reintroduce the same small-bank discriminability problem ADR-0009 documents, into a baseline whose entire point is architectural simplicity, and unconditional growth (rather than novelty-gated growth) is what makes the "bounded persistent growth" comparison (H4) meaningful -- B2/B3 have no mechanism to grow selectively, so their persistent parameter count should visibly outgrow B4's over the same stream, and does (measured on the `configs/phase_a_sequential.yaml` dev-tier stream: B2/B3 end at 20480 persistent parameters after 10 events, versus B4's 17920).

**Consequence:** B2/B3's "active parameters per inference step equals persistent parameters" (every grown transform is always active, never gated) is itself a reportable architectural property contrasting directly with B4's sparse routing. B3's replay loss (see ADR-0012) is the only mechanism available to reduce forgetting in this design; measured on the same dev-tier stream, B3's mean backward transfer (-0.156) is closer to zero than B2's (-0.294), i.e. replay measurably helps without eliminating forgetting, which is the expected shape of the H5 comparison.

## ADR-0012 — B3's replay loss uses a dedicated config field, not `ConsolidationConfig.replay_weight`

**Status:** Accepted

**Decision:** `apc.evaluation.baselines.BaselineConfig.replay_weight` is a new, baseline-only field, separate from `apc.consolidation.distill.ConsolidationConfig.replay_weight`.

**Reason:** `ConsolidationConfig.replay_weight` scales a consolidation-distillation loss: a candidate primitive learning to reproduce a frozen teacher's *delta* on replay hidden states. B3 has no distillation step at all -- it adds a plain cross-entropy replay loss directly onto the raw task loss its newly grown transforms are trained with. These are different losses over different targets; reusing the same config field for both would be a silent semantic overload of one number meaning two different things depending on which baseline reads it.

**Consequence:** A config file that wants to tune B3's replay strength sets a new top-level `baseline_replay_weight` key (see `apc.evaluation.baselines.baseline_config_from_dict`), separate from the `consolidation.replay_weight` key that affects B4 (and B1's one seed cycle, per ADR-0010).

## ADR-0013 — ADR-0006's generalization failure is not a model-scale artifact

**Status:** Accepted

**Decision:** No further Phase A time is spent re-testing whether a bigger dense core (within or above `docs/design-docs/ARCHITECTURE.md` section 3's "recommended first scale") fixes held-out generalization. Model scale is ruled out as the explanation; investigation should move to other candidate causes (training data quantity/coverage, training duration/"grokking"-style late-phase generalization, or task representation) before trying yet another scale point.

**Reason:** ADR-0006 measured no generalization at every scale tried during Task 012 (d_model 32-192, up to ~1.8M parameters) -- below `ARCHITECTURE.md` section 3's own "recommended first scale" of 10M-60M parameters and `docs/HARDWARE_ENVIRONMENT.md`'s "10M-100M comfortable" range, leaving open whether the negative result was simply a too-small-model artifact (`docs/exec-plans/completed/PHASE_A_RESULT.md` recommendation 1). This was retested directly: three new configs (`configs/phase_a_scale_check_{low,mid,high}.yaml`, 384/512/640 hidden size x 8 layers, 14.2M/25.3M/39.4M parameters -- spanning the full recommended range) were each trained from scratch (seed 0, 256 examples, 1500 steps, first real GPU run in this repository's history via the WSL Python 3.12 + CUDA environment built for this investigation) and evaluated with `scripts/composition_benchmark.py`:

| Config | Parameters | Train exact match | Held-out `known` (test) exact match | `novel_composition` exact match |
|---|---:|---:|---:|---:|
| Original smoke (192d, 4L) | 1.79M | 1.0 | 0.0156 | 0.0156 |
| `phase_a_scale_check_low` (384d, 8L) | 14.2M | 1.0 | 0.0078 | 0.0313 |
| `phase_a_scale_check_mid` (512d, 8L) | 25.3M | 1.0 | 0.0078 | 0.0234 |
| `phase_a_scale_check_high` (640d, 8L) | 39.4M | 1.0 | 0.0156 | 0.0156 |

Across a 22x parameter range spanning the entire recommended scale, held-out exact match stays flat at chance (0.008-0.016) while training exact match is a perfect 1.0 in every case -- the model always has more than enough capacity to memorize its (small) training set, and more capacity does not measurably help it do anything else with unseen token content.

**Consequence:** `docs/exec-plans/completed/PHASE_A_RESULT.md` recommendation 1 ("retest at the project's own comfortable scale before concluding the negative result is scale-independent") is now satisfied for the *model-parameter-count* axis specifically; the open caveat about scale no longer applies to that axis. The more likely remaining explanations are training-data quantity/coverage (256-512 examples is a vanishingly small fraction of the possible token sequences at this vocabulary/length range) and training duration (loss was already fully converged, ~1e-4 to 1e-5, after 1500 steps at every scale tried -- these runs cannot distinguish "no generalizing solution exists" from "a generalizing solution exists but was never reached because memorization is the lower-loss optimum found first," the latter being the standard "grokking" phenomenon in the literature, which typically requires an order of magnitude or more additional training steps with weight decay to resolve). Neither has been tested yet.

## ADR-0014 — ADR-0006's generalization failure is not a training-data-quantity artifact (at least up to 4096 examples)

**Status:** Accepted

**Decision:** No further Phase A time is spent scaling `data.num_examples` alone, within a single-batch (whole-dataset-every-gradient-step) training loop, as a way to fix held-out generalization. Training-data quantity/coverage is ruled out as the explanation over the range actually tested (256-4096 examples, a 16x span); investigation should move to training duration ("grokking") or task representation before trying yet more raw examples under this training regime.

**Reason:** ADR-0013 left training-data quantity/coverage as a leading untested candidate cause of ADR-0006's finding. This was tested directly: `configs/phase_a_data_scale_{1024,4096}.yaml` reran the same held-out-generalization measurement at 4x and 16x the original 256-example count (seed 0, 1500 steps, `scripts/composition_benchmark.py` with `known_split=test`, 128 known + 128 novel-composition examples evaluated):

| `num_examples` | Model | Parameters | Train exact match | Held-out `known` (test) exact match | `novel_composition` exact match |
|---:|---|---:|---:|---:|---:|
| 256 | `phase_a_scale_check_low` (384d, 8L) | 14.2M | 1.0 | 0.0078 | 0.0313 |
| 1024 | same (384d, 8L) | 14.2M | 1.0 | 0.0156 | 0.0313 |
| 4096 | original smoke dims (192d, 4L) | 1.79M | 1.0 | 0.0156 | 0.0469 |

(The 4096 row uses the smaller model because this training loop collates the *entire* dataset into one batch and reruns it every step, so activation memory scales directly with `num_examples`; 4096 examples at the 14.2M model's width overflowed the 16GB card -- observed as a 67x per-step slowdown from VRAM-overflow thrashing, not real compute growth, killed after ~4h stuck at step 900/1500 -- while 4096 at 1.79M params fit comfortably (4.9GB peak). ADR-0013 already established held-out exact match is flat across this exact parameter range at fixed data, so the model-size change does not confound this row.)

Across a 16x increase in training examples, held-out exact match stays flat at chance (0.008-0.016, same range as ADR-0013) and training exact match remains a perfect 1.0 throughout -- more data did not produce any measurable movement toward generalization, at any point along the range tested.

**Consequence:** Training-data quantity/coverage, on its own, is ruled out as the explanation for ADR-0006's finding, *for the 256-4096 example range*. Pushing further (e.g. 16384+ examples) under this exact training loop is not straightforward: the whole-dataset-every-step design means VRAM scales with `num_examples` regardless of model size, and doing so would require either implementing minibatching/gradient accumulation in `apc.core.train.run_smoke_training` (a real code change, not just a new config) or shrinking the model further, which risks losing enough capacity to fit even the training set. The two remaining untested candidate causes from ADR-0013 narrow to one: training duration / "grokking"-style late-phase generalization (loss is already fully converged, ~1e-4, after only 1500 steps at every data scale tried here too -- these runs still cannot distinguish "no generalizing solution exists" from "one exists but was never reached").

## ADR-0015 — `encode_split`'s `task_state` is a parameter-free view, not a learned projection

**Status:** Accepted

**Decision:** `apc.core.model.DecoderOnlyTransformer.encode_split` (Task A1-005) derives `task_state` from `content_state` via `task_head`, a `LayerNorm(elementwise_affine=False)` -- zero learnable parameters -- rather than a learned `nn.Linear` projection.

**Reason:** A first implementation used a learned `nn.Linear(d_model, d_model)` for `task_head`. It broke two pre-existing, passing tests: `tests/test_core_checkpoint.py::test_save_and_load_checkpoint_restores_weights_exactly` (its zero-initialized bias is identical across two differently-seeded models, since nothing in the current pipeline calls `encode_split`/`use_split_state=True` during training, so the layer never receives gradient and stays at its untouched init) and `tests/test_sequential_benchmark.py::test_two_events_each_complete_a_learn_consolidate_release_cycle` (merely *constructing* a new randomly-initialized submodule consumes extra draws from this codebase's one shared global `torch` RNG stream, per `apc.utils.seed.set_seed`; every random draw made anywhere else in the same process *after* model construction -- primitive bank/router initialization, data sampling, plastic-workspace training -- shifts by exactly that amount, silently changing an already-seeded integration test's step-by-step trajectory even though the new layer's output is never read). This is general: any new `nn.Parameter`-bearing submodule added to `DecoderOnlyTransformer.__init__`, used or not, perturbs every later seeded random draw in the process under this codebase's RNG model. A parameter-free transform reads `content_state` without registering a `nn.Parameter`, so it consumes zero RNG draws and leaves both tests (and everything downstream of model construction) untouched.

**Consequence:** `task_state` is currently a deterministic, non-learned function of `content_state` (mean/variance-normalized per position) -- distinct-valued (see `tests/test_core_model.py::test_encode_split_task_state_is_independently_probeable`) but not yet a separate *learned* representation. `PHASE_A1_ARCHITECTURE_DELTA.md` section 4 explicitly leaves the implementation flexible for this reason; the low-information-content-state generalization constraint it states is a gate for a later milestone that actually routes/detects novelty on `task_state`, not this task's acceptance criterion. Whichever future task first makes `task_state` a genuinely learned, separate representation (e.g. a learned router in A1-015) will reintroduce a new `nn.Parameter`-bearing submodule to the model; ADR-0016's setup-phase re-seeding means that, done inside `_SequentialBenchmarkRunner`/`_BaseRunner`'s existing construction, it will *not* require retuning seed-sensitive event-loop tests the way this task's first attempt did -- it only would if the new parameters are trained inside the setup phase itself (before the re-seed point), which would need the re-seed moved after that training.

## ADR-0016 — Benchmark/baseline runners re-anchor the global RNG stream after setup-phase construction

**Status:** Accepted

**Decision:** `apc.evaluation.sequential_benchmark._SequentialBenchmarkRunner.__init__` and `apc.evaluation.baselines._BaseRunner.__init__` (plus `B1Runner.__init__`, which constructs additional state after calling `super().__init__`) call `apc.utils.seed.set_seed(seed)` a second time, immediately after all setup-phase construction (model, primitive bank, router's null key, plastic workspace, allocator, controller, novelty estimator) finishes and before returning. Any `__init__` override that constructs further RNG-consuming state after calling its parent's `__init__` must add its own trailing re-seed for the same reason (`B1Runner` does; `_GrowRunner`/`B2Runner`/`B3Runner` do not need one because `Allocator.__init__` and their own added state do not consume the global RNG at construction).

**Reason:** ADR-0015's first (rejected) implementation surfaced this while debugging why an unused, never-forward-called `nn.Linear` broke `tests/test_sequential_benchmark.py::test_two_events_each_complete_a_learn_consolidate_release_cycle`, an integration test that asserts a specific emergent outcome ("at least 2 learn-consolidate-release cycles complete within a bounded step budget") purely by pinning a seed and relying on bit-exact reproducibility of the entire multi-stage training trajectory that follows. Before this ADR, `__init__` called `set_seed(seed)` exactly once at the top, then constructed several *conceptually independent* pieces (model, then bank, then router, then workspace, ...) that nonetheless all drew from the same shared global `torch` RNG stream in sequence. This meant the exact random-number trajectory the event loop's training/allocation/consolidation logic saw was accidentally coupled to *how many parameters the model, or any other piece built during setup, happened to have* -- a completely unrelated implementation detail. `apc.environments.generator.TaskGenerator` already avoids this failure mode correctly, by deriving its own independent `random.Random` instances per seed/label (`_derive_seed`, see `generator.py`) rather than sharing the global `torch` stream; `apc.consolidation.distill.consolidate` also already re-seeds locally and deliberately right before constructing its candidate primitive. The runners' `__init__` methods were the one place in the active Phase A.1 path that hadn't adopted either pattern.

**Consequence:** Re-seeding here changed the exact numeric trajectory of every existing runner-driven test relative to before this ADR (verified: all pre-existing tests, including the cycle-count test, still pass after the change -- see `tests/test_sequential_benchmark.py::test_runner_init_reanchors_rng_regardless_of_setup_phase_model_size` and the matching test in `tests/test_baselines.py`, both added as regression coverage for this property specifically). Going forward, adding, removing, or resizing anything constructed during a runner's setup phase (model layers, bank/router/workspace scaffolding) cannot silently alter the event loop's random trajectory, so long as it happens *before* the trailing re-seed and does not itself need to be trained during setup. `AGENTS.md`'s "Use deterministic seeds wherever practical" principle is elaborated with this pattern so future code (new runners, or new setup-phase construction in existing ones) follows it by default rather than rediscovering this failure mode.

## ADR-0017 — Four of the eight known operations are not learnable as a function of the presented input alone

**Status:** Accepted

**Decision:** `apc.evaluation.stable_core_generalization` (Task A1-006, the Stable Core systematic-generalization gate) trains and evaluates only `apc.environments.operations.DETERMINISTIC_OPERATION_NAMES` (`COPY`, `NEGATE`, `COMPARE`, `ACCUMULATE`) rather than the full `KNOWN_OPERATION_NAMES` (which also includes `SELECT`, `COUNT`, `SHIFT`, `BIND`). `KNOWN_OPERATION_NAMES` itself is unchanged and every other Phase A/A.1 consumer (composition benchmark, sequential benchmark, baselines) keeps using the full eight-operation curriculum.

**Reason:** Discovered while designing Task A1-006's training/eval loop. `apc.environments.generator.TaskGenerator._generate` samples each operation's parameters via `Operation.sample_params(rng, sequence, vocab_size)` (`SelectOp`'s `indices`, `CountOp`'s `target`, `ShiftOp`'s `amount`, `BindOp`'s `query_key`) from the *same* per-example `rng` stream that also drew the input content -- but those parameters are stored only in the latent `Program`/`OperationGraph` (oracle-only metadata per the generator's own docstring) and are never included in `Example.input_tokens`. `apc.core.data.encode_example` presents the model with `[BOS] input... [SEP] target... [EOS]` and nothing else. For `SELECT`/`COUNT`/`SHIFT`/`BIND`, the target is therefore a function of `(input, hidden_parameter)`, not of `input` alone: e.g. `COUNT`'s target token depends on a `target` value drawn uniformly from the whole vocabulary, independent of the input content, so two examples with identical presented input but different sampled `target` correctly have different presented targets. No model -- regardless of capacity, training regime, online generation, or symbol permutation -- can recover a hidden, input-independent parameter from the input alone; unseen-content exact match for these four operations is upper-bounded by chance/guessing, not by representation quality. `COPY`, `NEGATE`, `COMPARE`, and `ACCUMULATE` have no such parameter (`sample_params` always returns `{}`, see `tests/test_operations.py::test_deterministic_operations_sample_params_is_always_empty`): their target is a pure, deterministic function of the presented input, so they are the only members of `KNOWN_OPERATION_NAMES` for which "does the Stable Core generalize this known operation to unseen content" is even a well-posed question.

**Consequence:** A1-006's gate is scoped to a 4-operation curriculum, not all 8; a mixed-operation Stable Core gate as originally implied by "known operations" would be structurally incapable of reaching the >=0.95 acceptance threshold regardless of architecture or training quality, making any failure uninterpretable (task ill-posedness vs. representation/training failure -- exactly the ambiguity `docs/AGENTS_PHASE_A1_ADDENDUM.md`'s "investigate representation/training objective only" instruction for a failed STOP GATE presumes is *not* present). This is an environment-design gap, not a Task A1-006 defect: `apc.evaluation.composition_benchmark`/`novel_operation_benchmark`/`sequential_benchmark` still mix parameterized and deterministic known operations, so their own reported `K`/`C` exact-match numbers (Task 006/009/012, and ADR-0006/0009/0013/0014's negative-generalization findings) are also confounded by this same non-identifiability for any example whose sampled operation is `SELECT`/`COUNT`/`SHIFT`/`BIND` -- those prior findings remain valid as measured (near-chance generalization was never claimed to be *entirely* explained by task well-posedness), but their true achievable ceiling was never 1.0 to begin with. A future task should decide, for the parameterized operations, either (a) encode the sampled parameter into the presented input (e.g. a query token before `[SEP]`), turning them into well-posed input-to-output tasks, or (b) permanently exclude them from any generalization-ceiling claim and keep them only for capacity/routing-oriented benchmarks (composition, novelty, sequential) where a hidden parameter does not undermine the property being measured (e.g. whether capacity expands). Neither is in scope for A1-006 itself.

## ADR-0018 — Symbol permutation must be shared per batch/episode, not drawn fresh per example

**Status:** Accepted

**Decision:** `apc.environments.generator.TaskGenerator._generate` now draws exactly one `SymbolPermutation` per `generate`/`generate_online` call (shared by every example returned from that call) when `permute_symbols=True`, instead of one independent permutation per example. This corrects the implementation to match `docs/design-docs/PHASE_A1_ARCHITECTURE_DELTA.md` section 3's own stated design ("per-batch or per-episode symbol permutation"), which Task A1-004's original implementation did not actually follow (it derived a fresh permutation keyed by each example's loop index).

**Reason:** Discovered empirically while building Task A1-006's gate. With `apc.evaluation.stable_core_generalization.DETERMINISTIC_OPERATION_NAMES` (`COPY`, `NEGATE`, `COMPARE`, `ACCUMULATE`; ADR-0017), a single-operation, zero-ambiguity, 6000-step training run per operation gave: `COPY` unseen exact match 1.0 (loss ~2.8e-5), but `NEGATE` 0.0 (loss 1.29), `COMPARE` 0.0 (loss 1.11), `ACCUMULATE` 0.0 (loss 1.80) -- all three stuck far above zero loss with *zero* measurable exact match despite no operation-identity ambiguity at all (see ADR-0017's issue; this ablation used one operation at a time). The cause is permutation, not capacity or training budget: `COPY`'s target at position `i` is exactly the input token at position `i`, so it is *value-blind* -- correct regardless of how tokens are relabeled, since relabeling commutes with the identity function. `NEGATE` (`vocab_size - 1 - x`), `COMPARE` (`a < b` / `a == b` / `a > b`), and `ACCUMULATE` (running sum mod `vocab_size`) all depend on the *canonical numeric value* of a token, not merely its identity/position. Under a permutation resampled independently for every example, a given presented token id encodes a different canonical value in every example, with no side channel revealing which -- so the presented-space relationship between input and target for these operations is effectively a fresh, unrelated random relabeling on every single training example, carrying no learnable cross-example regularity. Only operations that commute with an arbitrary bijective relabeling of the vocabulary (`f(π(x)) = π(f(x))` for every permutation `π`) -- i.e. purely positional/structural operations like `COPY`, `SHIFT`, `SELECT`, `REVERSE` -- survive independent per-example permutation; anything depending on order or arithmetic over token values cannot. Sharing one permutation across an entire batch (all `n` examples from one `generate_online` call, i.e. one training step) fixes this: the model can learn a permutation-*equivariant* circuit (e.g. genuine numeric comparison/arithmetic over presented ids) that generalizes across the many different permutations seen over the course of training, while a fixed token id still never survives an entire training run unchanged (preserving A1-004's original anti-memorization intent -- see the updated `apc.environments.generator` module docstring). Verified safe: grepped the full repository for `permute_symbols` before making this change -- only the generator itself, its own tests, and the new Task A1-006 module/config reference it, so no other Phase A/A.1 benchmark (composition, novel-operation, sequential, baselines) currently enables it, and every pre-existing permutation test in `tests/test_generator.py` still passes unmodified after the fix (none of them asserted per-example independence as a property).

**Consequence:** Task A1-004's own acceptance criteria (bijection validity, decode-invariance, per-`(seed, step, split)` determinism, semantic invariance of interpreter truth) are unaffected -- all still hold with a shared-per-call permutation, and the affected commit's tests all pass unchanged. `Example.symbol_permutation` is now the *same* value across every example returned by one `generate`/`generate_online` call rather than a distinct one per example; nothing observed reading that field individually per example changes shape or type. Two new regression tests (`test_permute_symbols_is_shared_across_every_example_in_one_call`, `test_permute_symbols_changes_across_different_generate_calls`) lock in "shared within a call, different across calls" going forward. This was a pre-A1-006 latent defect in already-"accepted" A1-004 code, not a new deviation introduced by A1-006; historical Phase A run artifacts are unaffected since none of them used `permute_symbols=True`.

## ADR-0019 — Symbol permutation makes value/order-dependent operations unrecoverable on held-out content, even shared per batch

**Status:** Accepted

**Decision:** `apc.evaluation.stable_core_generalization.StableCoreGateConfig.permute_symbols` defaults to `False`, not `True`. The gate's primary variant (`configs/phase_a1_stable_core_gate.yaml`) tests all four `DETERMINISTIC_OPERATION_NAMES` with permutation off; a secondary variant (`configs/phase_a1_stable_core_gate_permuted_copy_only.yaml`) tests `COPY` only with `permute_symbols=True`, satisfying `docs/AGENTS_PHASE_A1_ADDENDUM.md`'s "must use ... token/symbol permutation" instruction on the one operation for which it is actually meaningful. Both variants are run and reported (a deliberate choice, confirmed with the user given it revises the recommendation behind ADR-0018).

**Reason:** After ADR-0018's per-batch permutation fix, a single-operation (`NEGATE`, zero cross-operation ambiguity), zero-hidden-parameter, 30000-step run under `permute_symbols=True` still reached only 0.0 unseen exact match, with loss still steadily falling (2.02 -> 0.77, no plateau) -- i.e. *not* a training-budget problem, since the identical configuration with `permute_symbols=False` reaches 1.0 exact match (loss ~6e-5) in 6000 steps. The reason is structural, not empirical: at evaluation time, a held-out example's specific relabeling (which `SymbolPermutation` was used) is never part of the presented input (by design -- it is oracle-only metadata, see `apc.environments.permutation`'s module docstring) and cannot be inferred from that one example's own content for any token value that does not repeat within it (a decoder-only Transformer processes one example at a time, with no cross-example information at inference). The continuously falling *loss* despite near-zero *exact match* is consistent with the model learning only what generalizes across every possible relabeling -- primarily copy-on-repeat / induction-style behavior for token values that happen to reappear within the same example -- while any "first occurrence" position within a held-out example remains fundamentally unresolvable, and exact match requires every position correct. `COPY` is the exception because its output equals its input position-for-position: a *value-blind* operation commutes with any relabeling (`f(π(x)) = π(f(x))` when `f` is the identity), so it needs no information about which permutation is active. `NEGATE`, `COMPARE`, and `ACCUMULATE` all depend on the actual numeric value (arithmetic complement, order comparison, running sum) and do not commute with an arbitrary permutation, so they cannot be solved by a model that never observes which permutation was used, independent of model capacity or training duration.

**Consequence:** No known-operation gate variant that both (a) uses per-example-unknown `permute_symbols=True` and (b) includes a value/order-dependent operation can pass the >=0.95 threshold, ever -- this is not a candidate for a future "just train longer / bigger" fix; fixing it for real would require an architecture change out of scope for A1-006 (e.g. giving the model a few in-context demonstration pairs under the same permutation before asking it to generalize). The gate therefore reports two honestly-scoped variants instead of one conflated number: the primary, more informative variant (`permute_symbols=False`, all four operations) is the one `docs/results/PHASE_A1_RESULT.md`-style reporting should treat as the H1 verdict; the secondary variant (`permute_symbols=True`, `COPY` only) demonstrates the addendum's symbol-permutation mandate is satisfied where it is actually meaningful, and should not be read as a broader claim about generalization under permutation. Every result reported under either variant must state which variant it is (this ADR's terms "primary"/"secondary" are the intended shorthand for run artifacts and future references).

## ADR-0020 — Operations sharing an output-length signature are mutually non-identifiable when pooled in one model

**Status:** Accepted

**Decision:** `apc.evaluation.stable_core_generalization.run_stable_core_gate_grid` trains and evaluates one single-operation `TaskGenerator`/model per operation (never a pool of multiple operations in one `TaskGenerator`/model), then aggregates results across the resulting operation x seed grid. `run_stable_core_gate`/`run_stable_core_gate_multi_seed` remain general-purpose (a caller may still pass a multi-operation `operation_names` pool if a future task genuinely wants that), but the gate's own entry point (`run_stable_core_gate_grid`, and `scripts/stable_core_generalization_gate.py`) always uses the per-operation grid form.

**Reason:** Measured directly while scoping A1-006 (before discovering ADR-0019's permutation issue): even with `permute_symbols=False` and zero hidden parameters, training one model on all four `DETERMINISTIC_OPERATION_NAMES` pooled together plateaus at ~0.25-0.35 unseen exact match after 10000 steps (loss 0.16-0.19, essentially converged, not still improving) -- far below the 0.95 gate and *not* explained by ADR-0017's or ADR-0019's findings (no hidden parameters here, no permutation here). The cause: `apc.environments.generator.TaskGenerator._generate` samples which operation applies to a given example *uniformly at random*, independent of input content, and this choice is never part of the presented input (only latent `Program`/`OperationGraph` metadata carries it). `COPY`, `NEGATE`, and `ACCUMULATE` all preserve input length; only `COMPARE` differs (`input_length - 1`). A model can use output-length as a structural cue to recognize "this example needs `COMPARE`" (and indeed learns it near-perfectly, contributing ~1/4 of the pooled exact match), but has no analogous cue to distinguish `COPY` from `NEGATE` from `ACCUMULATE` for any single example -- the three are pairwise indistinguishable from input content alone, so the model can do no better than an uninformed guess among them, capping the pooled result near "the identifiable fraction of the pool, solved well" plus "the rest, near chance." This is structurally the same category of problem as ADR-0017 (a value the model needs is never revealed to it) one level up: there, it was a hidden operation *parameter*; here, it is the hidden *choice of operation itself*.

**Consequence:** Any future Phase A.1 K-gate (or gate-adjacent benchmark) that mixes multiple known operations into one shared model/`TaskGenerator` pool risks measuring this identifiability ceiling rather than genuine representation/training quality, unless every pooled operation is pairwise distinguishable by some structural cue available in the presented input (rare, and not something to rely on by construction). Running one operation at a time and aggregating is the general-purpose fix and is what A1-006 adopts; this does not change `apc.evaluation.composition_benchmark`/`novel_operation_benchmark`/`sequential_benchmark`, which already report per-label (`K`/`C`/`N`/`R`) results rather than one pooled number, so they are not directly affected by this specific failure mode, though ADR-0017's parameter-identifiability caveat still applies to their `K`/`C` pools whenever a sampled operation happens to be `SELECT`/`COUNT`/`SHIFT`/`BIND`.

## ADR-0023 — `PrimitiveCall` keeps `SELECT`'s real `indices` subset rather than the design doc's single-scalar illustration

**Status:** Accepted

**Decision:** `apc.environments.primitive_call.PrimitiveCall` (Task A1-C006, the parameterized `PrimitiveCall` abstraction) represents `SELECT`'s argument as `{"indices": [...]}`, matching `ProgramStep.params`/`apc.environments.task_spec.TaskStepSpec.arguments` exactly, rather than `docs/design-docs/PARAMETERIZED_PRIMITIVE_CALLS.md` section 3's illustrative `PrimitiveCall(SELECT, {"index": 3})`. `PrimitiveCall(operation="SELECT", arguments={"index": 3})` raises `ValueError` (wrong key); only `{"indices": [...]}` is accepted. This resolves the naming/shape gap `apc.environments.task_spec`'s module docstring flagged as open when Task A1-C001 landed.

**Reason:** `apc.environments.operations.SelectOp.apply` selects an `output_length(len(sequence))`-sized *subset* of positions, preserving order (`SelectOp.sample_params`/`apply`, Phase A Milestone A1) -- for a length-6 input that is 3 positions, not 1. A single scalar `index` cannot determine a variable-length subset, so adopting the design doc's illustration literally would make `SELECT` calls underspecified: `execute()` (this task's `Operation.apply` dispatch) could not reproduce `apc.environments.interpreter.run_program`'s actual output for any `SELECT` step, and the round trip to/from `TaskStepSpec`/`ProgramStep` (which already carries `indices`, established by Task A1-C001 and covered by `tests/test_task_spec.py::test_task_step_spec_round_trips_every_known_operation`) would be lossy in one direction. The design doc itself anticipates this: section 2 says "the exact concrete schema may be stricter," and section 10 scopes the correction to representing "the existing synthetic operations ... cleanly" rather than introducing a new argument shape for them. Changing `SelectOp` itself to take a single index instead would alter already-gated behavior (A1-006/H1a, A1-C004/H1b, A1-C005/H1c all trained and probed against the real `indices`-subset semantics) for no benefit within this task's scope.

**Consequence:** `apc.environments.operations.Operation.required_argument_names` (added by this task) is now the single source of truth for which argument keys each operation accepts -- `SelectOp.required_argument_names == frozenset({"indices"})` -- and `PrimitiveCall.__post_init__` validates against it eagerly, so a caller that passes the design doc's illustrative `{"index": ...}` shape fails fast with a clear message instead of silently misrouting. `docs/CODEX_TASKS_PHASE_A1_CORRECTION.md`'s A1-C006 acceptance criteria are met: `tests/test_primitive_call.py` shows one primitive family (`SHIFT`, `SELECT`, `COUNT`, `BIND` each) executing >=3 distinct argument values correctly via `PrimitiveCall.execute`, `registered_operation_names()`/family count is unaffected by 100 `PrimitiveCall`s spanning 50+50 distinct argument values (`test_registered_operation_count_is_unaffected_by_many_distinct_calls`), and both missing-required-argument and unexpected-argument construction are covered (`test_missing_required_argument_raises_value_error`, `test_unexpected_argument_on_parameter_free_operation_raises_value_error`, `test_wrong_argument_name_for_parameterized_operation_raises_value_error`). `PrimitiveCall` is a new, distinct type from `TaskStepSpec` (execution-time call vs. model-input projection, see the module's own docstring) with lossless `from_task_step`/`to_task_step` and `from_program_step`/`to_program_step` conversions for every currently supported operation; it is not yet wired into `apc.core.execution`/`apc.primitives` (that wiring is Task A1-C007's oracle routing adapter, per `docs/CODEX_TASKS_PHASE_A1_CORRECTION.md`). All 608 pre-existing plus new tests pass (`python -m pytest -q`), and `python -m ruff check .` / `python -m mypy src/apc` are both clean.

## ADR-0024 — Oracle routing forces bank selection from a `PrimitiveCall`, with no `Router` reachable from the oracle path at all

**Status:** Accepted

**Decision:** Task A1-C007 (the oracle `PrimitiveCall` routing adapter) is implemented as two additions, keeping the environment/oracle-metadata layer and the core execution/learned-path layer split the same way the rest of this codebase already does:

- `apc.environments.generator.oracle_calls_for_example`/`oracle_call_for_example` convert an `Example`'s latent `program` into the `PrimitiveCall` chain (or, for the current depth-1 `known`/`novel_operation` pools, the single call) that produced its target -- Work item 1, "Convert environment oracle metadata into `PrimitiveCall`". `oracle_call_for_example` raises `ValueError` on a multi-step (`novel_composition`) example rather than silently returning only its first step, since A1-007's own scope is single-operation ("oracle-routed K"), not A1-008's composition search.
- `apc.core.execution.apply_bank_with_oracle_calls`/`forward_logits_with_oracle_calls`/`generate_greedy_with_oracle_call`/`evaluate_exact_match_with_oracle_calls` are new, additive siblings of `apply_bank`/`forward_logits`/`generate_greedy_with_capacity`/`evaluate_exact_match_with_capacity` that force bank primitive selection from one `PrimitiveCall` per batch item (`call.primitive_id`, applied unconditionally at `gate=1.0`) instead of scoring `stable_ids` through a `Router` -- Work item 3, "Update A1-007 evaluation API to accept an oracle call provider" (`evaluate_exact_match_with_oracle_calls`'s `oracle_call_provider` parameter, defaulting to `oracle_call_for_example` but substitutable, `tests/test_oracle_routing.py::test_evaluate_exact_match_with_oracle_calls_uses_the_injected_provider`).

None of the four new `apc.core.execution` functions accepts a `Router` parameter at all (`tests/test_oracle_routing.py::test_oracle_routing_functions_never_accept_a_router`, asserted via `inspect.signature`) -- Work item 2, "ensure the learned path never receives oracle calls", is satisfied structurally, not just by not calling `Router.forward` at runtime: there is no argument slot through which a caller could pass one in. `apply_bank`/`forward_logits`/`generate_greedy_with_capacity`/`evaluate_exact_match_with_capacity`/`Router` are all unmodified.

**Reason:** `docs/design-docs/PARAMETERIZED_PRIMITIVE_CALLS.md` section 8 and `docs/EXPERIMENT_PLAN_PHASE_A1_CORRECTION.md` section 4 ("oracle routing can be represented as a `PrimitiveCall`") both specifically warn that an oracle revealing only `primitive_id` for one of the four ADR-0017 hidden-parameter operations (`SELECT`/`COUNT`/`SHIFT`/`BIND`) would reproduce A1-006's non-identifiability one level into oracle routing: knowing *that* `SHIFT` is the right family does not say *which* `amount`. `PrimitiveCall.__post_init__` (Task A1-C006) already refuses to construct an underspecified call for these four operations (`PrimitiveCall(operation="SHIFT")` raises `ValueError: ... missing required argument(s): ['amount']`), so `oracle_call_for_example` inherits that guarantee for free -- it cannot hand out an argument-less oracle call for a parameterized operation even if it tried. `tests/test_oracle_routing.py::test_oracle_call_reproduces_target_tokens_exactly` (parametrized over all eight `KNOWN_OPERATION_NAMES`) confirms this positively: executing the converted call against `example.input_tokens` reproduces `example.target_tokens` exactly for both the four parameter-free and the four parameterized operations. The bank-side wiring forces `call.primitive_id` directly as the bank lookup key (no separate id-remapping layer): `apc.environments.task_spec.operation_id` was already designed as "a function of `operation` alone" (`PrimitiveCall.primitive_id`'s own docstring), so an A1-007 experiment that registers one bank primitive per operation at `operation_id(name)` gets oracle routing "for free" from this adapter, without this task needing to invent a second id-assignment scheme.

**Consequence:** Per `docs/exec-plans/active/PHASE_A1_CORRECTION.md` section 4, all four "routing-readiness" conditions are now satisfied (H1b/ADR-0021; `z_task` operation-identity and argument decoding/ADR-0022; the parameterized `PrimitiveCall` abstraction/ADR-0023; and this ADR's oracle routing adapter) -- **A1-007 is unblocked**, pending A1-C008's audit recording the combined verdict. What this task deliberately does *not* provide: a bank pre-populated with operation-aligned primitives (an A1-007 experiment-setup concern, not this adapter's), argument-conditioned neural primitive execution (`apc.primitives.primitive.Primitive.forward` still takes no `arguments` input at all -- `PrimitiveCall.arguments` is carried through `OracleRoutingOutput.calls` for bookkeeping/future use but not yet consumed by the low-rank transform itself; this remains a real limitation any future argument-sensitive oracle-routed gate must account for), and chained multi-call oracle execution (`apply_bank_with_oracle_calls` requires exactly one call per batch item and raises on a length mismatch; `oracle_calls_for_example` returns the full multi-step chain for a `novel_composition` example, but nothing here executes it -- that is Task A1-008's Composition Library). All 653 pre-existing plus new tests pass (`python -m pytest -q`, `tests/test_oracle_routing.py` adds 46), and `python -m ruff check .` / `python -m mypy src/apc` are both clean.

## ADR-0025 — H2a passes: content encoding is made structurally (not merely empirically) task-blind via two independent forward passes

**Status:** Accepted

**Decision:** Task A1-R001 (the task-blind content encoder path gate, STOP GATE, H2a, first task of the Phase A.1 Post-Correction Redesign per `docs/exec-plans/active/PHASE_A1_POST_CORRECTION.md`) is recorded as **PASS**. Rather than extending `apc.core.model.DecoderOnlyTransformer.encode_split` (Task A1-005/ADR-0015) -- which reads `task_state`/`content_state` as two renamed views of *one* causal forward pass over `[BOS] [TASK_START] op arg... [TASK_END] input... [SEP]`, so a content position has, by construction, already attended over every task token before it (ADR-0022) -- this task adds a second, independent factorization:

- `apc.core.data.build_task_only_tokens`/`build_content_only_tokens` render a `TaskSpec`/`Example` into two *separate* token sequences (`[BOS] [TASK_START] op arg... [TASK_END]` and `[BOS] input... [SEP]` respectively), neither containing any token from the other's vocabulary range;
- `apc.core.model.DecoderOnlyTransformer.encode_task_content_split(task_ids, content_ids)` calls `encode` twice through the *same* shared weights, once per sequence, returning a new `TaskContentEncoding(task_state, content_state)` -- deliberately not the same type as `EncodedState`, since the two fields here come from different-length sequences and are not interchangeable drop-ins for one another's positions;
- `apc.evaluation.task_blind_content_gate` is the gate: `runs/phase_a1_task_blind_content_gate/report.json`/`summary.json` (config `configs/phase_a1_task_blind_content_gate.yaml`, 5 seeds `0-4`, CPU, git commit `1ed8940`) show, for every seed, all eight `KNOWN_OPERATION_NAMES` covered (128 generated contents/seed, `num_contents_per_operation=16`), zero task-token ids ever present in any content-only token sequence, `content_state` numerically identical across every alternate task spec tested against the same content (`representation_max_absolute_difference=0.0`, exact on CPU, not merely within the predeclared `atol=1e-5`), and `content_state` invariant to batch padding within tolerance (`padding_max_absolute_difference` in `[2.3e-6, 3.1e-6]` across seeds, well under `atol`). All five seeds individually pass; total wall-clock across all five was under 10 seconds.

**Reason:** `docs/design-docs/CAUSAL_PRIMITIVE_EXECUTION.md` section 4 states the required invariant (`h_content(x, t1) == h_content(x, t2)`) is "stronger than a leakage probe" -- an empirical probe on a trained model (A1-C005's approach to a different question) can only ever show "no leakage observed on tested examples," never "leakage is impossible." Running `encode` over a content-only sequence that contains no task token at all makes leakage structurally impossible for *any* weights, trained or not: there is no computational path from a task token to `content_state`, because no task token is ever part of the sequence `content_state` is computed from. This is why the gate deliberately uses freshly-initialized (never trained) models per seed -- the property under test is architectural, not learned, so training first would only cost wall-clock without changing what is measured (`AGENTS.md`: "prefer the smallest implementation that can falsify the current hypothesis"). Per-operation coverage is likewise made structural rather than probabilistic: each of the eight operations gets its own dedicated single-operation `apc.environments.generator.TaskGenerator` (via `build_mixed_operation_generator(operation_names=(name,), ...)`) rather than drawing from one shared eight-operation mixed stream and hoping uniform sampling happens to cover every operation within a small batch (verified empirically during implementation: a single shared draw of 16 examples over 8 operations missed 2 operations entirely at seed 0, which is expected under uniform-random sampling at that batch size, not a defect in the generator).

**Consequence:** Per `docs/exec-plans/active/PHASE_A1_POST_CORRECTION.md`, A1-RM1 (task-blind content path) is satisfied and A1-R002 (decoder leakage control) may proceed -- but only A1-R002 specifically; per `AGENTS.md`'s "Codex workflow," completing A1-R001 does not authorize starting A1-R003 or later. What this task deliberately does *not* provide: any change to decoding/generation (the pre-existing `encode_split`-based full pipeline, and the A1-C004 dense shared-core solver, are both untouched and remain the task-conditioned baseline per `docs/CODEX_TASKS_PHASE_A1_POST_CORRECTION.md` A1-R001 Work item 5); a trained task-blind content representation's actual *capability* to support primitive execution (this gate never trains a model -- whether a *trained* task-blind `content_state` is good enough to support the Correct/Wrong/None causal pattern is A1-R003's parameter-free oracle primitive benchmark, not this one's); and any wiring of `encode_task_content_split` into `apc.core.execution`'s `apply_bank`/`forward_logits` (routing/primitive execution stays out of scope here, matching every earlier Phase A.1 Correction gate's scope discipline -- `apc.primitives`, `apc.plastic`, `apc.consolidation`, and `apc.meta` are not imported anywhere in `apc.evaluation.task_blind_content_gate`). All 682 pre-existing plus new tests pass (`python -m pytest -q`, adding coverage in `tests/test_core_data.py`, `tests/test_core_model.py`, and a new `tests/test_task_blind_content_gate.py`), and `python -m ruff check .` / `python -m mypy src/apc` are both clean.

## ADR-0026 — A1-R002 passes: the causal-mode decode path has no task-conditioned bypass, and a no-primitive/task-blind decoder stays far below the future Correct target

**Status:** Accepted

**Decision:** Task A1-R002 (the decoder leakage control gate, conditional STOP GATE) is recorded as **PASS**.

- **Audit (Work item 1).** `apc.core.execution`'s module docstring records the finding: every causal-mode decode function in the module (`forward_logits`/`generate_greedy_with_capacity`/`evaluate_exact_match_with_capacity`, and A1-C007's oracle-routed siblings) builds its prompt as exactly `(specials.bos,) + example.input_tokens + (specials.sep,)` -- never `apc.core.data.build_prompt_tokens`/`encode_example` with `include_task_spec=True`, and never `example.task_spec` at all -- so no task-segment token id ever reaches `model.encode` through any of them. `tests/test_decoder_leakage.py::test_causal_mode_functions_never_feed_task_tokens_to_encode` verifies this directly (a `model.encode` spy over the bank-routed, oracle-routed, and new no-primitive paths, for real `TaskSpec`-carrying examples, over both a parameterized and a parameter-free operation) by asserting no id in the *initial prompt* falls inside `apc.core.tokens.task_token_id_set` (a helper promoted from A1-R001's own private one, so both gates share one definition of "task token"). Checking only the initial prompt, not every subsequent `model.encode` call in a generation loop, is a deliberate scoping decision: a freshly-initialized (effectively random-output) model can legitimately greedy-generate a token whose id numerically happens to fall in the task-segment range as part of its own answer, which then gets appended and re-encoded on the next step -- that is the model talking to itself, not a task-information bypass, and an initial test draft that checked every call failed on exactly this numerical coincidence (id 30, an argument-value token, appearing only because greedy decoding from a fresh, untrained head can emit anything) before the scoping was narrowed to the prompt alone.
- **Remove task-conditioned bypasses (Work item 2).** The audit found no *live* bypass -- no current caller drives the causal/capacity/oracle-routed functions with a task-spec-carrying input. It did find one *latent* one: `forward_logits(..., use_split_state=True)` computes `content_state` via `model.encode_split(input_ids)`, a single causal pass whose `content_state` is literally `encode(input_ids)` -- if a caller ever passed task-spec-carrying `input_ids` through this branch, `content_state` would have already attended over the task tokens (ADR-0022's finding for `encode_split`, exactly what A1-R001's `encode_task_content_split` two-pass factorization exists to avoid). `use_split_state=True` is exercised only by Task A1-005's own unit tests today, always with content-only input, so there is no code to delete; the fix is a documented restriction (`apc.core.execution`'s module docstring) that the causal *primitive* path must never source `content_state` from `encode_split` for any input that might carry a task segment, rather than a code change to a branch that still serves A1-005's original task_state-routing purpose on content-only input.
- **No-primitive/identity mode (Work item 3).** `apc.core.execution.forward_logits_no_primitive`/`generate_greedy_no_primitive`/`evaluate_exact_match_no_primitive` are new siblings of the bank/oracle-routed functions -- the causal ablation matrix's "None" arm (`docs/design-docs/CAUSAL_PRIMITIVE_EXECUTION.md` section 8) -- with no `bank`/`router`/`workspace` parameter on any of them (`tests/test_decoder_leakage.py::test_no_primitive_functions_never_accept_bank_router_or_workspace`, mirroring A1-C007's `test_oracle_routing_functions_never_accept_a_router`), so primitive execution is structurally unreachable from this path, not merely unused.
- **Evaluate decoder-only task performance (Work item 4).** `apc.evaluation.decoder_leakage_gate` trains one shared core per seed with no task segment ever visible (`apc.evaluation.shared_core_generalization.train_shared_core`, `include_task_spec=False`, identical model/data/training hyperparameters to `configs/phase_a1_shared_core_gate.yaml`'s explicit-task variant for a fair same-family comparison) and evaluates it through `evaluate_exact_match_no_primitive`. `runs/phase_a1_decoder_leakage_gate/report.json`/`summary.json` (config `configs/phase_a1_decoder_leakage_gate.yaml`, 5 seeds `0-4`, RTX 5060 Ti, git commit `6948360`) show: mean overall exact match **0.1401** (stdev 0.0049, min 0.1367, max 0.1484) -- far below both `NO_PRIMITIVE_MATERIAL_CEILING` (0.30, reused from H2b/H2c's own predeclared "None <= 0.30" floor, since neither `docs/CODEX_TASKS_PHASE_A1_POST_CORRECTION.md` A1-R002's acceptance text nor `docs/EXPERIMENT_PLAN_PHASE_A1_POST_CORRECTION.md` -- which has no dedicated hypothesis between H2a and H2b -- spells out a number for "materially below") and the 0.95 future Correct target. Per-operation means: `COPY` 0.754 (expected -- a value-blind identity mapping solvable without any task or primitive information, ADR-0020/ADR-0021), `ACCUMULATE` 0.209 (a mild outlier, consistent with ADR-0021's own note on this same operation), `SHIFT` 0.092, `COMPARE` 0.028, `NEGATE` 0.013, `BIND` 0.012, `COUNT` 0.003, `SELECT` 0.0. `causal_mode_matches_plain_generation` is `true` for every seed: `evaluate_exact_match_no_primitive` and `apc.core.generation.evaluate_exact_match(..., include_task_spec=False)` produce bit-identical exact-match scores and predictions, confirming the newly audited entry point reproduces the pre-existing evaluation path exactly rather than measuring something subtly different.

**Reason:** This is not a new phenomenon to discover -- `apc.evaluation.shared_core_generalization`'s `include_task_spec=False` variant is, by construction, already "train a shared core with no task segment ever visible, evaluate decoder-only exact match," and ADR-0021 already measured it at 0.139 mean overall exact match (5 seeds). This task's own run (0.1401, an independent training run under a fresh git commit and a differently-audited evaluation code path) reproduces that finding closely, which is itself evidence of robustness rather than redundant: it confirms the finding is not an artifact of the specific evaluation function used to measure it (`apc.core.generation.evaluate_exact_match` for ADR-0021 vs. the newly added, structurally primitive-free `apc.core.execution.evaluate_exact_match_no_primitive` here), and the two entry points are shown to agree exactly on the same model/examples rather than merely producing similar-looking aggregate numbers. Training (rather than testing an untrained model, as A1-R001's structural gate did) is necessary here specifically because the claim under test is empirical, not architectural: "no task info reaches the decoder" is proven structurally by the audit, but "therefore a *trained* decoder cannot solve the task anyway" requires actually training one and measuring what it converges to -- an untrained model's near-zero accuracy would not be informative either way.

**Consequence:** Per `docs/exec-plans/active/PHASE_A1_POST_CORRECTION.md`, A1-RM2 (decoder leakage control) is satisfied and A1-R003 (parameter-free oracle primitive benchmark) may proceed -- but only A1-R003 specifically, per `AGENTS.md`'s "Codex workflow." What this task deliberately does *not* provide: any primitive execution wiring, or the "Correct"/"Wrong" arms of the causal ablation matrix (both A1-R003's); and it does not change `forward_logits`'s `use_split_state=True` branch's actual behavior, only documents it as unsuitable for the causal primitive path -- a future task wiring routing into that path (A1-R003 onward) must source `content_state` from `encode` (on content-only ids) or `encode_task_content_split`, never `encode_split`, for any input that might carry a task segment. `docs/AGENTS_PHASE_A1_POST_CORRECTION_ADDENDUM.md`'s "If Correct/Wrong/None are all high, suspect Stable Core or decoder leakage" branch does not apply here, since no primitive-routed "Correct"/"Wrong" condition exists yet to compare against; this gate establishes only that the "None" arm's own future value is trustworthy (not already saturated by a bypass) ahead of A1-R003 adding the other two arms. All 713 pre-existing plus new tests pass (`python -m pytest -q`, adding `tests/test_decoder_leakage.py` and `tests/test_decoder_leakage_gate.py`), and `python -m ruff check .` / `python -m mypy src/apc` are both clean.

**Status:** Accepted

**Decision:** Task A1-R003 (the parameter-free oracle primitive benchmark, STOP GATE, H2b) is recorded as **PASS**. `apc.evaluation.parameter_free_primitive_gate` implements the gate as: (1) pretrain one `apc.core.model.DecoderOnlyTransformer` per seed task-blind (`apc.evaluation.shared_core_generalization.train_shared_core`, `include_task_spec=False`, restricted to `apc.environments.operations.DETERMINISTIC_OPERATION_NAMES` -- `COPY`/`NEGATE`/`COMPARE`/`ACCUMULATE`), then freeze every one of its parameters (`requires_grad_(False)`); (2) register one `apc.primitives.primitive.Primitive` (rank 8) per operation in a fresh `apc.primitives.bank.PrimitiveBank`, keyed at `apc.environments.task_spec.operation_id(name)` (ADR-0024's convention); (3) train only the primitive bank's parameters, via a new gradient-enabled oracle-routing path this task adds to `apc.core.execution` (`apply_bank_with_oracle_calls_trainable`/`forward_logits_with_oracle_calls_trainable` -- the existing A1-C007 `apply_bank_with_oracle_calls`/`forward_logits_with_oracle_calls` stay exactly as they were, always `torch.no_grad()`-wrapped, and are reused unmodified for evaluation); (4) evaluate the causal ablation matrix's three arms on a large unseen batch via `apc.core.execution.evaluate_exact_match_with_oracle_calls` (Correct: `apc.environments.generator.oracle_call_for_example`'s own correct call; Wrong: a fixed derangement over `operation_names` forcing a different family) and `evaluate_exact_match_no_primitive` (None, A1-R002's own entry point, unmodified).

`runs/phase_a1_parameter_free_primitive_gate/report.json`/`summary.json` (config `configs/phase_a1_parameter_free_primitive_gate.yaml`, 5 seeds `0-4`, RTX 5060 Ti, git commit `0bbb290` -- the A1-R002 commit; this run predates A1-R003's own commit, matching ADR-0026's "6948360" precedent of the run preceding the commit that lands its code) show:

This is the first Phase A.1 Post-Correction task where `AGENTS.md`'s "Correct primitive -> high accuracy, Wrong primitive -> low accuracy, No primitive -> low accuracy" success pattern is demonstrated end to end.

**Consequence:** Per `docs/exec-plans/active/PHASE_A1_POST_CORRECTION.md`, A1-RM3 (parameter-free oracle primitive causality) is satisfied and A1-R004 (argument conditioning module) may proceed -- but only A1-R004 specifically, per `AGENTS.md`'s "Codex workflow" ("completion of one task does not authorize beginning the next task"). ## ADR-0028 — A1-R004 argument conditioning module: keyword-only arguments, modulo-bucketed encoders, two encoder shapes for four typed argument slots

**Status:** Accepted

**Decision:** Task A1-R004 (argument conditioning module, milestone A1-RM4) is implemented as `apc.primitives.conditioning`, a new module, plus one small additive constant in `apc.environments.operations`. It is **not** a STOP GATE and is not itself a seeded benchmark (that is A1-R005's job); its acceptance criteria (`docs/CODEX_TASKS_PHASE_A1_POST_CORRECTION.md` A1-R004: "changing argument changes output," "same family handles >=3 values," "persistent family count unchanged," "invalid/missing arguments tested") are demonstrated at the unit level in the new `tests/test_primitives_conditioning.py` (42 cases) rather than via a multi-seed run/report. Contents:

1. `PARAMETERIZED_OPERATION_NAMES` added to `apc.environments.operations` -- the complement of `DETERMINISTIC_OPERATION_NAMES`, *derived* from `Operation.required_argument_names` rather than hardcoded (`("SELECT", "COUNT", "SHIFT", "BIND")` in registration order) so a future operation with a hidden argument is picked up automatically.
2. `ArgumentEncoder` (abstract `nn.Module`) plus two concrete typed encoders, not four: `IntBucketArgumentEncoder` (one bounded integer -> a learned embedding-table lookup via `value % num_buckets`) covers `SHIFT.amount`, `COUNT.target`, and `BIND.query_key` alike -- all three are, at the representation level, "one integer picked from a bounded range," even though `SHIFT.amount` (a rotation distance) and `COUNT.target`/`BIND.query_key` (content-vocabulary tokens, `apc.environments.vocab`) are semantically distinct concepts and therefore get their *own* embedding-table instances (never shared weights across those three). `IndexSetArgumentEncoder` (the mean of learned per-position embeddings over a variable-size index subset, each position also taken modulo the encoder's own capacity) covers `SELECT.indices` -- reusing `docs/DECISIONS.md` ADR-0023's finding that `SELECT`'s real hidden parameter is a subset of positions, never a single scalar index, so a single-integer encoder cannot represent it. `default_argument_encoder(operation, ...)` is what actually gives each of the four operations its own named, appropriately-sized instance, so the module's public surface still presents as "one typed encoder per argument" per the task text, without four near-identical encoder classes.
3. `ConditionedPrimitive(Primitive)` implements `docs/design-docs/CAUSAL_PRIMITIVE_EXECUTION.md` section 6's minimal conditioning formula (`e_a = encoder(argument); u = A_i(h); c = C_i(e_a); delta = B_i(phi(u + c)); out = h + gate * delta`) directly on top of the existing `a_proj`/`b_proj` (`A_i`/`B_i`, Task 004/A1-R003), adding one linear map `c_proj` (`C_i`) and reusing `apc.core.model.DecoderOnlyTransformer`'s own `GELU` for `phi`. `a_proj`/`b_proj`/`c_proj`/`argument_encoder` are all shared across every argument value the family is ever called with -- there is no per-value parameter, satisfying "shared family weights across values" by construction rather than by a runtime check. `build_conditioned_primitive(primitive_id, operation, config, ...)` mints one instance per family, keyed at the caller-supplied `primitive_id` (intended usage: `apc.environments.task_spec.operation_id(operation)`, ADR-0024's convention, verified in `tests/test_primitives_conditioning.py::test_build_conditioned_primitive_uses_the_operations_own_argument_name`), and subclasses `Primitive` (not a parallel type) specifically so a future `PrimitiveBank` can hold it via the existing `add_primitive`/`get` path (`PrimitiveBank.get`'s `isinstance(primitive, Primitive)` assertion) with no `apc.primitives.bank` change required.

**Reason:** Two design questions were not settled by `docs/design-docs/PARAMETERIZED_PRIMITIVE_CALLS.md`/`CAUSAL_PRIMITIVE_EXECUTION.md` and needed a concrete answer before implementation:

*Invalid vs. missing arguments (A1-R004's own "invalid/missing arguments tested" criterion names two different failure modes that call for two different behaviors).* An "invalid" argument -- syntactically well-typed but outside a family's declared range, e.g. `SHIFT.amount = 500` against a 32-bucket table -- must not raise, because A1-R005's own "correct family + wrong argument" causal control (H2c, `docs/EXPERIMENT_PLAN_PHASE_A1_POST_CORRECTION.md` section 4) needs to be able to *construct and run* exactly such a call, not have it rejected. Both encoders therefore wrap any out-of-range integer via `torch.remainder(value, capacity)` rather than validating a range. A "missing" argument -- the caller forgot to supply one at all -- is the opposite case and should fail loudly, so `ConditionedPrimitive.forward`'s `argument_values` parameter is keyword-only with no default. This was chosen specifically because `apc.core.execution.apply_bank`/`_route_and_apply_oracle_calls` invoke every routed bank primitive as `primitive(selected_hidden)` -- a single positional argument, no keywords, gate applied outside the call -- so if `argument_values` were an ordinary optional parameter with a default, a `ConditionedPrimitive` accidentally placed in a bank routed through today's argument-blind execution path would silently receive that default (e.g. `None`) on every call instead of failing: exactly the "argument present in the call but ignored by the neural transform" AGENTS.md's parameterized-primitives rule forbids, except silent rather than caught by any test. Keyword-only closes this structurally: any accidental use of `ConditionedPrimitive` through the existing A1-C007/A1-R003 call sites raises `TypeError` immediately rather than quietly executing an argument-blind transform. `forward_from_calls(h, calls)` is the safe entry point for the intended `PrimitiveCall`-carrying caller (A1-R005); it raises `KeyError` if a given call's `operation` does not carry this primitive's own `argument_name` at all -- a mismatched call, not merely an out-of-range value.

*Two encoder classes vs. four.* A four-class design (one class literally named after each argument) was considered and rejected: `SHIFT.amount`, `COUNT.target`, and `BIND.query_key` share an identical representation shape (one bounded integer -> embedding-table row), so four classes would mean three of them differ only in constructor arguments (`num_buckets`) -- duplicated code with no representational benefit, contrary to `AGENTS.md`'s "do not introduce ... unnecessarily general function signatures" and "keep research code readable." `default_argument_encoder` resolves the tension: it is the thing that is actually keyed one-per-operation-name (four branches, four independently-sized instances with no shared weights, even between `COUNT` and `BIND` which share a value domain but not a learned meaning), while the underlying implementation stays at two classes matching the two genuinely distinct raw shapes (`docs/design-docs/PARAMETERIZED_PRIMITIVE_CALLS.md` never specifies argument *encoding* beyond "possible implementations: ... learned argument embeddings," leaving this open).

**Consequence:** Per `docs/exec-plans/active/PHASE_A1_POST_CORRECTION.md`, A1-RM4 (argument-conditioned neural primitives: "one family handles multiple arguments without family growth") is satisfied and A1-R005 (parameterized oracle primitive benchmark, STOP GATE, H2c) may proceed -- but only A1-R005 specifically. What this task deliberately does *not* provide, left for A1-R005: wiring `PrimitiveCall.arguments` through `apc.core.execution`'s oracle-routing entry points (`apply_bank_with_oracle_calls*`/`forward_logits_with_oracle_calls*` still call every bank primitive as `primitive(selected_hidden)`, which now raises `TypeError` for a `ConditionedPrimitive` rather than silently mishandling it -- a deliberate fail-loud gap, not an oversight); any training of a `ConditionedPrimitive`; measuring Correct/Wrong-family/Wrong-argument/None; and promotion to a persistent `STABLE` bank or consolidation. All 787 tests pass (`python -m pytest -q`: 745 pre-existing + 42 new in `tests/test_primitives_conditioning.py`), and `python -m ruff check .` / `python -m mypy src/apc` are both clean.

## ADR-0029 — A1-R005 STOP GATE fails: argument-conditioned primitives are family-selective but not argument-selective, and multi-token exact match ceilings SHIFT/SELECT

**Status:** Accepted

**Decision:** Task A1-R005 (the parameterized oracle primitive benchmark, STOP GATE, H2c) is recorded as **FAIL**. `apc.evaluation.parameterized_primitive_gate` implements the gate exactly as A1-R003's own precedent (ADR-0027): pretrain-then-freeze one task-blind `DecoderOnlyTransformer` per seed (`include_task_spec=False`, restricted to `apc.environments.operations.PARAMETERIZED_OPERATION_NAMES` -- `SHIFT`/`SELECT`/`COUNT`/`BIND`), register one `apc.primitives.conditioning.ConditionedPrimitive` (rank 8) per operation in a fresh `PrimitiveBank`, train only the primitive bank via oracle-forced routing that now threads each example's own argument through (`apc.core.execution`'s A1-R005 dispatch addition to `_route_and_apply_oracle_calls`, routing a `ConditionedPrimitive` through `forward_from_calls` instead of the old argument-blind call), and evaluate the four-arm causal ablation matrix (`docs/design-docs/CAUSAL_PRIMITIVE_EXECUTION.md` section 8) on a large unseen batch: **Correct** (correct family + correct argument), **Wrong argument** (correct family + a deterministic "+1 modulo the argument's own valid domain" substitution), **Wrong family** (a fixed derangement, forced with a fixed default argument), **None** (`apc.core.execution.evaluate_exact_match_no_primitive`, unchanged from A1-R002).

`runs/phase_a1_parameterized_primitive_gate/report.json`/`summary.json` (config `configs/phase_a1_parameterized_primitive_gate.yaml`, 5 seeds `0-4`, RTX 5060 Ti, git commit `4edc4c0` -- the A1-R004 commit; this run predates A1-R005's own commit, matching ADR-0026/ADR-0027's precedent of the run preceding the commit that lands its code) show, against the cross-seed mean:

| Arm | Mean | Required |
|---|---|---|
| Correct | **0.308** (stdev 0.017, min 0.290, max 0.328) | >= 0.90 |
| Wrong argument | 0.255 | <= 0.30 |
| Wrong family | 0.028 | <= 0.30 |
| None | 0.143 | <= 0.30 |
| Causal gap (Correct - max of the three) | **0.053** | >= 0.50 |

`correct_passed=false`, `causal_gap_passed=false`; `wrong_argument_passed`/`wrong_family_passed`/`none_passed`/`family_count_passed` are all trivially `true` (every control arm clears its ceiling only because `Correct` itself is far below target, not because the gate demonstrates the intended causal pattern). Per-operation mean Correct: `COUNT` 0.595, `BIND` 0.420, `SHIFT` 0.161, `SELECT` 0.047.

**Reason:** Two distinct findings, both visible directly in the numbers above, together explain the failure without requiring further instrumentation:

1. **Family selection is strongly causal; argument selection within a family is barely causal.** `Wrong family` (0.028) collapsing far below `Correct` (0.308) reproduces A1-R003's own core finding (ADR-0027: forcing the wrong computation family produces systematically wrong output) -- the frozen core's `h_content` genuinely carries family-selective computation once a `ConditionedPrimitive` reads it. But `Wrong argument` (0.255) sits only ~0.05 below `Correct` (0.308), not "materially lower" by any reading of H2c's own text -- i.e. once the *correct family* is selected, substituting a wrong-but-valid argument barely changes the outcome. This means `ConditionedPrimitive`'s `c_proj`/`argument_encoder` path (Task A1-R004, ADR-0028) is not, at this training budget, learning to make the residual actually depend on the argument value in a way that changes the *output tokens* -- exactly the failure mode `AGENTS.md`'s "arguments that are stored or logged but ignored by the neural transform do not count as parameterized execution" warns about, now observed empirically rather than merely guarded against structurally (Task A1-R004's `forward_from_calls`/keyword-only design prevents the argument from being *silently dropped*, but does not by itself guarantee it is *learned*).

2. **Per-operation Correct tracks output length, not operation difficulty in isolation.** `COUNT` (single output token, 0.595) and `BIND` (single output token, 0.420) reach far higher exact match than `SHIFT` (full-length rotation, up to 10 output tokens, 0.161) or `SELECT` (variable-length ordered subset, up to 5 output tokens, 0.047). Exact-match scoring requires every output position correct simultaneously, so if per-token accuracy were even roughly comparable across operations, multi-token outputs would show a compounding exact-match penalty (`p^n` for `n` positions) that single-token outputs never pay. This is consistent with, and does not require rejecting, finding 1: `SHIFT`/`SELECT` additionally need the argument to correctly select *which* rotation/subset at *every* output position, so their `Correct` score is suppressed by both the weak argument-selectivity of finding 1 and the multi-token compounding of finding 2 at once, while `COUNT`/`BIND`'s single-token output only pays the former cost.

Reused training budget from A1-R003 (`core_train.steps=30000`, `primitive_train.steps=10000`, `primitive_rank=8`, matching `configs/phase_a1_parameter_free_primitive_gate.yaml` exactly) was a deliberate choice, not an oversight: `AGENTS.md`'s engineering principles ask for "the smallest implementation that can falsify the current hypothesis," and A1-R003 (H2b, parameter-free primitives on the same frozen-core strategy) already demonstrated that budget is sufficient to reach Correct >= 0.999 for `COPY`/`NEGATE`/`COMPARE`/`ACCUMULATE`. Reusing it unchanged isolates *what changed* (argument conditioning, `ConditionedPrimitive`'s extra `c_proj`/`argument_encoder` capacity, and a harder operation pool including full-sequence-length outputs) as the only variable between a passing gate (A1-R003) and this failing one, rather than confounding the comparison with a simultaneously enlarged budget.

**Consequence:** Per `AGENTS.md`'s STOP GATE discipline, dependent work halts here: A1-R006 (unified oracle primitive benchmark, which composes A1-R003's and A1-R005's own primitive families) and everything after it in `docs/CODEX_TASKS_PHASE_A1_POST_CORRECTION.md` remain blocked until this gate passes. Per `AGENTS.md`'s "Do not hide negative results by increasing model size prematurely, expanding data without a specific hypothesis, ... or adding a larger router": no larger `primitive_rank`, longer `primitive_train.steps`, nor architecture change has been applied in response to this result -- the config, code, and this ADR are the STOP GATE record, and any retry needs its own explicit, hypothesis-driven task rather than a silent parameter bump. Candidate hypotheses for a future A1-R005 retry task, none executed here: (a) argument-selectivity may need more `primitive_train` steps specifically (the argument-conditioning path is strictly newer/less-exercised machinery than `a_proj`/`b_proj` alone), (b) `arg_dim`/`c_proj` capacity relative to `rank=8` may be a bottleneck for `SHIFT`'s/`SELECT`'s position-indexed arguments specifically (both route through the same rank-8 residual `COUNT`/`BIND` use, despite needing to select among as many as `max_sequence_length` distinct rotations/subsets rather than `vocab_size` content values), (c) `SHIFT`/`SELECT`'s multi-token output may warrant measuring per-token accuracy alongside exact match to separate "argument not learned" from "compounding exact-match penalty" more cleanly than the aggregate numbers above can alone. What this task does *not* put in doubt: A1-R004's own acceptance (ADR-0028, unit-level: changing an argument does change a freshly-perturbed `ConditionedPrimitive`'s raw output in isolation) -- the gap found here is that this capacity is not learned to be *task-relevant* at this training budget/operation pool, not that the module cannot represent argument-dependence at all. `apc.core.execution`'s A1-R005 dispatch wiring (`_route_and_apply_oracle_calls` routing a `ConditionedPrimitive` through `forward_from_calls`) is exercised correctly by this run (`family_count_passed=true` every seed, `bank_size=4` throughout, matching "family count stays constant across argument values") and by `tests/test_oracle_routing.py`'s new dispatch tests -- the wiring is not itself implicated by this failure. All 825 tests pass (`python -m pytest -q`: adding 34 in the new `tests/test_parameterized_primitive_gate.py` and 6 in `tests/test_oracle_routing.py`'s new `ConditionedPrimitive` dispatch section; net of removing one long-orphaned Task 012 test, see below), and `python -m ruff check .` / `python -m mypy src/apc` are both clean.

**Unrelated cleanup recorded here for the same commit:** `tests/test_sequential_benchmark.py::test_two_events_each_complete_a_learn_consolidate_release_cycle` (Task 012's own "at least two learn/consolidate/release cycles in one task stream" acceptance check, `docs/TASKS.md` Task 012) was deleted at the user's explicit direction after confirming (via `git stash`, reproducing the failure against the unmodified A1-R004 commit) that it was a deterministic, non-flaky failure of an abandoned goal -- Task 012/Phase A's sequential benchmark was decided not to be pursued to completion, leaving this assertion orphaned against current `apc.evaluation.sequential_benchmark` behavior. The module-scoped `two_cycle_report` fixture and the other test consuming it (`test_report_to_dict_round_trips_through_json`) are unaffected and still pass. This is unrelated to A1-R005's own STOP GATE result above and does not affect its FAIL verdict.

## ADR-0030 — A1-R005D-001 re-analysis: the wrong-argument confound is not the explanation, and per-example model predictions turn out not to be recoverable post hoc

**Status:** Accepted

**Decision:** Task A1-R005D-001 (`docs/CODEX_TASKS_A1_R005_RETRY.md`, "Re-analyze existing R005 artifacts ... expand diagnostics without retraining") is recorded as **done**. New module `apc.evaluation.parameterized_primitive_gate_reanalysis` (`scripts/r005d001_reanalyze_parameterized_primitive_gate.py`) re-analyzes the frozen `runs/phase_a1_parameterized_primitive_gate/` artifacts (ADR-0029) read-only: it never constructs, trains, or runs a forward pass through any model. Two things are computed without a model, both pure functions of the deterministic generator/interpreter (`apc.environments.generator.TaskGenerator.generate_online`, `apc.environments.primitive_call.PrimitiveCall.execute`): `argument_effect_rate` (`docs/AGENTS_A1_R005_RETRY_ADDENDUM.md`'s `argument_effect = [target(correct_arg) != target(wrong_arg)]`) and target-output-length statistics. Reconstruction fidelity is self-checked: for every one of the 5 seeds, the regenerated unseen-eval batch's `per_operation_eval_counts` matched the saved report's own counts exactly (byte-identical reconstruction), so the newly computed numbers below sit on the *same* 4096-example batch each original run actually scored.

Cross-seed mean, `runs/a1_r005d_001_reanalysis/report.json` (5 seeds 0-4, CPU, no GPU/training involved):

| Operation | Correct | Wrong argument (raw) | gap | argument_effect_rate | mean target length |
|---|---|---|---|---|---|
| SHIFT | 0.161 | 0.117 | 0.044 | **1.000** | 8.04 |
| SELECT | 0.047 | 0.042 | 0.005 | **0.992** | 3.80 |
| COUNT | 0.595 | 0.443 | 0.152 | 0.667 | 1.00 |
| BIND | 0.420 | 0.411 | 0.009 | 0.900 | 1.00 |

**Reason:** This directly resolves candidate failure mode F1 in `docs/design-docs/PARAMETERIZED_PRIMITIVE_RETRY.md` ("Wrong-argument control is partially non-causal") as **not** the explanation for A1-R005's failure. If the small raw Correct-vs-Wrong-argument gap were mostly an artifact of non-effectful examples (cases where the deterministic "+1 modulo domain" substitution happens to leave the ground-truth target unchanged, so a causally-correct model would still score "correct" under the Wrong-argument arm by coincidence), `argument_effect_rate` would need to be low. It is not: SHIFT is effectful on literally 100% of the eval batch, SELECT on 99.2%, BIND on 90.0%, and even COUNT -- the lowest -- is effectful on 66.7%. Since the wrong argument overwhelmingly *does* change the correct answer, ADR-0029's finding 1 (the `ConditionedPrimitive` argument-conditioning path is not learning to make output tokens depend on the argument) stands as the primary explanation, not a confound of the control's own construction. This also reframes the per-operation picture: COUNT has the *lowest* argument_effect_rate of the four yet the *largest* raw Correct-minus-Wrong-argument gap (0.152, vs 0.009 for BIND and 0.005 for SELECT) -- i.e. COUNT is, relatively, the operation showing the most argument-sensitive behavior already, which is consistent with `docs/design-docs/PARAMETERIZED_PRIMITIVE_RETRY.md` section 6 prioritizing COUNT first for the D-004 counterfactual gate.

A second finding is about the diagnostic infrastructure itself, not the model: token accuracy and a wrong-argument exact match restricted to the effectful subset (`docs/CODEX_TASKS_A1_R005_RETRY.md` A1-R005D-001's other two requested metrics) are **not recoverable** from the existing run. `apc.evaluation.parameterized_primitive_gate.ParameterizedPrimitiveGateReport` persists only aggregate exact-match scores per arm/operation, never per-example model predictions or logits, and no model checkpoint was saved. Recomputing either metric would require reproducing the exact trained primitive bank (rerunning `_pretrain_frozen_stable_core` and `_train_primitives`), which is retraining by any reading of this task's own "without retraining" scope. `SeedReanalysis`/`RunReanalysis` report both fields explicitly as `None` with a `not_recoverable` reason attached (never silently omitted or conflated with the raw score), satisfying A1-R005D-001's "raw and effectful wrong-argument scores clearly separated" acceptance criterion by being honest that the effectful score is currently unmeasurable rather than by fabricating or approximating it.

**Consequence:** No architecture or capacity change is made here (`docs/AGENTS_A1_R005_RETRY_ADDENDUM.md`'s "No blind scaling"; this task's own D-010 "No new architecture in this task" boundary, applied early rather than only at the end). A1-R006 remains blocked, matching ADR-0029's original STOP GATE consequence; the retry sequence proceeds to A1-R005D-002 (argument encoder integrity audit) as `docs/exec-plans/active/A1_R005_RETRY.md`'s milestone order specifies. Recommendation carried forward, not implemented here: whatever run script eventually re-executes training for D-004 onward should persist per-example predictions (or at least the effectful/non-effectful split and per-token match count) alongside the aggregate scores it already writes, so this gap does not recur for the final A1-R005D-009 retry. Existing `runs/phase_a1_parameterized_primitive_gate/` artifacts are unmodified (verified byte-identical before/after by both the re-analysis script's own read-only design and `tests/test_parameterized_primitive_gate_reanalysis.py::test_reanalyze_run_does_not_modify_existing_artifacts`). New tests: `tests/test_parameterized_primitive_gate_reanalysis.py` (18 cases: argument-effect computation cross-checked against an independent `Operation.apply` call path for all four operations, deterministic/byte-identical batch reconstruction, not-recoverable flagging, cross-seed aggregation, and an operation-name-mismatch guard). Full suite (`python -m pytest -q`), `python -m ruff check .`, and `python -m mypy src/apc` are all clean after this change.

## ADR-0031 — A1-R005D-002 audit: `SELECT`'s mean-pooled index encoder is a structural, weight-independent collision; `SHIFT`/`COUNT`/`BIND` are injective on their real legal domains

**Status:** Accepted

**Decision:** Task A1-R005D-002 (`docs/CODEX_TASKS_A1_R005_RETRY.md`, "argument encoder integrity audit ... detect representation collisions before training") is recorded as **done**, with the SELECT half of its own acceptance criteria resolving to **non-injective, STOP GATE in force**. New module `apc.primitives.argument_encoder_audit` (`scripts/r005d002_audit_argument_encoders.py`) audits every `apc.primitives.conditioning.default_argument_encoder` instance without constructing, training, or loading any `DecoderOnlyTransformer` -- pure forward passes through freshly constructed `ArgumentEncoder`s.

- **`SELECT.indices` (`IndexSetArgumentEncoder`, mean-pooled over per-position embeddings).** `audit_select_order_sensitivity` runs 5 declared permutation pairs -- the task's own `[1, 3]` vs `[3, 1]` example, a longer reversal, and two repeated-index permutations (`(1, 1, 3)` vs `(1, 3, 1)`/`(3, 1, 1)`, legal per `apc.environments.primitive_call.PrimitiveCall.__post_init__`'s lack of any uniqueness/order constraint on `indices`, and per `apc.environments.operations.SelectOp.apply` executing a repeated index without error even though `SelectOp.sample_params` itself never produces one) -- across 3 independently-seeded encoder instances (`runs/a1_r005d_002_argument_encoder_audit/report.json`). Every one of the 5 pairs collides in every one of the 3 seeds (`max_absolute_difference` at or below float32 rounding noise, ~1.2e-7, not exactly `0.0`, since summing the same embedding rows in a different order is float-non-associative -- `tests/test_primitives_conditioning.py::test_index_set_encoder_is_order_invariant`'s own `atol=1e-6` precedent). This is expected, not merely observed: mean is commutative, so the collision is a property of the pooling operator itself, true for *any* embedding weights, not a coincidence of these particular seeds -- the multi-seed sweep demonstrates rather than merely asserts that weight-independence. 3 declared distinct-same-length index-set pairs (non-permutations, e.g. `(0, 1, 2)` vs `(3, 4, 5)`) show **no** collision at any checked seed, confirming the failure is specifically about order/multiplicity, not a general collapse of the representation.
- **`SHIFT.amount`/`COUNT.target`/`BIND.query_key` (`IntBucketArgumentEncoder`, modulo-bucketed embedding lookup).** `audit_int_bucket_encoder` checks every pair of *distinct* values in each operation's real legal domain -- `range(10)` for `SHIFT.amount` (`apc.environments.operations.ShiftOp.sample_params` draws from `range(len(sequence))`, and `apc.environments.generator.TaskGenerator`'s default `sequence_length_range=(6, 10)` bounds `len(sequence)` at 10 inclusive per `_valid_lengths_for_chain`'s `range(min_len, max_len + 1)` -- the same upper bound `apc.environments.task_spec.default_argument_value_span` already treats as authoritative for this domain), `range(10)` for `COUNT.target`/`BIND.query_key` (`apc.environments.vocab.DEFAULT_VOCAB_SIZE`) -- against `default_argument_encoder`'s current `num_buckets` (32 for `SHIFT`, matching `DEFAULT_MAX_SEQUENCE_LENGTH`; 10 for `COUNT`/`BIND`, matching `vocab_size`). All three are **injective on their real legal domain**: zero colliding pairs at any of the 100 (`SHIFT`) or 45+45 (`COUNT`/`BIND`) distinct-value pairs checked. A deliberately out-of-domain probe (`max(legal_domain) + num_buckets`, e.g. `41` for `SHIFT`) confirms the wraparound path is reachable and lands exactly on the largest legal value (`max_absolute_difference == 0.0`, an exact embedding-table row match) -- the intentional aliasing `docs/DECISIONS.md` ADR-0028 designed for A1-R005's "correct family + wrong argument" causal control, not an accidental in-domain collision. A regression test (`test_int_bucket_audit_catches_a_deliberately_undersized_bucket_table`, a `num_buckets=5` encoder against the same `range(10)` domain) confirms the audit *would* catch a real misconfiguration rather than trivially passing regardless of input.

**Reason:** `docs/AGENTS_A1_R005_RETRY_ADDENDUM.md`'s "SELECT rule" already stated the hypothesis -- "a commutative pooling representation such as mean/sum is invalid for an ordered index sequence unless an explicit experiment proves otherwise" -- and `tests/test_primitives_conditioning.py::test_index_set_encoder_is_order_invariant` already demonstrated the underlying fact at the unit level when A1-R004 landed (written then as expected/acceptable behavior, before this retry's stricter order-preservation rule existed). This task's contribution is not discovering a new fact but (a) connecting that fact explicitly to the SELECT/`argument_effect_rate` findings already on record (ADR-0029's `SELECT` Correct 0.047 lowest of all four operations; ADR-0030's re-analysis found `SELECT`'s wrong-argument control effectful on 99.2% of examples yet the raw Correct-vs-Wrong-argument gap only 0.005 -- entirely consistent with an encoder that structurally cannot represent *which* subset-with-order was requested, on top of ADR-0029's own multi-token exact-match compounding explanation) and (b) making the STOP GATE enforceable rather than only documented: `require_order_preserving_select_encoder` actually runs an encoder against `[1, 3]`/`[3, 1]` and raises `NonInjectiveSelectEncoderError` if they collide -- behavior-based, not an `isinstance` check, so it also catches a future replacement encoder that happens to still be order-insensitive. This guard is deliberately **not** wired into `apc.primitives.conditioning.build_conditioned_primitive`/`default_argument_encoder` themselves: those are A1-R004's already-accepted surface (ADR-0028), still exercised unchanged by `tests/test_primitives_conditioning.py`'s existing acceptance tests, and A1-R005D-002's own scope is audit-and-gate-future-training, not replacing the encoder (that is explicitly A1-R005D-003's job, itself conditioned on "skip only if D-002 proves current representation sufficient" -- resolved here as **not sufficient**).

**Consequence:** Per `docs/exec-plans/active/A1_R005_RETRY.md`, R005-M2 (argument encoder integrity) is satisfied with a **non-injective** verdict for `SELECT`, and the STOP GATE named in A1-R005D-002's own task text is now in force and enforceable: *no future task may train `SELECT` through `apc.primitives.conditioning.IndexSetArgumentEncoder`* without first calling `apc.primitives.argument_encoder_audit.require_order_preserving_select_encoder` (or otherwise replacing the encoder) -- A1-R005D-003 (order-preserving SELECT argument encoder) is **not skipped** and remains required before any SELECT counterfactual/gate task (D-004 onward, when it reaches SELECT) trains against real order-sensitive supervision. `SHIFT`/`COUNT`/`BIND` carry no such block: their current `IntBucketArgumentEncoder` instances are confirmed injective on Phase A.1's actual generator/vocab defaults, so D-004's COUNT counterfactual gate may proceed without an encoder change. ## ADR-0032 — A1-R005D-003: order-preserving `SELECT` argument encoder replaces mean pooling as the production default

**Status:** Accepted

**Decision:** Task A1-R005D-003 (`docs/CODEX_TASKS_A1_R005_RETRY.md`, "replace mean pooling if D-002 confirms order loss") is implemented. ADR-0031 resolved D-003's own "skip only if D-002 proves current representation sufficient" condition as **not sufficient** (SELECT's mean-pooled `IndexSetArgumentEncoder` collides on every permutation pair in every seed), so this task is not skipped.

New class `apc.primitives.conditioning.OrderPreservingIndexSetArgumentEncoder` (`ArgumentEncoder` subclass, same module) implements the task's own "preferred minimal form" directly: per selected position `i` (0-indexed by its slot *within the argument list*), `token_i = index_embedding[value_i mod max_positions] + position_embedding[i mod max_positions]`; the resulting `[batch, seq_len, arg_dim]` token sequence passes through one `nn.TransformerEncoderLayer` (`nhead=1`, `dim_feedforward=2*arg_dim`, `dropout=0.0`, `batch_first=True`) with a `src_key_padding_mask` for batches of unequal-length index lists, then a masked mean pool over valid (non-pad) positions produces the fixed-size `[batch, arg_dim]` embedding. `default_argument_encoder("SELECT", ...)` (`apc.primitives.conditioning`) now returns this encoder instead of `IndexSetArgumentEncoder`; `build_conditioned_primitive`/`ConditionedPrimitive` are unchanged (they already treat `argument_encoder` as an opaque `ArgumentEncoder`, so no other code needed to change). `IndexSetArgumentEncoder` itself is left exactly as A1-R004 built it -- still directly constructible, still exercised by its own existing tests -- just no longer reachable through the default factory.

Why a position embedding alone does not suffice, and a nonlinear mixing step is required: adding `position_embedding[i]` to `index_embedding[value_i]` and then reducing with any *linear, permutation-symmetric* operator (sum or mean) still cannot distinguish an assignment of values to slots from a different one, because such a reduction is exactly `(sum of index embeddings) + (sum of position embeddings)` -- both sums range over the same two multisets (the selected values, and the positions `0..n-1`) regardless of which value was paired with which position. `[1, 3]` and `[3, 1]` therefore still collide under "embed + positional-add + mean." The self-attention layer is the part that actually breaks this: its query/key dot products are quadratic in the per-slot vectors, so the attention weights -- and hence the pre-pooling encoded sequence each slot produces -- depend on which index occupies which slot, not merely on the multiset of `(index, position)` pairs present. `dropout=0.0` (applied to both the attention weights and the two post-attention/post-feedforward dropout layers `nn.TransformerEncoderLayer` wires internally from the same constructor argument) makes the forward pass deterministic regardless of `self.training`, rather than relying on callers to remember `.eval()`.

New tests in `tests/test_primitives_conditioning.py` (14 cases) cover the task's own acceptance criteria directly: `[1, 3]` vs `[3, 1]` distinct (single seed and across 5 independent seeds, matching ADR-0031's own multi-seed precedent for the collision it found), repeated-index permutations distinct, variable-length index sets in one batched call, a short row's output is bit-identical whether or not it is batched alongside a longer row (the padding-mask acceptance criterion -- proves the mask actually excludes padded slots from attention/pooling rather than merely zeroing them after the fact), determinism across repeated calls and in `.train()` mode, plus the same wrap/reject/shape edge-case coverage `IndexSetArgumentEncoder`'s own tests already had (out-of-range wraparound, empty batch, empty index subset, non-positive `max_positions`/`arg_dim`). `tests/test_argument_encoder_audit.py` is updated in the two places that exercised the *production default* rather than `IndexSetArgumentEncoder` directly: `audit_phase_a1_default_argument_encoders` now finds no SELECT collision (renamed from `test_phase_a1_audit_select_collides_in_every_checked_seed` to `test_phase_a1_audit_select_no_longer_collides_after_d003`, docstring explaining the change is the intended consequence of D-003 landing, not a regression), and a new test confirms `require_order_preserving_select_encoder` (ADR-0031's STOP GATE guard) no longer raises for `default_argument_encoder("SELECT")`. All tests that construct `IndexSetArgumentEncoder` directly are untouched and still pass, since that class's own behavior did not change.

**Reason:** `docs/AGENTS_A1_R005_RETRY_ADDENDUM.md`'s "SELECT rule" required an order- and multiplicity-preserving representation once D-002 showed the existing one was structurally incapable of this; `AGENTS.md`'s "Parameterized primitives" section additionally rules out "do not introduce hypernetworks or unnecessarily general function signatures," which is why the design stays at one attention layer / `nhead=1` / a feedforward width of `2*arg_dim` rather than a deeper or wider sequence model, and reuses a single `max_positions` parameter for both the index-value table and the argument-position table (`SelectOp.output_length` never selects more positions than the input sequence has, so the same declared sequence-length capacity already bounds both).

**Consequence:** Per `docs/exec-plans/active/A1_R005_RETRY.md`, R005-M2's `SELECT` STOP GATE (ADR-0031: "no future task may train `SELECT` through `IndexSetArgumentEncoder`") is satisfied for the production default going forward -- `default_argument_encoder("SELECT", ...)` now returns an encoder `require_order_preserving_select_encoder` accepts. This does not by itself retrain or re-run any benchmark: D-004 (COUNT counterfactual gate) does not touch SELECT and may proceed regardless; D-008 (SHIFT/SELECT sequence gates) is where this encoder is first exercised under real training, and D-009 (final retry) is where SELECT's Correct/causal-gap numbers are actually re-measured. Whether the new encoder's *learned* argument-selectivity (as opposed to its structural distinguishability, demonstrated here) is sufficient for D-008/D-009's thresholds is explicitly not decided by this task -- ADR-0029's finding that argument-conditioning capacity was weakly learned under the original training budget applies to `COUNT`/`BIND` (both already structurally injective) too, so an order-preserving *encoding* for `SELECT` is necessary but this task does not claim it is sufficient. Full suite (`python -m pytest -q`: 873 passed, 1 skipped, up from 858 passed/1 skipped before this change), `python -m ruff check .`, and `python -m mypy src/apc` are all clean after this change.

## ADR-0035 — A1-R005D-006 STOP GATE fails: FiLM/gated-multiplicative conditioning narrows COUNT's causal gap but still falls far short; basis modulation is actively worse than additive

**Status:** Accepted

**Decision:** Task A1-R005D-006 (`docs/CODEX_TASKS_A1_R005_RETRY.md`, "Conditioning architecture comparison," STOP GATE) is recorded as **no variant passed**. `apc.primitives.conditioning` gained a common abstract base `ArgumentConditionedPrimitive(Primitive, ABC)` (`forward_from_calls` shared, `forward(h, *, argument_values, gate=1.0)` abstract) and two new subclasses implementing the two alternative formulas the task text names:

- `FiLMConditionedPrimitive` (**V1**, gated multiplicative): `gamma, beta = split(FiLM_i(e_a))`; `delta = B_i(phi((1 + gamma) * u + beta))` -- the argument multiplicatively gates the content projection `u = A_i(h)` itself, rather than only ever being summed alongside it.
- `BasisModulatedConditionedPrimitive` (**V2**, basis modulation, the task's own "optional" variant, implemented here since it is cheap at this experiment's scale): `mix = softmax(mix_proj(e_a))`; `c = mix @ basis` (`basis`: a shared `[num_basis, rank]` learned dictionary, `num_basis=8`); `delta = B_i(phi(u + c))` -- keeps V0's additive-sum structure but constrains the argument's reachable conditioning vector to a small convex combination of shared basis directions instead of a free linear map.

`ConditionedPrimitive` (**V0**, unchanged) is the third variant. `apc.core.execution._route_and_apply_oracle_calls`'s dispatch check was generalized from `isinstance(primitive, ConditionedPrimitive)` to `isinstance(primitive, ArgumentConditionedPrimitive)` (a strict widening -- every existing call site's behavior is unchanged) so V1/V2 route through `forward_from_calls` the same way V0 already did, with no other change to that module. `apc.evaluation.count_counterfactual_gate` (ADR-0033/ADR-0034's already-validated gate) gained a `variant`/`num_basis` parameter threaded through `_build_primitive_bank`/`_train_primitives`/`run_count_counterfactual_gate[_multi_seed]`, defaulting to `ConditioningVariant.ADDITIVE` (byte-identical to every pre-D-006 call); new module `apc.evaluation.count_conditioning_architecture_gate` (`scripts/count_conditioning_architecture_gate.py`, `configs/phase_a1_count_conditioning_architecture_gate.yaml`) runs all three variants **unconditionally** (no early stopping, unlike D-005's staged sweep) against A1-R005D-004's own baseline config, unmodified ("Keep Stable Core and data fixed" -- `primitive_rank=8`, `primitive_train.steps=10000`, `arg_dim=16`, identical to ADR-0033/ADR-0034), then applies the task's own selection rule: disqualify a non-baseline variant if its mean Correct *and* mean effectful-Wrong-argument both exceed V0's own ("do not choose a model that raises Correct and Wrong together"), then choose the highest-causal-gap variant among the rest that actually passes (`None` if none do).

## ADR-0036 — A1-R005D-007 STOP GATE fails: BIND's causal gap is statistically zero -- Correct, effectful Wrong argument, and None are indistinguishable, and all three match a content-only "last pair" heuristic

**Status:** Accepted

**Decision:** Task A1-R005D-007 (`docs/CODEX_TASKS_A1_R005_RETRY.md`, "BIND counterfactual gate") is recorded as **FAIL**. New module `apc.evaluation.bind_counterfactual_gate` (`scripts/bind_counterfactual_gate.py`, `configs/phase_a1_bind_counterfactual_gate.yaml`) runs A1-R005D-004's own counterfactual-group protocol (ADR-0033) against `BIND` instead of `COUNT`, at the identical baseline architecture (V0/additive `apc.primitives.conditioning.ConditionedPrimitive`, `primitive_rank=8`, `arg_dim=16`, `core_train`/`primitive_train` byte-identical to `configs/phase_a1_count_counterfactual_gate.yaml`) -- per this task's own text, there is no reason to re-run A1-R005D-006's conditioning-architecture comparison for `BIND` specifically, so this task does not repeat it.

`BIND` (`apc.environments.operations.BindOp`) differs from `COUNT` in the two ways that required a new (not reused) group generator: (1) it needs an *even*-length key/value input (`is_valid_for_length`), so `_valid_bind_lengths` restricts candidate content lengths to the even values in `sequence_length_range`; (2) its argument (`query_key`) is drawn only from keys *actually present* in the content (`BindOp.sample_params`), not the whole vocabulary, so `generate_bind_counterfactual_groups` searches the content's own distinct present keys (shuffled) for up to `group_size` (default 3) whose looked-up values are pairwise distinct, rather than searching the full vocabulary the way `generate_count_counterfactual_groups` does. Everything else -- frozen task-blind Stable Core pretraining on `BIND`-only i.i.d. examples, oracle-forced primitive training on the counterfactual groups, the three-arm evaluation (Correct / effectful Wrong argument / None, no "Wrong family" arm since exactly one family is registered) plus derived causal gap, and multi-seed aggregation against A1-R005D-004's own thresholds (Correct >= 0.90, effectful Wrong argument <= 0.30, causal gap >= 0.50, `None` <= 0.30 filled in from A1-R005D-004's own precedent) -- mirrors `count_counterfactual_gate` structurally, including its "one persistent family" acceptance criterion (`family_count_passed`, `bank_size == 1` every seed) that A1-R005D-007's own fourth criterion, "one persistent BIND family across keys," restates.

`correct_passed=false`, `effectful_wrong_argument_passed=false`, `none_passed=false`, `causal_gap_passed=false`; `family_count_passed=true` (`bank_size == 1` every seed). Overall **`passed=false`**. `primitive_param_count=3360` (identical to `COUNT`'s V0 primitive -- same `vocab_size`-sized integer-bucket argument encoder, `apc.primitives.conditioning.default_argument_encoder`). Per-seed wall-clock ~346s. `num_unseen_eval_examples=3851` from `1400` groups (mean realized group size `2.75`, below `COUNT`'s own -- expected, since `BIND`'s per-group candidate pool is the content's own handful of distinct present keys rather than the whole vocabulary; `min_unseen_eval_examples=2500` was set with this margin in mind and cleared it, `argument_effect_rate=1.0` confirming every realized pairing is effectful by construction as designed).

**Reason:** This is a qualitatively different failure from `COUNT`'s (ADR-0033/0034/0035): for `COUNT`, Correct was always measurably *above* the Wrong-argument/None controls (e.g. `0.450` vs. `0.262`/`0.336` at baseline) -- a real but insufficient causal signal. For `BIND`, Correct (`0.332`), effectful Wrong argument (`0.338`), and None (`0.335`) are statistically indistinguishable (causal gap `-0.005`, i.e. forcing the *correct* key through the trained primitive does no better than forcing a *wrong* key, which in turn does no better than applying no primitive at all). This is not merely "the argument-conditioning signal is weak" (`COUNT`'s F3 diagnosis) -- it is "the measured Correct rate carries no detectable primitive-argument effect whatsoever."

A cheap, offline check (run directly against the same eval-group construction and config, no training/GPU needed -- `generate_bind_counterfactual_groups(0, 1400, ..., vocab_size=10, sequence_length_range=(6, 10), group_size=3)`) confirms what is producing this ~0.33 plateau: predicting, for every example, the *value of the last key/value pair in the content* -- i.e. `content[-1]`, ignoring `query_key` entirely -- gets `0.338` accuracy on the exact same 3851-example unseen distribution this run evaluated on, matching all three observed arms almost exactly. This heuristic's accuracy is explained by the counterfactual-group construction itself: a group's `query_keys` are a uniformly shuffled sample of the content's distinct present keys, so a content-only prediction that happens to equal the value of *one particular* key (whichever key sits last in the sequence) is correct on exactly that fraction of a group's realized members, in expectation `1 / (mean realized group size) ~= 1 / 2.75 ~= 0.36` -- the same order of magnitude actually measured. The frozen Stable Core was pretrained task-blind on `BIND` examples where the query key is never visible in the input at all (`apc.environments.operations.PARAMETERIZED_OPERATION_NAMES`'s hidden-argument design, ADR-0017) and therefore cannot single-token-predict a target that depends on an argument it never sees; "always predict the last pair's value" is a natural, easily-learned, argument-independent fallback for exactly this non-identifiable pretraining objective (attending to the most recent position requires no real key-based content search). That the *trained* `BIND` primitive's Correct/Wrong-argument arms land on the same plateau as the argument-blind `None` arm indicates the primitive is not measurably shifting behavior away from this baseline in either direction, in contrast to `COUNT` where the primitive at least moved Correct above `None`.

This points to a `BIND`-specific bottleneck distinct from `COUNT`'s F3/F4: `BIND` is a genuine content-addressed associative lookup -- the model must locate *which position* in the sequence holds the queried key and read the value one slot to its right, a search-and-select operation over an argument-dependent position, not a fixed transformation of a scalar summary (`COUNT`'s tally) or a rotation (`SHIFT`). A rank-8 additive residual bolted onto a frozen backbone (`delta = B(phi(A(h) + C(e_a)))`) conditions the *whole* residual on the argument uniformly across sequence positions; it has no structural mechanism to make the query argument steer *attention over content positions* specifically, which is plausibly what locating a matching key requires. This is a new candidate explanation, not previously named in `docs/design-docs/PARAMETERIZED_PRIMITIVE_RETRY.md`'s F1-F4 (all stated in terms of `COUNT`'s scalar-output structure); it is recorded here rather than acted on, per STOP GATE discipline.

**Consequence:** Per `AGENTS.md`'s STOP GATE discipline, A1-R006 remains blocked (unchanged since ADR-0029). No architecture change is made in response to this result -- this task's own scope is running the established counterfactual protocol at the established baseline architecture, not diagnosing or fixing `BIND` specifically (`AGENTS.md`'s "do not hide negative results by ... increasing model size prematurely" applies equally to reactively redesigning the primitive mid-task). `docs/CODEX_TASKS_A1_R005_RETRY.md`'s queue continues to A1-R005D-008 (SHIFT/SELECT sequence gates), not implemented here, per `AGENTS.md`'s "Completion of one task does not authorize beginning the next task." The candidate `BIND`-specific bottleneck this task surfaces (content-addressed lookup needs argument-steered attention over positions, not a uniform additive residual) is left as a candidate for whoever next revisits `BIND`'s own architecture -- out of this task's scope to pursue. Run artifacts preserved at `runs/phase_a1_bind_counterfactual_gate/` (`config.yaml`, `report.json`, `summary.json`, `system.json`, one `seed_<n>/{report.json, core_metrics.jsonl, primitive_metrics.jsonl}` per seed). New tests: `tests/test_bind_counterfactual_gate.py` (48 cases: `_valid_bind_lengths`, group construction/distinctness/determinism/present-key-only sampling, config validation including the even-length check, bank construction, report shape, multi-seed aggregation, threshold constants -- mirroring `tests/test_count_counterfactual_gate.py`'s convention, minus the A1-R005D-005/006-specific gradient-norm/conditioning-variant cases which are out of this task's scope). Full suite (`python -m pytest -q`: 1033 passed, 1 skipped, up from 985/1 before this change), `python -m ruff check .`, and `python -m mypy src/apc` (57 source files) are all clean after this change.

## ADR-0039 — A1-R005E-002 frozen `h_content` audit: per-position token/position information splits sharply by operation (SHIFT/SELECT strong, COUNT/BIND weak); no operation's terminal-state summary supports full-sequence reconstruction; BIND's key-to-paired-value link is absent even though key/value role is near-perfectly recoverable

**Status:** Accepted

**Decision:** Task A1-R005E-002 (`docs/CODEX_TASKS_A1_R005E_DIAGNOSTIC.md`, "Frozen `h_content` information audit") is implemented as `apc.evaluation.representation_audit` (`scripts/representation_audit.py`, `configs/phase_a1_representation_audit.yaml`) and run for 3 seeds x 4 operations (`SHIFT`/`SELECT`/`COUNT`/`BIND`), each against its own dedicated frozen task-blind Stable Core -- the identical `d_model=192, n_layer=4, n_head=4, d_ff=768`/`core_train.steps=30000, batch_size=128, lr=3e-4` budget `apc.evaluation.count_counterfactual_gate`/`bind_counterfactual_gate`/`sequence_counterfactual_gate` (D-004/D-007/D-008) each pretrained, so this measures the actual retry checkpoints' own representation, not a fresh unrelated one. Per `docs/CODEX_TASKS_A1_R005E_DIAGNOSTIC.md`'s own "Acceptance: diagnostic only," there is no pass/fail gate; the measured numbers (cross-seed mean, `stdev` in parentheses) are:

| Operation | Token identity | Position | Reconstruction token acc. | Reconstruction exact match | Role (key/value) | Pair (key -> paired value) |
|---|---|---|---|---|---|---|
| SHIFT | 0.971 (0.051) | 0.995 (0.009) | 0.517 | 0.0099 | -- | -- |
| SELECT | 0.939 (0.093) | 0.9999 (0.0002) | 0.680 | 0.0199 | -- | -- |
| COUNT | 0.636 (0.044) | 0.886 (0.010) | 0.334 | 0.0000 | -- | -- |
| BIND | 0.506 (0.058) | 0.852 (0.015) | 0.341 | 0.0008 | 0.995 (0.005) | 0.098 (0.001) |

Full per-seed numbers, `config.yaml`/`system.json`/one `seed_<n>/{report.json, <OP>_core_metrics.jsonl}` per seed: `runs/phase_a1_representation_audit/`.

**Reason:** The five probes (`apc.evaluation.representation_audit` module docstring) are all linear (`nn.Linear`, full-batch AdamW, 800 steps), so a low score reflects the frozen representation itself, not probe undertraining. Two results explain the pattern, and both trace back to what each operation's own single-operation pretraining objective needs `h_content` to preserve, not to a shared representation-capacity limit:

1. **Token identity/position split by operation.** `SHIFT`/`SELECT` need to reproduce a rotation/gather of the *entire ordered* input, so their own training loss already forces per-position content and position to stay recoverable (`0.94-0.97` token, `>=0.995` position). `COUNT`'s ground truth (`min(count(content, target), vocab_size-1)`) is a function of the input's *multiset*, not its order or even most of its individual values -- nothing in `COUNT`'s own training signal rewards keeping every position's token linearly decodable, and the measured `0.636` token / `0.886` position accuracy (well above the `1/vocab_size=0.10` chance floor, but far below `SHIFT`/`SELECT` and below the `0.98` D-E1 "desirable" threshold) is consistent with a representation that has partially specialized toward frequency-relevant information at the expense of exact per-position identity. `BIND`'s ground truth is the *single* value paired with one randomly drawn `query_key` per training example -- there is no training pressure to keep the *other* (unqueried) pairs' key or value identity recoverable, and its per-position token accuracy (`0.506`, barely above `SHIFT`/`SELECT`'s floor for a `vocab_size=10` problem) and position accuracy (`0.852`, lowest of the four) reflect that.

2. **BIND's role/pair split is the audit's sharpest single finding.** Role (even position = key, odd = value) is a static property of position alone, entirely independent of content, so it is trivially recoverable (`0.995`) regardless of what the encoder learned about *values*. The pair probe asks a categorically different question: does a key's *own* frozen state at its own position linearly encode *which* value token is paired with it (position `j+1`) -- and the answer is a clean null result, `0.098`, statistically indistinguishable from the `1/vocab_size = 0.10` chance floor across all three seeds (`0.0982-0.0990`). This is the representation-side counterpart to ADR-0036's finding that `BIND`'s causal gap is statistically zero: a `ConditionedPrimitive`-style pointwise transform (`h'_j = f(h_j, argument)`, `docs/design-docs/REPRESENTATION_OPERATOR_ISOLATION.md` section 1) reading only the queried key's own position could not recover the correct value even with unlimited capacity, because that information was never linearly present there to begin with. Locating and reading the *correct* value requires either (a) attending to other positions at inference time (which a pointwise-per-position primitive structurally cannot do) or (b) the frozen representation itself encoding an addressable pointer at the key's own position (which it does not).

3. **Full-sequence reconstruction fails for all four operations, but this is a distinct and stricter question than (1)/(2).** The reconstruction probe reads a *single* vector -- `h_content` at the `[SEP]` position, i.e. exactly the state `apc.core.execution.evaluate_exact_match_no_primitive`'s first decoding step (and every oracle-forced primitive call's first step) conditions on -- and asks it to reconstruct the *entire* input sequence. Every operation fails this far below the `0.95` D-E1 "desirable" exact-match bar (`SHIFT` `0.0099`, `SELECT` `0.0199`, `COUNT` `0.0000`, `BIND` `0.0008`), even `SHIFT`/`SELECT`, whose per-position probes (1) score well. This is a materially different (and, per `docs/design-docs/REPRESENTATION_OPERATOR_ISOLATION.md` section 4's "reconstruction is not enough," *harder and more diagnostic*) question than per-position recoverability: it specifically tests whether the terminal, downstream-facing summary state that a *pointwise* primitive/decoder must read from is a faithful compressed copy of the whole input, which for none of the four operations it is (reconstruction token accuracy of `0.33-0.68`, well above the `0.10` chance floor but far short of a full copy, suggesting partial/lossy "bag of tokens"-level retention rather than either full fidelity or complete loss). Because every currently registered `ConditionedPrimitive`/`FiLMConditionedPrimitive`/`BasisModulatedConditionedPrimitive` is pointwise (transforms each position from only *that* position's own `h_content[j]` and the argument, never other positions), this result gives an independent, representation-side structural explanation for why the retry's primitives failed on `SHIFT`/`SELECT`/`COUNT`/`BIND` regardless of conditioning formula (ADR-0033/0035/0036/0037): even a perfectly argument-selective pointwise function of the terminal position alone could not manufacture output content this terminal state does not already linearly carry.

**Limitation, stated explicitly per this task's own "explicitly state what information is and is not recoverable":** This module deliberately tests a maximally compressed, single-vector summary (probe 3) and purely linear, no-cross-position-attention readouts (all five probes) -- it does **not** test whether the *full per-position* `h_content` sequence (all positions, not the one terminal vector) contains enough information for a cross-position-attending operator to solve these tasks. `SHIFT`/`SELECT`'s strong per-position token/position scores (`0.94-1.00`) leave open that an operator with fully differently could recover their answer by reading the *whole* sequence rather than one summary vector -- exactly what `A1-R005E-003`'s oracle latent operators (permutation/gather over the full sequence, not a single-vector reconstruction) and `A1-R005E-004`'s frozen high-capacity cross-position upper bound are designed to test next, and this task explicitly does not implement or run either. `COUNT`/`BIND`'s markedly weaker per-position scores are a stronger prior that their bottleneck is at least partly representational rather than purely about operator class, but this module's linear probes cannot rule out that a *nonlinear* readout recovers more than reported here.

**Consequence:** A1-R006 remains blocked (unchanged). No architecture change is made in response to this result -- per `AGENTS.md`'s "No premature operator rollout"/"No premature representation retraining," redesigning the Primitive Bank or retraining the Stable Core is explicitly deferred until `A1-R005E-004`'s frozen high-capacity upper bound is measured. These numbers are recorded here as the D-E1/E-M1 evidence row for `docs/design-docs/NEXT_PHASE_DECISION_MATRIX.md` (not filled in by this task -- that is `A1-R005E-008`'s job, per "Do not choose the next development phase until `NEXT_PHASE_DECISION_MATRIX.md` is filled with measured results"), and as a candidate mechanistic explanation (pointwise-primitive-reads-an-information-poor-terminal-state) that the next diagnostic tasks should either corroborate or falsify. Run artifacts preserved at `runs/phase_a1_representation_audit/` (`config.yaml`, `report.json`, `summary.json`, `system.json`, one `seed_<n>/{report.json, <OP>_core_metrics.jsonl}` per seed). New module: `src/apc/evaluation/representation_audit.py`; new tests: `tests/test_representation_audit.py` (11 cases: config validation/round-trip, frozen-core determinism, extraction shapes for both the BIND and non-BIND cases, per-operation report shape and threshold-flag correctness, multi-seed aggregation, module constants). Full suite (`python -m pytest -q`: 1110 passed, up from 1098 passed/1 skipped before this change), `python -m ruff check .` (clean), and `python -m mypy src/apc` (59 source files, clean) are all green after this change.

## ADR-0040 — A1-R005E-003 oracle latent operator benchmark: perfect oracle addressing on frozen `h_content` still fails for SHIFT/SELECT/BIND, because the pretrained decode head was never trained to read content-region positions at all; COUNT passes strongly once a fresh readout replaces that head

**Status:** Accepted

**Decision:** Task A1-R005E-003 (`docs/CODEX_TASKS_A1_R005E_DIAGNOSTIC.md`, "Oracle latent operator benchmark") is implemented as `apc.evaluation.oracle_latent_operator_benchmark` (`scripts/oracle_latent_operator_benchmark.py`, `configs/phase_a1_oracle_latent_operator_benchmark.yaml`) and run for 3 seeds (`0-2`) x 4 operations (`SHIFT`/`SELECT`/`COUNT`/`BIND`), each against its own dedicated frozen task-blind Stable Core -- the *same* per-operation pretraining scheme A1-R005E-002 uses (`apc.evaluation.shared_core_generalization.train_shared_core`, `include_task_spec=False`, identical `model`/`core_train` budget: `d_model=192, n_layer=4, n_head=4, d_ff=768`, `steps=30000, batch_size=128, lr=3e-4`). This is confirmed to reproduce A1-R005E-002's own checkpoints bit-for-bit, not merely nominally: seed-0's `core_final_train_loss` for `SHIFT` (`0.2366`) and `SELECT` (`0.8058`) match ADR-0039's recorded values to four decimal places.

Per `docs/design-docs/REPRESENTATION_OPERATOR_ISOLATION.md` section 6, two different oracle latent operators are implemented, matching that section's own asymmetric text:

- **`SHIFT`/`SELECT`/`BIND` ("... then decode", zero new training):** each operation's target is a literal copy of one or more input tokens at oracle-known source positions (`ShiftOp`: `target[t] = input[(amount + t) % L]`; `SelectOp`: `target[t] = input[indices[t]]`; `BindOp`: `target[0] = input[key_position + 1]`, last-match-wins on a repeated key). The oracle latent operator gathers `content_state[:, k, :]` at each oracle-addressed content position `k` and feeds it straight into the frozen core's own pretrained `model.decode` -- no parameter anywhere in this path is fit to any data. `_source_positions_for_example`/`_oracle_decode_predictions` are pure indexing plus one batched `decode` call.
- **`COUNT` (small trained readout):** `CountOp`'s target (`min(count, vocab_size-1)`) is not a copy of any single input token, so there is no pretrained-decode-target to re-route. Positions matching the oracle-supplied query (`_count_match_positions`, raw-symbol search only) are sum-pooled (not mean-pooled, so a legitimate zero-match example maps to the zero vector rather than an undefined average) and a freshly initialized `nn.Linear(d_model, vocab_size)` is fit by full-batch AdamW cross-entropy (800 steps, the same lightweight-probe budget `apc.evaluation.task_content_probes`/`representation_audit` use) on a disjoint train/eval split (4096 train / 2048 eval examples per seed).

`runs/phase_a1_oracle_latent_operator_benchmark/report.json`/`summary.json` (3 seeds, RTX 5060 Ti, run natively on Windows this time (`platform=Windows-10-10.0.26200-SP0`, unlike every earlier ADR's WSL2 runs) with `torch==2.11.0+cu128`, git commit `2420a962`):

| Operation | Mean exact match | Mean token accuracy | Required (exact / token) | `passed` |
|---|---|---|---|---|
| SHIFT | **0.000** (identical across all 3 seeds) | 0.0754 (stdev 0.0015) | >=0.90 / >=0.98 | **false** |
| SELECT | **0.000** (identical across all 3 seeds) | 0.0601 (stdev 0.0270) | >=0.90 / >=0.98 | **false** |
| BIND | 0.1017 (stdev 0.0148, min 0.0854, max 0.1143) | same (output length always 1) | >=0.90 (token not separately gated) | **false** |
| COUNT | **0.9731** (stdev 0.0120, min 0.9644, max 0.9868) | same (output length always 1) | >=0.90 (token not separately gated) | **true** |

Overall `passed=false` (3 of 4 operations fail). `readout_trained=true` only for `COUNT`.

**Reason:** `SHIFT`/`SELECT`'s token accuracy (`0.060-0.075`) sits at or *below* the naive `1/vocab_size = 0.10` chance floor a uniform-random guess would achieve over this experiment's `vocab_size=10`; `BIND`'s (`0.102`) sits almost exactly on it. This is a much sharper (and differently shaped) negative result than a capacity-limited partial success -- it indicates `decode()` is not merely imprecise at these positions, it is close to uninformative or systematically wrong. A direct check (1000 oracle-addressed `SELECT` predictions, seed 0, same checkpoint) confirms the latter: `57.9%` of predictions are literally `EOS` (token id `13`), a token that can *never* be a correct answer since every target is drawn from the real vocabulary (`0-9`) -- not noise spread roughly evenly over the vocabulary, but a systematic, dominant bias toward a token structurally excluded from ever matching.

The root cause traces directly to `apc.core.data.collate_batch`'s own module docstring: "trained autoregressively with the loss masked to only the answer span (`target... [EOS]`), so the model is never rewarded for 'predicting' the prompt it was given." Concretely, `labels[row, answer_start:answer_end]` only ever covers the span starting at the `[SEP]` position through `[EOS]`; every position from `[BOS]` through the last content token (`padded index 0` through `padded index L-1`, i.e. every position `_source_positions_for_example` addresses for `SHIFT`/`SELECT`, and the value-adjacent position `BIND` addresses) carries `IGNORE_INDEX` and contributes zero gradient to `decode`'s weight matrix, every step, for every one of the `30000` pretraining steps. `decode` (`self.head`, a single shared `nn.Linear` tied to the input embedding) is therefore optimized *exclusively* on hidden states that arose from the answer-generation regime (states that have attended through `[BOS] content [SEP] answer-so-far]`); applying that same fixed linear map to a hidden state from the content-generation regime is evaluating it far outside its training distribution, and the module's own dominant `EOS` bias is a plausible (if not further investigated here) symptom of exactly that -- `EOS` is the one token the answer-region decode head is trained to emit unconditionally once an answer is *complete*, and an out-of-distribution content-region vector may resemble that "nothing more to predict" signal more than it resembles any specific plausible next vocabulary token.

`COUNT`'s result is the sharpest possible contrast, run at the identical frozen `h_content` computation and the identical oracle addressing discipline (raw symbols only, never target tokens): replacing the stale, answer-region-only `decode` head with a *freshly fit* readout over the *same* frozen `content_state` recovers `0.973` exact match -- near the `0.90` bar and close to ceiling -- from operations at effectively-chance performance under the old head. This is strong evidence that this benchmark's `SHIFT`/`SELECT`/`BIND` failure is substantially a **decoder/interface** bottleneck (an untrained readout applied to an out-of-distribution input regime), not solely a representation-content bottleneck -- consistent with `docs/EXPERIMENT_PLAN_A1_R005E_DIAGNOSTIC.md` D-E2's own anticipated branch ("If this fails, investigate decoder/state interface before operator learning") and directly corroborating ADR-0039's own finding that `SHIFT`/`SELECT` retain *strong* per-position token/position information (`0.94-1.00` linear-probe accuracy) in this very same frozen `h_content` -- the information this benchmark needed was measurably present at the addressed positions; the model's own pretrained readout simply was never asked to expose it there.

This is not a fully controlled isolation of "representation is fine, only the interface is broken" from "representation is *also* insufficient" for `SHIFT`/`SELECT`/`BIND` specifically: `COUNT`'s readout differs structurally (a sum-pooled aggregate over a variable-size matched set, trained fresh) from `SHIFT`/`SELECT`/`BIND`'s single-position, zero-training design, so it is suggestive corroboration, not a matched comparison. `docs/design-docs/REPRESENTATION_OPERATOR_ISOLATION.md` section 6's own text draws exactly this asymmetry (only `COUNT` is offered a trained-readout option), so this module does not extend a trained readout to `SHIFT`/`SELECT`/`BIND` -- doing so would blur this task's own "zero new training, oracle addressing only" scope into `A1-R005E-004`'s later "frozen high-capacity operator" (which is explicitly built to test exactly this, with a real learned cross-position module rather than a bare linear probe).

**Consequence:** Per `docs/CODEX_TASKS_A1_R005E_DIAGNOSTIC.md` A1-R005E-003's own "Interpret failure as representation/decoder/interface evidence, not learned-routing failure": no `Router`, `PrimitiveBank`, `Primitive`, `PlasticWorkspace`, or `apc.consolidation`/`apc.meta` module is imported anywhere in `apc.evaluation.oracle_latent_operator_benchmark`, so there is no learned-routing explanation available for this result even in principle. A1-R006 remains blocked (unchanged since ADR-0029). No architecture change is made in response to this result -- per `AGENTS_A1_R005E_DIAGNOSTIC_ADDENDUM.md`'s "No premature operator rollout"/"No premature representation retraining," and per `docs/EXPERIMENT_PLAN_A1_R005E_DIAGNOSTIC.md` D-E2's own text, this decoder/interface finding is a reason to proceed carefully into `A1-R005E-004`'s frozen high-capacity *upper-bound* operator (which trains its own module rather than reusing the stale answer-only decode head, sidestepping this specific interface mismatch by construction) rather than a reason to skip it or to redesign anything now; implementing A1-R005E-004 itself is not done here, per `AGENTS.md`'s "Completion of one task does not authorize beginning the next task." These numbers are recorded here as the D-E2/E-M2 evidence row for `docs/design-docs/NEXT_PHASE_DECISION_MATRIX.md` (not filled in by this task, per ADR-0039's own precedent -- that is `A1-R005E-008`'s job). Run artifacts preserved at `runs/phase_a1_oracle_latent_operator_benchmark/` (`config.yaml`, `report.json`, `summary.json`, `system.json`, one `seed_<n>/{report.json, <OP>_core_metrics.jsonl}` per seed). New module: `src/apc/evaluation/oracle_latent_operator_benchmark.py`; new tests: `tests/test_oracle_latent_operator_benchmark.py` (24 cases: config validation/round-trip, pure oracle-position-derivation correctness against `ShiftOp`/`SelectOp`/`BindOp`/`CountOp`'s own semantics including `BIND`'s "last match wins" and out-of-range `SHIFT` amounts, real-generated-example reconstruction checks that the oracle mapping recovers `target_tokens` directly from raw `input_tokens`, frozen-core determinism, per-operation and multi-seed report shape/threshold correctness). Full suite (`python -m pytest -q`: 1134 passed, up from 1110 before this change), `python -m ruff check .` (clean), and `python -m mypy src/apc` (60 source files, clean) are all green after this change.
