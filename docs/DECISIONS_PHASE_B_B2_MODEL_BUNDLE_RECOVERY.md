**Status:** Accepted (Task B-C005REC-001 complete; **RG0: investigation complete**; no training performed, no shared cache modified, no checkout performed)
**Affects:** `AGENTS.md`, `docs/exec-plans/active/PHASE_B_B2_POST_D2_REPAIR.md`, `docs/CODEX_TASKS_PHASE_B_B2_POST_D2_REPAIR.md`, `docs/DECISIONS.md`, `docs/DECISIONS_PHASE_B_B2_MODEL_BUNDLE_RECOVERY.md`. No `src/` code was modified.

### Context

`B-C005R3-010`'s G4 result (ADR-0091) reported that the cached `primitive_bank_16.pt` for development seeds 10-14 is incoherent with the real shared encoder `B-C005R3-009` pretrained for those same seeds, breaking raw execution for 10 of 16 primitives, plus an independent COUNT<->BIND L3 routing degradation. A separately supplied "Model Bundle Recovery" instruction pack (`docs/CODEX_TASKS_PHASE_B_B2_MODEL_BUNDLE_RECOVERY.md` and its companion documents, task IDs `B-C005REC-001`..`008`) treats ADR-0091's findings as reported facts to be independently confirmed against the live repository before any restore/rebuild work proceeds. This task (`B-C005REC-001`) performs that confirmation, plus a read-only dependency inventory and per-model restore/build classification. No training, no shared-cache writes, and no git checkout were performed, per the task's own boundary.

### Evidence

1. **ADR-0091's two root-cause claims are independently confirmed against live code and file timestamps, not merely re-quoted.** (a) `runs/phase_a2_bank_scaling_benchmark/seed_{10..14}/primitive_bank_16.pt` (1,236,371 bytes each) are all dated 2026-09-06 01:01-01:05; `runs/phase_a1_shift_compact_structural_probe/seed_{10..14}/shared_encoder.pt` (7,209,373 bytes each, `B-C005R3-009`'s output) are all dated 2026-09-07 08:18-08:49 -- the bank cache strictly predates the Core it is now loaded against for every one of the 5 development seeds. (b) Reading `get_or_build_16_primitive_bank` (`src/apc/evaluation/incremental_router_benchmark.py:152-257`) directly confirms: on a cache hit (`ckpt_path.is_file()`, true for all 5 seeds), it reconstructs bank modules fresh and blindly `load_state_dict`s the 2026-09-06 checkpoint onto them with no Core-identity check of any kind -- only file existence is checked; on a cache miss, it calls `_train_single_primitive` only for the 6 `PHASE_A2_INCREMENTAL_NEW_OPERATIONS` (line 247), never for the other 10 (8 `ALL_CANONICAL_OPERATIONS` + 2 `BRANCH_B_NOVEL_OPERATION_NAMES` = `SWAP_PAIRS`, `INVERT_HALF`). Both files' git history (`69159be`/A2-C003 and `b52630c`/B-C005R1 respectively for `incremental_router_benchmark.py` and `argument_scoring.py`) predates the entire R3 series -- no R3-00x task ever modified either file; every R3 task only calls them.
2. **A materially relevant fact not stated in ADR-0091: the cache-miss path's only fallback source for the 10 non-incremental primitives is itself missing for every development seed.** `get_or_build_16_primitive_bank`'s cache-miss branch attempts `runs/phase_a1_learned_routing_benchmark/seed_{seed}/primitive_bank.pt` (hardcoded path, line 225) with `strict=False`; this file, and its own further fallback `runs/phase_a1_composition_library_benchmark/seed_{seed}/primitive_bank.pt`, do **not exist** for any of seeds 10-14 (confirmed by direct file-existence check). This means a genuinely cache-free build with today's code would leave those 10 primitives at random initialization -- not merely "stale," but never trained at all for these seeds -- which is exactly what ADR-0091's own live diagnostic already measured (COPY at chance-level, `~0.067` token accuracy, when pointed at a throwaway never-used cache directory) but had described narratively as a "stale cache" finding rather than an "no trained artifact exists for a fresh build" finding. Both framings describe the same measured fact; this ADR makes the stronger implication explicit.
3. **An existing, currently-unwired recipe already trains all 10 affected primitives correctly against an arbitrary Core, including the real R3-009 Core, without new training code.** `_ensure_learned_routing_bank_and_core` (`src/apc/evaluation/learned_routing_benchmark.py:493-649`) trains the 8 canonical operations (`config.bank_train_steps`) and the 2 Branch-B operations (`SWAP_PAIRS`/`INVERT_HALF`, 3000 steps each) against whichever Core it constructs, and its own default Core-checkpoint lookup (`learned_routing_benchmark.py:526-533`) already points at `runs/phase_a1_shift_compact_structural_probe/seed_{seed}/shared_encoder.pt` -- the identical path `B-C005R3-009` populated. This narrows ADR-0091 Evidence 3's cost estimate ("requires implementing ... new training code") to an orchestration/wiring gap rather than a from-scratch implementation gap. **This has not been exercised or validated by this task** (REC-001 performs no training); whether its output is functionally adequate against the new Core is unmeasured. A second existing, independent recipe for the 8 canonical operations only (not Branch-B) is `run_unified_oracle_causal_benchmark` (`unified_oracle_causal_benchmark.py:743`, unmoved, still callable, with a multi-seed wrapper at line 1054).
4. **Using either existing recipe for recovery, as currently written, requires writing into the shared cache, which the recovery contract prohibits.** `_ensure_learned_routing_bank_and_core`'s only way to hand trained weights to `get_or_build_16_primitive_bank` is via the latter's hardcoded `runs/phase_a1_learned_routing_benchmark/seed_{seed}/primitive_bank.pt` path (`incremental_router_benchmark.py:225-226`) -- not a parameter, not redirectable without a code change. Populating it in place would mutate a shared, pre-existing cache path; redirecting it to a namespace-isolated recovery directory is a `src/` code change, out of `B-C005REC-001`'s own investigation-only scope, and is deferred to `B-C005REC-002`/`003`.
5. **`sequential_closed_loop_benchmark.py` has no seam to accept an externally repaired bank/router/scorer, confirmed by a full read, not by name-matching.** `_setup_initial_environment` (line 451) and `run_sequential_closed_loop_for_seed` (line 534) each independently construct their own Core/Bank/Router from scratch (`get_or_build_16_primitive_bank` internally, `output_dir` defaulting to the same stale `runs/phase_a2_bank_scaling_benchmark` cache); the file's full import list contains no `apc.primitives.argument_scoring` import anywhere, confirming it never uses an `ArgumentScorer`. This is the structural gap `B-C005REC-006`'s runtime-injection adapter must resolve; it is flagged, not implemented, here.

## ADR-0093: Immutable ModelBundle, Strict Loading & Qualification Contract -- a Fail-Closed Loader That Would Have Caught ADR-0091's Stale-Bank-vs-New-Core Bug Directly, Verified Against Both Synthetic Fixtures and a Real Production Checkpoint (Task B-C005REC-002, RG1 PASS)

**Date:** 2026-09-07
**Status:** Accepted (Task B-C005REC-002 complete; **RG1: CPU contract PASS**; no training performed, no shared cache modified)
**Affects:** `src/apc/utils/model_bundle.py` (new), `src/apc/evaluation/model_bundle_recovery.py` (new), `scripts/run_phase_b_b2_model_bundle_recovery.py` (new), `configs/phase_b_b2_model_bundle_recovery_rec002.yaml` (new), `tests/test_model_bundle_contract.py` (new, 33 CPU-only tests), `AGENTS.md`, `docs/DECISIONS.md`, `docs/DECISIONS_PHASE_B_B2_MODEL_BUNDLE_RECOVERY.md`.
**Run Artifacts:** `runs/phase_b_b2_model_bundle_recovery/rec002/run_001/` (`bundle_schema.json`, `loader_contract_tests.json`, `compatibility_rules.json`, `legacy_import_policy.json`, `protocol.json`).

### Context

`B-C005REC-001`/ADR-0092 confirmed ADR-0091's root cause directly: `get_or_build_16_primitive_bank`'s cache-hit path (`incremental_router_benchmark.py:152-257`) loads a cached `primitive_bank_16.pt` onto a fresh module with `state_dict.load_state_dict` and **no Core-identity check of any kind** -- only `ckpt_path.is_file()`. Nothing in the current runtime path can distinguish "trained against this Core" from "trained against a Core that has since been silently replaced." `docs/design-docs/B2_MODEL_BUNDLE_RECOVERY_CONTRACT.md` proposes a manifest/hash/loader contract to make that distinction mechanical rather than absent. This task (`B-C005REC-002`) implements that contract as new code and proves it on CPU-only fixtures per RG1's own scope (`docs/EXPERIMENT_PLAN_PHASE_B_B2_MODEL_BUNDLE_RECOVERY.md` section 4: "CPUの正常・異常fixtureで検査する") -- no GPU work, no training, no scientific/performance evaluation; that is REC-004 onward's job.

### Design

`apc.utils.model_bundle` implements the design contract's dataclasses close to the letter of section 2 (`ComponentManifest`, `PrimitiveManifestEntry`, `RouterManifest`, `ArgumentScorerManifest`, `ScoringPolicyManifest`, `ModelBundleManifest`), a `BuildRoute`/`BundleScope`/`PublishStatus`/`ProvenanceStatus` enum set, and 13 typed `ModelBundleError` subclasses (`MISSING_ARTIFACT`, `CORRUPTED_ARTIFACT`, `CORE_DEPENDENCY_MISMATCH`, `SCHEMA_MISMATCH`, `ARGUMENT_SCHEMA_MISMATCH`, `ROUTER_KEY_MAPPING_MISMATCH`, `EXECUTION_SIGNATURE_MISMATCH`, `UNTRAINED_COMPONENT`, `UNKNOWN_PROVENANCE`, `UNCERTIFIED_PAIR`, `INCOMPLETE_BUNDLE`, `CAPABILITY_NOT_QUALIFIED`, `DUPLICATE_TRAINING_IDENTITY`) -- a superset of the design doc's own illustrative label list. `load_bundle(manifest, mode, required_capabilities, ...)` is read-only: it never imports or calls a builder/optimizer/trainer, and performs, in order, manifest self-consistency, capability/scope gating, publish-status, structural completeness, provenance, Core integrity, decoder/vocabulary integrity + cross-component schema agreement, per-primitive integrity **and the Core-dependency check that is the whole point of this task** (`entry.core_dependency_hash != manifest.core.canonical_state_hash` -> `CoreDependencyMismatchError` -- exactly the check ADR-0091's bug lacked), argument-schema consistency, router integrity + key-to-primitive mapping, argument-scorer integrity, router/scorer pair compatibility, and execution-signature agreement.

Two independent hashes are kept per component throughout: `file_sha256` (raw bytes) and `canonical_state_hash` (tensor name/shape/dtype/content, independent of pickling metadata) -- a byte copy matches both, independently trained weights match neither, a re-serialized copy of the same weights matches only the canonical one (`raw_file_sha256`/`canonical_state_hash`/`canonical_state_hash_from_file` in `model_bundle.py`; property-tested in `tests/test_model_bundle_contract.py`).

Two design corrections were made during implementation, both confirmed necessary by a failing test before the fix:
1. **`compute_content_manifest_digest`'s payload originally embedded `file_path`/`source_artifact` (filesystem locations).** This made `bundle_id` differ for two bundles holding byte-identical content at different paths -- wrong, since a namespace copy of the same weights is the same content per the design doc's own restore-vs-build distinction. Fixed by building the digest payload from explicit content-only field extractors (`_component_digest_payload`, `_primitive_digest_payload`, `_router_digest_payload`, `_argument_scorer_digest_payload`) that omit path and free-text (`training_receipt`) fields. Caught by `test_bundle_id_deterministic_for_identical_content`.
2. **`RouterManifest.weights_hash` originally covered the router's full `state_dict`, including its per-primitive `_keys.<id>` entries.** This made a two-key swap (the "bank key順序交換" required test) indistinguishable from a general router-weights corruption -- both raised `CORE_DEPENDENCY_MISMATCH` before the key-mapping check was ever reached. Fixed by introducing `router_non_key_state_dict` (excludes `_keys.*`) so `weights_hash` covers only the router's shared parameters (`query_proj.*`), while `key_to_primitive_mapping_hash` (content-addressed per id, order-independent) separately and specifically catches a swapped/corrupted key. Caught by `test_router_key_swap_between_primitives_is_rejected`.

### Context

`B-C005REC-001`/ADR-0092 found that every one of the 16 real registry primitives already has a callable, correct existing training recipe, but wiring them together for recovery is orchestration work, not new training-algorithm design; `B-C005REC-002`/ADR-0093 gave the recovery a fail-closed manifest/loader contract but qualified no real bundle. ### Design

Eight ordered build stages (`CORE_RESTORE` -> `CANONICAL_AND_BRANCH_B_BUILD` / `SHIFT_DEDICATED` -> `SHIFT_OVERRIDE_MERGE` -> `INCREMENTAL_6_BUILD` -> `ROUTER_CALIBRATION` -> `ARGUMENT_SCORER_CALIBRATION` -> `CERTIFICATE`), each naming a real recipe function confirmed against live source during this task (not re-derived from REC-001's report alone): `learned_routing_benchmark._ensure_learned_routing_bank_and_core` (Core restore, then 8 canonical + 2 Branch-B ops, called with a namespace-safe `seed_dir` rather than the function's own hardcoded default), the *shape* of `incremental_router_benchmark.get_or_build_16_primitive_bank`'s incremental-training loop (steps=1000 per op) applied directly to the already-coherent bank rather than that function's own `strict=False` fallback load from the hardcoded `runs/phase_a1_learned_routing_benchmark` path, `shift_functional_generalization_repair`'s dedicated versioned-replacement pipeline for SHIFT, `incremental_router_benchmark.update_router_incrementally` (`R0_FULL_RETRAIN`), and `apc.primitives.argument_scoring.ArgumentScorer.train_on_examples`. ### Design finding made during this task (not in REC-001)

Reading `_ensure_learned_routing_bank_and_core`'s canonical training loop (`learned_routing_benchmark.py:627-634`) directly shows it also trains SHIFT -- SHIFT is a member of `ALL_CANONICAL_OPERATIONS` -- using the *generic* per-operation trainer, not R3-009's dedicated versioned-replacement pipeline that actually produced the real committed SHIFT candidates. A build plan that simply called this function and kept its output whole would silently discard R3-009's real, hash-verified SHIFT work and replace it with an untested generic-recipe SHIFT slot -- a new instance of exactly the "quietly-combined incompatible components" failure class ADR-0091 diagnosed, just introduced by the recovery tooling itself instead of inherited from it. The build plan resolves this with an explicit two-source design: `CANONICAL_AND_BRANCH_B_BUILD`'s own SHIFT output is documented as a **discarded byproduct, never published**, and a separate `SHIFT_OVERRIDE_MERGE` stage (depending on both `CANONICAL_AND_BRANCH_B_BUILD` and the dedicated `SHIFT_DEDICATED` stage) replaces that slot with the real R3-009-lineage weights before any evaluation reads the bank -- restore for seeds 10/11/14 (COMMITTED per `bank_transaction_log.json`), registered `REBUILD_REQUIRED_NOT_EXECUTED` for seeds 12/13 (ROLLED_BACK), per the experiment plan's SHIFT-only `COHERENT_LIMITED` exception (section 2.2 item 4).

### Context

`B-C005REC-004`/ADR-0095 found 4 of the 6 `INCREMENTAL_6_BUILD` operations (CYCLE_FOUR, MIRROR_HALVES, ROTATE_TRIPLETS, SWAP_ENDS) below the 0.95 non-SHIFT recovery floor after exactly 1000 optimizer steps each, and explicitly left open whether the budget itself, generalization, or something unresolved was the cause. This task (`B-C005REC-004A`, `docs/CODEX_TASKS_PHASE_B_B2_INCREMENTAL_BUDGET_CALIBRATION.md`) answers that question directly: it re-trains only those 4 operations, fresh (Stage A confirmed the parent has no optimizer/scheduler/RNG/data-iterator state -- only final 1000-step weights -- so "resume" is impossible and this is `FRESH_PAIRED_REBUILD`, never called `EXACT_CONTINUATION`), on one continuous trajectory per operation with checkpoints at 1000/2000/4000/6000 cumulative steps, against a **fixed** `budget_validation` set (1024 examples, same input at every checkpoint), and selects the smallest step clearing 0.95 per operation. ### Design

The LR schedule is the one point genuinely requiring a new decision (not present in the original 1000-step recipe): `CosineAnnealingLR(T_max=1000)` is undefined past its own nominal length. Rather than reconstruct it with `T_max=6000` (a redesign the task doc forbids) or resume with unknown state, `T_max` stays fixed at 1000 and the same scheduler object is simply stepped past 1000 up to 6000 -- a mechanical, no-redesign extension whose defining property is that the **first 1000 steps' LR sequence is byte-identical to a plain 1000-step run** (the closed-form value at step *t* depends only on *t* and `T_max`, never on how many further steps follow). This is disclosed as `MECHANICAL_EXTENSION_FIXED_T_MAX` in `budget_protocol.json`, including the observed consequence: LR cycles back toward the 0.0008 peak by step 2000 (period `2*T_max`), so steps 1001-6000 train mostly at full LR, not near `eta_min` -- confirmed in `learning_curve.jsonl` (`learning_rate_at_step`: 0.000010 at step 1000, 0.000800 at 2000/4000/6000).

Per-step training data is generated by `_generate_step_training_examples`, an exact reproduction of `_train_single_primitive`'s non-parameterized branch (same `_derive_local_seed(seed, step, f"train:{operation}")` formula, same oracle program construction) -- since this depends only on `(seed, step, operation)`, the first 1000 steps' training *examples* are identical to REC-004's original run; only the fresh primitive's random weight-initialization draw differs (disclosed, not claimed bit-identical). `budget_validation` (1024 examples, split `rec004a_budget_validation`) is regenerated identically at every checkpoint by construction (a pure deterministic generator keyed on seed/split/n), so "same input at every step" holds without holding the actual objects in memory across steps. `_dedup_audit` independently confirmed zero example overlap between `train_fit`/`budget_validation`/`recheck_query` for every target operation.

### Context
