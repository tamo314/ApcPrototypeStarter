

**## ADR-0099: MIRROR\_HALVES Length-Conditioned Position Bias -- a 192-Parameter Explicit-Coordinate Attention Bias Produces a Large, Consistent Paired Gain Across All 5 Initializations (Mean EM 0.387 -> 0.719) but None Reach the 0.95 Recovery Floor, With the Residual Gap Concentrated Specifically at the Longest Trained Length; RG3 Recheck Is Never Executed by the Task's Own All-Five Gate (Task B-C005REC-004D, \`candidate\_status: POSITION\_BIAS\_VALIDATION\_NOT\_MET\`)**

**\*\*Date:\*\*** 2026-09-09

**\*\*Status:\*\*** Accepted (Task B-C005REC-004D complete; real GPU training executed for the pilot seed only, 10 isolated MIRROR\_HALVES trials (5 inits x {U, P} arms, 6000 updates each, 60000 total); no candidate selected, no child bundle built, no RG3 recheck executed; no shared cache modified)

**### Context**

\`B-C005REC-004C\`/ADR-0098 left MIRROR\_HALVES's recovery gap diagnosed but unresolved: 5 fresh initializations spanned 0.20-0.50 validation EM under the identical Core, data stream, and recipe, and neither a length-monotonic capacity story (ADR-0096) nor an initialization-sensitivity story alone (ADR-0097) cleanly explained the per-length failure signature across all 3-5 samples. ADR-0098 also positively confirmed the padding/batching execution contract and MIRROR\_HALVES's position map, ruling out an implementation bug -- but left unaddressed whether the existing \`CrossPositionPrimitive\` architecture has any explicit path to real content length/position at all. A user-supplied task doc (\`docs/CODEX\_TASKS\_PHASE\_B\_B2\_MIRROR\_LENGTH\_POSITION\_BIAS.md\`, this task's own design doc \`docs/design-docs/B2\_LENGTH\_CONDITIONED\_POSITION\_BIAS\_V1.md\`) tests that specific hypothesis: add a small (192-parameter), generic-coordinate-only additive position bias to MIRROR\_HALVES's attention scores, and compare U (unmodified \`CrossPositionPrimitive\`) against P (\`CrossPositionLengthBiasPrimitive\`) from REC-004C's own 5 saved initial states, holding Core, the other 15 primitives, recipe, and per-step training data identical between arms.

The task doc pre-registers a strict, all-or-nothing adoption rule: only if **\*\*all 5\*\*** P runs independently clear the existing 0.95 validation floor is P/I01 at step=6000 fixed as the new candidate (never the best-performing init), assembled into a child bundle with REC-004A's 3 fixed candidates, and independently rechecked. It also required Stage A to confirm/correct a specific fixed-position claim inherited from ADR-0098, and Stage B to verify the new architecture (zero-bias parity, gradient path, mask/layout, strict serialization) before any real training.

**### Evidence**

1\. **\*\*Stage A found the erratum the task doc predicted -- in the prose only, not in any JSON aggregate.\*\*** REC-004C's \`report.md:68-69\`/\`:153\` and ADR-0098 Evidence 4 describe MIRROR\_HALVES's "fixed" position bucket as "odd lengths 7/9 only" and the fixed index as "the middle" position. Recomputing \`pi\_n\` (\`mpid.mirror\_halves\_position\_map\`, itself oracle-verified) for the 5 legal lengths shows both claims are wrong: **\*\*4 of 5 lengths (6, 7, 9, 10) contribute a fixed position\*\***, even lengths 6/10 contribute 2 each (0.667 of the 6-position total across all 5 lengths), and n=7's single fixed index (1) is not its middle index (3, which is actually moved). Reconciling REC-004C's own \`position\_error\_summary.json\` cells against this same \`pi\_n\` reproduces \`position\_confusion.json\`'s \`structural\_moved\_vs\_fixed\` counts for all 3 historical checkpoints exactly (\`metric\_erratum.json\`: \`status: RECONCILED\`, \`all\_match: true\`) -- classified \`REPORT\_ONLY\_ERRATUM\`: no JSON number was wrong, only two \`report.md\` sentences and one ADR-0098 sentence mischaracterized which lengths contribute a fixed position and what "the middle" means. Recorded here, not silently edited into REC-004C's own artifacts.

2\. **\*\*Stage A's position-access audit confirms, by real forward/backward on a heterogeneous-length batch (not by source-reading alone), that \`CrossPositionPrimitive.forward\` had no explicit length or relative-position feature before this task\*\*** -- only two absolute-index \`nn.Embedding\` tables (content/query position). \`content\_lengths\` is confirmed to be the real per-example content length (distinct from the padded batch max), and a length-6/length-10 pair in one batch produces genuinely different bias values (\`position\_access\_audit.json\`).

3\. **\*\*Stage B's four pre-training gates all pass on the real Core (RTX 5060 Ti) before any of the 60,000 real updates ran.\*\*** \`architecture\_spec.json\`: exactly 192 new parameters (128+32+32, \`Linear(4,32)\` + \`Linear(32,1,bias=False)\`), 1.12% of the base primitive's 17,098 -- under the 5% budget ceiling. \`zero\_bias\_parity.json\`: forward pass is bit-exact (0.0 max abs diff) between U and a freshly-constructed P on both CPU and CUDA; shared-parameter gradients match exactly (0.0) on CUDA and within a pre-registered 1e-6 tolerance on CPU (observed \~2.2e-8, attributed to PyTorch's fused-attention kernel taking a different internal path for a float \`attn\_mask\` than a bool \`key\_padding\_mask\` -- disclosed with backend/tolerance, fixed before Stage C locked the protocol, never widened after). \`gradient\_path\_audit.json\`: at init, the bias output layer's own gradient is nonzero while the hidden layer's is exactly zero (blocked by the zero output weight, as designed); after one optimizer step the hidden layer's gradient becomes nonzero too -- confirming the branch is genuinely trainable, not \`detach()\`'d or permanently dead. \`operator\_serialization\_contract.json\`: the new type round-trips exactly; the old class's \`strict=True\` load of a bias-carrying state dict is rejected (missing keys), and the new class's \`strict=True\` load of a base-only state dict is rejected (missing keys) -- there is no \`strict=False\` bias-dropping path anywhere in the loader.

4\. **\*\*The 5 shared base initial states are confirmed to be REC-004C's own I01-I05\*\*** (\`canonical\_state\_hash\` recomputed from \`initial\_states/I0N.pt\` matches \`initialization\_summary.json\`'s recorded hash for all 5, exactly), and the 3 fixed candidates' reported step=4000 EM is reproduced exactly against REC-004A's own validation split before any new training (\`source\_audit.json\`: \`matches\_within\_tolerance: true\` for CYCLE\_FOUR/ROTATE\_TRIPLETS/SWAP\_ENDS).

5\. **\*\*All 10 planned runs completed (0 diverged), and all 10 received byte-identical per-step training data\*\*** (\`data\_stream\_identical: true\`, confirmed across all 10 outcomes' \`data\_digests\`, not just pairwise) -- the only disclosed difference between any two runs is the initial weight draw and, for U-vs-P at the same init, the 192 extra bias parameters (zero-initialized, so U and P start as an exact forward no-op of each other, per Evidence 3).

6\. **\*\*P produces a large, positive, paired gain over U on every single one of the 5 initializations -- \`PAIRED\_GAIN\_ALL\_FIVE\_OBSERVED\`, not a mixed or null result\*\*** (\`initialization\_stability.json\`, \`paired\_comparison.json\`):

   Mean validation EM rises from 0.3873 (U, matching ADR-0098's own I01-I05 figures exactly, confirming U is a faithful fresh replay of REC-004C's own control) to **\*\*0.7189\*\*** (P, sample SD 0.1201, range 0.3311, n=5) -- every P run beats its paired U run by at least +0.137. **\*\*This is now positive, direct, causal evidence that an explicit generic-coordinate position signal helps this operator learn\*\***, not merely a plausible hypothesis.

7\. **\*\*None of the 5 P runs reach the pre-registered 0.95 floor -- best is I05 at 0.9023\*\*** -- so per the task's own all-or-nothing adoption rule, \`candidate\_status: POSITION\_BIAS\_VALIDATION\_NOT\_MET\`, \`n\_p\_reaching\_floor: 0/5\`.

8\. **\*\*The residual gap concentrates specifically at length 10, the longest length in the training range, and is qualitatively different from lengths 6-9.\*\*** At length 6, P reaches 0.98-1.00 EM in all 5 inits (vs. 0.38-0.71 for U); lengths 7-9 also improve substantially and often reach 0.6-0.99. At length 10, by contrast, P is **\*\*flat or WORSE than U in 4 of 5 inits\*\*** (I01: 0.02->0.03 negligible; I02: 0.24->0.19 down; I03: 0.31->0.05 down; I04: 0.65->0.46 down; only I05 is flat at 0.75->0.74). This pattern is consistent across all 5 independent initializations, not a one-off -- a genuine, disclosed, unresolved finding, not attributed to a mechanism here (candidate leads: an \`n/length\_ref\` normalization or an \`i/d\`,\`j/d\` boundary effect specific to the top of the trained length range; not investigated further per this task's own scope).

9\. **\*\*The trained P models are heavily and consistently coupled to their own learned bias, not merely assisted by it.\*\*** Zeroing each trained P's \`position\_bias\_out\` weight (a diagnostic intervention on the trained weights, not a reset to U's architecture) collapses EM to 0.0-0.007 for all 5 inits (\`bias\_ablation.json\`); restoring the bias reproduces the original predictions exactly for all 5 (\`restore\_reproduces\_original\_predictions\_exactly: true\`). This shows P's improvement is not achieved via an independently-improved base pathway that merely benefits from an add-on signal -- the whole computation, as trained, depends on the bias term. Per the task's own caveat, this does not by itself prove the *\*original\** U failure was caused solely by missing position information.

10\. **\*\*Freeze and side-effect audits pass exactly as in every prior REC task.\*\*** Core's \`canonical\_state\_hash\` and all 12 protected primitives' hashes (including SHIFT) are byte-identical before/after the entire 60,000-update run (\`freeze\_audit.json\`); all 5 tracked shared-cache paths are byte-identical before/after (\`side\_effect\_audit.json\`); no staging or bundle directory was created for this task (\`candidate\_decision.json\`: \`selected\_arm: null\`, \`selected\_init: null\` -- Stage E/F never ran, consistent with the STOP rule).

11\. **\*\*Two latent bugs, never previously exercised in this repo's history, were found and fixed while implementing Stage E/F (both would have crashed the first REC task ever to actually reach them, since REC-004A/B/C's own real runs never selected a candidate and so never called this code path for real):\*\*** (a) \`build\_child\_bundle\`'s own \`\_guard\_not\_frozen\` call is incompatible with being invoked inside the \`with frozen\_evaluation():\` block the REC-004B orchestration pattern wraps it in -- fixed in this task's own orchestration by running \`build\_child\_bundle\` (assembly only, no new training) before entering \`frozen\_evaluation()\`, and wrapping only the read-only post-build checks; (b) the core/vocabulary \`ComponentManifest.file\_path\` written by \`legacy\_import\` was relative (unlike the router/scorer/bank paths, which are explicitly \`.resolve()\`d), which breaks once the fresh-process Stage F subprocess runs from a different scratch working directory -- fixed by resolving \`publish\_dir\` to absolute immediately after creation. Both are exercised for real in this task's own Stage-E/F CPU smoke tests (a tiny 4-step training run through the full assembly + fresh-process pipeline) before the real 60,000-step run; since \`candidate\_status\` did not clear the floor, Stage E/F never ran in the real milestone run itself, but the fix is verified working end-to-end on real repo artifacts (real parent bundle, real Core, real fresh-process subprocess) via that smoke test.

12\. **\*\*A third, pre-existing latent bug (shared by \`ibc.run\_protected\_regression\_check\`) was found and fixed in this task's own \`rec004d\_protected\_regression\_check\`\*\***: \`BindOp.is\_valid\_for\_length\` requires an even length, but the generic parameter-free example sampler draws lengths uniformly over \`(6,10)\` regardless, crashing the interpreter for BIND at length 7 or 9 with near-certainty over any real sample. Fixed via a new \`\_generate\_length\_safe\_examples\` helper (filters to lengths the operation actually accepts) for the protected-regression check, and via the same is-parameterized branch \`scripts/rec004\_fresh\_process\_check.py\` already uses correctly for Stage F's own in-process/fresh-process prediction comparison.

**### Consequences**

\- **\*\*\`B-C005REC-005\` remains blocked\*\***, for the same reasons ADR-0095-0098 already established; this task adds evidence the gap is *\*partially\** explainable by missing position information (a large, consistent, causal improvement) without closing it.

\- **\*\*No candidate was selected, no child bundle was built, and no RG3 recheck ran\*\***, regardless of how close I05 came, per the task's own pre-registered all-or-nothing rule -- \`candidate\_status: POSITION\_BIAS\_VALIDATION\_NOT\_MET\`, \`rg3\_recheck: NOT\_EXECUTED\`, \`rec005\_eligible: false\` unconditionally.

\- **\*\*The position-bias hypothesis is now supported, not merely plausible, but is insufficient alone.\*\*** A future task investigating MIRROR\_HALVES should treat "explicit position signal helps substantially" as an established finding (Evidence 6), and the length-10-specific residual gap (Evidence 8) as the primary open lead -- not a length-uniform capacity limit (ADR-0096's original hypothesis does not hold uniformly: lengths 6-9 are now largely solved). Per AGENTS.md's rule against skipping a failed mechanism by adding complexity downstream, no \`L\_ref\`/feature redesign, no additional length range, and no capacity increase was attempted here.

\- **\*\*No historical PASS/FAIL is changed.\*\*** \`B-C005REC-001\` through \`-004C\` (ADR-0092-0098) are preserved as-is; this task adds one paired-comparison layer and published no new bundle.

\- **\*\*No shared cache file was written\*\*** (Evidence 10). All new files are under \`src/\`, \`tests/\`, \`scripts/\`, \`configs/\`, and this task's own \`runs/phase\_b\_b2\_model\_bundle\_recovery/rec004d/run\_001/\` namespace; REC-004/REC-004A/REC-004B/REC-004C's own directories were read-only throughout.

\- Per the task doc's STOP rule, only \`B-C005REC-004D\` was executed; \`B-C005REC-005\` onward, \`B-C005R3-011\`, \`B-C006\`, and Task Inference remain blocked pending an explicit next user instruction. Whether to investigate the length-10-specific residual gap, redesign the bias feature set, widen the trained length range, or otherwise respond to this finding is not decided here and requires its own explicit next instruction.
