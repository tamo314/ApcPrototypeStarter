

**## ADR-0097: MIRROR\_HALVES Schedule Comparison -- Neither a Fixed-T\_max=1000 Mechanical Extension nor a Single T\_max=6000 Decay Clears the 0.95 Recovery Floor From a Fresh Initialization, and the Fresh Run Does Not Reproduce ADR-0096's Clean Length-Monotonic Failure Pattern, So the RG3 Recheck Is Never Executed by the Task's Own D1 Gate (Task B-C005REC-004B, \`mirror\_candidate\_status: VALIDATION\_TARGET\_NOT\_MET\`)**

**\*\*Status:\*\*** Accepted (Task B-C005REC-004B complete; \`mirror\_candidate\_status: VALIDATION\_TARGET\_NOT\_MET\`; \`rg3\_recheck: NOT\_EXECUTED\`; real GPU training executed for the pilot seed only; no child bundle published, no shared cache modified)

**### Context**

\`B-C005REC-004A\`/ADR-0096 left MIRROR\_HALVES the one \`INCREMENTAL\_6\_BUILD\` operation that did not clear the 0.95 non-SHIFT recovery floor within a 6000-step budget cap (0.6875 at step 6000), diagnosed as a length-dependent capacity limit (clean monotonic falloff: 96% correct at length 6, 22% at length 10) rather than an undertrained recipe or a generalization/leakage artifact. This inserted task (\`B-C005REC-004B\`, \`docs/CODEX\_TASKS\_PHASE\_B\_B2\_MIRROR\_SCHEDULE\_REPAIR.md\`) tests one specific, narrow alternative hypothesis -- that \`CosineAnnealingLR(T\_max=1000)\`'s mechanical extension past its own nominal length (ADR-0096's \`MECHANICAL\_EXTENSION\_FIXED\_T\_MAX\`, which cycles the LR back to near-peak every 2000 steps rather than decaying monotonically) is itself limiting convergence -- by comparing it against a single monotonic \`T\_max=6000\` decay, same initial weights, same per-step training data, same 6000 new optimizer updates, differing **\*\*only\*\*** in the scheduler's \`T\_max\`. CYCLE\_FOUR/ROTATE\_TRIPLETS/SWAP\_ENDS are not retrained; their REC-004A step=4000 checkpoints are imported read-only as fixed candidates (a new selection decision, switching from REC-004A's own minimal selected steps of 1000/2000/2000 to the more-margin step=4000 snapshot). A child bundle and independent RG3 recheck are built only if MIRROR\_HALVES's decisive step=6000 checkpoint clears 0.95 under either condition (\`B\_SINGLE\_DECAY\_6000\` primary, \`A\_FIXED\_TMAX\_1000\` a preregistered fallback) -- the task doc's own D1 gate.

**### Design**

MIRROR\_HALVES's weights are initialized **\*\*once\*\*** from a fresh draw (\`\_derive\_local\_seed(seed, 0, "rec004b\_shared\_init\:MIRROR\_HALVES")\` -- a new seed label, distinct from ADR-0096's own \`rec004a\_init\:MIRROR\_HALVES\`, per the task doc's explicit instruction not to fine-tune or resume REC-004A's own trained weights) and loaded identically into both conditions before training starts. Per-step training examples are generated by the same \`(seed, step, operation)\`-keyed pure function REC-004A used, so both conditions receive byte-identical per-step batches by construction -- verified per-step via a SHA-256 digest of each batch's \`(input\_tokens, target\_tokens)\` content, with the orchestrator raising \`PAIRING\_CONTRACT\_FAILURE\` if the two conditions' digest sequences ever diverge (they did not, in the real run: \`data\_stream\_identical: true\`).

A CPU dry-run LR-trace preflight (\`\_verify\_lr\_trace\`) checks the *\*real\** installed \`CosineAnnealingLR\`'s output against the task doc's closed-form \`eta\_T(u) = eta\_min + (base\_lr - eta\_min)/2 \* (1 + cos(pi\*u/T))\` at every 500-step checkpoint for both \`T\_max\` values before any training starts, raising \`LR\_TRACE\_CONTRACT\_FAILURE\` on any mismatch beyond a 1e-6 tolerance; the real run's own per-step \`lr\_trace.jsonl\` was independently checked to match the same closed form at every checkpoint (e.g. \`B\_SINGLE\_DECAY\_6000\` at u=1000: 0.00074708 vs. the table's 0.0007470800; at u=6000: 0.00001 vs. eta\_min exactly). Each condition checkpoints every 500 steps (13 checkpoints: 0, 500, ..., 6000), saving both a weights-only file (\`checkpoints/step\<u>.pt\`) and a full resumable state (\`training\_states/step\<u>.pt\`: weights + optimizer + scheduler + CPU/CUDA RNG + cumulative-update count) -- the decisive selection checkpoint is **\*\*only\*\*** step=6000, per the task doc's explicit prohibition on selecting from an intermediate checkpoint.

**### Evidence**

1\. **\*\*Neither condition clears the 0.95 floor at the decisive step=6000 checkpoint\*\*** (\`learning\_curve.jsonl\`, \`paired\_comparison.json\`, all measured on the same fixed \`schedule\_validation\` split REC-004A used, hash-verified in Stage A):

   | Condition | T\_max | EM @ 6000 | Token acc @ 6000 | train\_fit EM @ 6000 |

   |---|---:|---:|---:|---:|

   | A\_FIXED\_TMAX\_1000 | 1000 | **\*\*0.4717\*\*** | 0.9303 | 0.5029 |

   | B\_SINGLE\_DECAY\_6000 | 6000 | **\*\*0.4336\*\*** | 0.9190 | 0.4268 |

   \`mirror\_candidate\_status: VALIDATION\_TARGET\_NOT\_MET\` (neither reaches 0.95; per the task's own selection rule, B is primary and A a preregistered fallback, and neither is reached, so \`selected\_condition: null\`). The single monotonic decay (B, the schedule-fix hypothesis under test) does **\*\*not\*\*** outperform the mechanical extension (A, the control) in this pilot -- \`delta\_b\_minus\_a = -0.0381\` -- which does not support the schedule-cycling hypothesis on this one seed/init.

2\. **\*\*The gap is not causal leakage and not a generalization gap\*\*** -- \`wrong\_family\_exact\_match\`/\`none\_exact\_match\` are both \`0.0000\` for both conditions at every checkpoint (causal gap = correct EM exactly), and \`train\_fit\` tracks \`schedule\_validation\` closely throughout (0.503 vs 0.472 for A, 0.427 vs 0.434 for B at step 6000) -- both conditions are genuinely still learning the real transformation, not stuck, shortcut-driven, or overfit.

3\. **\*\*This fresh run's absolute performance is substantially below ADR-0096's own original run under the** *\*same\** **\`A\_FIXED\_TMAX\_1000\` schedule family\*\*** (0.4717 here vs. 0.6875 in ADR-0096, both \`T\_max=1000\` mechanical extension, both seed=10, both 6000 steps) -- the only disclosed difference is the fresh, independent weight-initialization draw this task's own design requires (task doc section A3 forbids reusing or fine-tuning ADR-0096's trained weights). This is strong same-seed evidence that MIRROR\_HALVES's convergence under this compact operator is **\*\*highly initialization-sensitive\*\***, independently reinforcing (not contradicting) ADR-0096's own \`CYCLE\_FOUR\` caveat (\`ORIGINAL\_FAILURE\_NOT\_REPRODUCED\`) that a different init draw alone can shift outcomes substantially -- one seed and one initialization is not evidence of a stable schedule effect either way.

4\. **\*\*This run's own by-length breakdown does not reproduce ADR-0096's clean monotonic length-dependent falloff\*\*** (\`error\_breakdown.json\`, step=6000): A: {6: 41.7%, 7: 40.2%, 8: 57.7%, 9: 59.2%, 10: 37.9%}; B: {6: 53.9%, 7: 52.8%, 8: 30.9%, 9: 28.2%, 10: 50.0%} -- both noisy and non-monotonic, unlike ADR-0096's smooth 96%->22% falloff. This task does not confirm, refute, or re-derive ADR-0096's "length-dependent capacity limit" attribution; it only discloses that the same overall failure (missing the 0.95 floor) does not present with the same per-length signature in this run, consistent with Evidence 3's init-sensitivity finding rather than a single stable mechanism.

5\. **\*\*The 3 fixed candidates' step=4000 checkpoints reproduce ADR-0096's reported values exactly\*\*** (\`source\_audit.json\`, \`source\_validation\_replay\`): CYCLE\_FOUR 0.9912109375, ROTATE\_TRIPLETS 0.998046875, SWAP\_ENDS 0.9970703125 -- all \`matches\_within\_tolerance: true\` against the same \`schedule\_validation\`/\`budget\_validation\` split, confirming these are genuinely REC-004A's own trained weights, not a relabeled or corrupted copy.

6\. **\*\*Freeze and side-effect audits pass\*\*** (\`freeze\_audit.json\`, \`side\_effect\_audit.json\`): Core's \`canonical\_state\_hash\` and all 12 protected non-SHIFT primitives' + SHIFT's content hashes are byte-identical before/after the run; the 3 fixed-candidate checkpoint files on disk are byte-identical before/after (never touched); all 5 tracked shared-cache paths are byte-identical before/after. \`torch.optim.AdamW\` receives only the target primitive's own parameters (verified by an intercepting spy in \`tests/test\_mirror\_schedule\_comparison.py\`, mirroring ADR-0096's own pattern).

7\. **\*\*Per the task's own D1 gate, Stage D (child bundle) and Stage E (independent \`rec004b\_recheck\_query\` + fresh-process RG3 recheck) never ran\*\*** -- no child bundle was built or published, no \`rec004b\_recheck\_query\` examples were ever generated or scored (verified by their absence from the run's own output list).

8\. **\*\*Test suite\*\***: \`tests/test\_mirror\_schedule\_comparison.py\` (23 CPU-only tests, including a real tiny-ladder end-to-end CPU training call verifying Core/other-15-primitives isolation, optimizer parameter scoping, NaN-divergence handling, identical A/B data streams from a shared init, and the LR-trace preflight against the closed-form formula) all pass. \`python -m ruff check .\` and \`python -m mypy src/apc\` (134 source files) are clean. Full-repo \`python -m pytest -q\`: \`2048 passed, 3 warnings in 1492.18s (0:24:52)\` -- zero failures, up from ADR-0096's \`2025 passed\` by exactly this task's 23 new tests; 2 of the 3 warnings are this task's own benign LR-trace-preflight warning (\`scheduler.step()\` before \`optimizer.step()\`, intentional -- no gradients needed for a closed-form check), the third is the same pre-existing, unrelated \`torch\` nested-tensor prototype-API warning noted in every prior REC ADR. Total wall-clock for Stage A-C (12,000 training steps + 26 checkpoint evaluations across 2 conditions) was 131.1s on the target RTX 5060 Ti.

**### Consequences**

\- **\*\*\`B-C005REC-005\` remains blocked\*\***, for the same reasons ADR-0095/ADR-0096 already established, now joined by this task's own \`VALIDATION\_TARGET\_NOT\_MET\`: no bundle in this branch has ever passed the non-SHIFT-15 floor.

\- **\*\*Neither schedule hypothesis is supported as a general fix on this pilot\*\*** -- the single-decay condition this task exists to test performs *\*worse\** than the mechanical-extension control here, but per the task doc's own interpretive table this is reported as "B案はこのpilotで支持されない" (not: schedule cycling is confirmed harmless, and not: mechanical extension is confirmed better). One seed, one initialization, two conditions is not sufficient evidence to generalize either direction.

\- **\*\*MIRROR\_HALVES's underlying mechanism remains an open, now more complicated question\*\***: this task's evidence (3 and 4 above) shows the gap's magnitude and per-length signature are sensitive to the random initialization draw alone, holding schedule, data, and architecture fixed -- a future task investigating this operation should treat initialization sensitivity as a candidate mechanism alongside (not instead of) ADR-0096's length-dependent capacity-limit hypothesis, and should not assume either mechanism from a single run.

\- **\*\*No historical PASS/FAIL is changed.\*\*** \`B-C005REC-001\` through \`-004A\` (ADR-0092-0096) are preserved as-is; this task adds a schedule-comparison layer only and published no new bundle.

\- **\*\*No shared cache file was written\*\*** (Evidence 6). All new files are under \`src/\`, \`tests/\`, \`scripts/\`, \`configs/\`, and this task's own \`runs/phase\_b\_b2\_model\_bundle\_recovery/rec004b/run\_001/\` namespace.

\- Per the task doc's STOP rule, only \`B-C005REC-004B\` was executed; \`B-C005REC-005\` onward, \`B-C005R3-011\`, \`B-C006\`, and Task Inference remain blocked pending an explicit next user instruction. Whether to investigate initialization sensitivity directly (e.g. multiple init draws per condition), pursue position-bias diagnostics, or otherwise respond to this finding is not decided here and requires its own explicit next instruction.
