

**## ADR-0096: Incremental Primitive Budget Calibration -- 3 of 4 \`INCREMENTAL\_6\_BUILD\` Failures Clear the Recovery Floor With a Finite Step-Budget Increase, but MIRROR\_HALVES Does Not Reach 0.95 Within the Pre-Registered 6000-Step Cap, So the RG3 Recheck Is Never Executed by the Task's Own All-or-Nothing Gate (Task B-C005REC-004A, \`calibration\_status: VALIDATION\_TARGET\_NOT\_MET\`)**

**\*\*Date:\*\*** 2026-09-08

**\*\*Status:\*\*** Accepted (Task B-C005REC-004A complete; \`calibration\_status: VALIDATION\_TARGET\_NOT\_MET\`; \`rg3\_recheck: NOT\_EXECUTED\`; real GPU training executed for the pilot seed only; no child bundle published, no shared cache modified)

**\*\*Affects:\*\*** \`src/apc/evaluation/incremental\_budget\_calibration.py\` (new), \`scripts/run\_phase\_b\_b2\_model\_bundle\_recovery.py\` (\`--task B-C005REC-004A\` dispatch added), \`configs/phase\_b\_b2\_model\_bundle\_recovery\_rec004a.yaml\` (new), \`tests/test\_incremental\_budget\_calibration.py\` (new, 21 CPU-only tests), \`AGENTS.md\`, \`docs/DECISIONS.md\`, \`docs/DECISIONS\_PHASE\_B\_B2\_MODEL\_BUNDLE\_RECOVERY.md\`.

**\*\*Run Artifacts:\*\*** \`runs/phase\_b\_b2\_model\_bundle\_recovery/rec004a/run\_001/\` (\`parent\_audit.json\`, \`resume\_audit.json\`, \`operation\_contract\_audit.json\`, \`existing\_learning\_curve\_audit.json\`, \`qualification\_scope\_audit.json\`, \`budget\_protocol.json\`, \`learning\_curve.jsonl\`, \`error\_breakdown.json\`, \`selected\_recipe.json\`, \`side\_effect\_audit.json\`, \`summary.json\`, \`checkpoints/\` -- 16 weight snapshots, 4 operations x 4 ladder steps).

**### Context**

\`B-C005REC-004\`/ADR-0095 found 4 of the 6 \`INCREMENTAL\_6\_BUILD\` operations (CYCLE\_FOUR, MIRROR\_HALVES, ROTATE\_TRIPLETS, SWAP\_ENDS) below the 0.95 non-SHIFT recovery floor after exactly 1000 optimizer steps each, and explicitly left open whether the budget itself, generalization, or something unresolved was the cause. This task (\`B-C005REC-004A\`, \`docs/CODEX\_TASKS\_PHASE\_B\_B2\_INCREMENTAL\_BUDGET\_CALIBRATION.md\`) answers that question directly: it re-trains only those 4 operations, fresh (Stage A confirmed the parent has no optimizer/scheduler/RNG/data-iterator state -- only final 1000-step weights -- so "resume" is impossible and this is \`FRESH\_PAIRED\_REBUILD\`, never called \`EXACT\_CONTINUATION\`), on one continuous trajectory per operation with checkpoints at 1000/2000/4000/6000 cumulative steps, against a **\*\*fixed\*\*** \`budget\_validation\` set (1024 examples, same input at every checkpoint), and selects the smallest step clearing 0.95 per operation. Core, the 12 protected primitives, Router, and ArgumentScorer are never touched (Stage C trains each target primitive in isolation against a frozen 16-op bank rebuilt from REC-004's own published bundle, \`2356543740ce...cf53995\`). Stage D (child bundle) and Stage E (independent \`recheck\_query\` + fresh-process RG3 recheck) only run if **\*\*all 4\*\*** operations select a passing checkpoint -- the task doc's own all-or-nothing gate.

**### Design**

The LR schedule is the one point genuinely requiring a new decision (not present in the original 1000-step recipe): \`CosineAnnealingLR(T\_max=1000)\` is undefined past its own nominal length. Rather than reconstruct it with \`T\_max=6000\` (a redesign the task doc forbids) or resume with unknown state, \`T\_max\` stays fixed at 1000 and the same scheduler object is simply stepped past 1000 up to 6000 -- a mechanical, no-redesign extension whose defining property is that the **\*\*first 1000 steps' LR sequence is byte-identical to a plain 1000-step run\*\*** (the closed-form value at step *\*t\** depends only on *\*t\** and \`T\_max\`, never on how many further steps follow). This is disclosed as \`MECHANICAL\_EXTENSION\_FIXED\_T\_MAX\` in \`budget\_protocol.json\`, including the observed consequence: LR cycles back toward the 0.0008 peak by step 2000 (period \`2\*T\_max\`), so steps 1001-6000 train mostly at full LR, not near \`eta\_min\` -- confirmed in \`learning\_curve.jsonl\` (\`learning\_rate\_at\_step\`: 0.000010 at step 1000, 0.000800 at 2000/4000/6000).

Per-step training data is generated by \`\_generate\_step\_training\_examples\`, an exact reproduction of \`\_train\_single\_primitive\`'s non-parameterized branch (same \`\_derive\_local\_seed(seed, step, f"train:{operation}")\` formula, same oracle program construction) -- since this depends only on \`(seed, step, operation)\`, the first 1000 steps' training *\*examples\** are identical to REC-004's original run; only the fresh primitive's random weight-initialization draw differs (disclosed, not claimed bit-identical). \`budget\_validation\` (1024 examples, split \`rec004a\_budget\_validation\`) is regenerated identically at every checkpoint by construction (a pure deterministic generator keyed on seed/split/n), so "same input at every step" holds without holding the actual objects in memory across steps. \`\_dedup\_audit\` independently confirmed zero example overlap between \`train\_fit\`/\`budget\_validation\`/\`recheck\_query\` for every target operation.

**### Evidence**

1\. **\*\*3 of 4 operations cross the 0.95 floor within the 6000-step cap; one does not\*\***, all measured on the fixed \`budget\_validation\` set (\`selected\_recipe.json\`, \`learning\_curve.jsonl\`):

   | Operation | 1000 | 2000 | 4000 | 6000 | Selected step | Label |

   |---|---:|---:|---:|---:|---:|---|

   | CYCLE\_FOUR | 0.9541 | 0.9648 | 0.9912 | 0.9990 | **\*\*1000\*\*** | \`ORIGINAL\_FAILURE\_NOT\_REPRODUCED\` (REC-004's own fresh 1000-step run already clears the floor here -- see caveat below) |

   | ROTATE\_TRIPLETS | 0.9238 | 0.9512 | 0.9980 | 1.0000 | **\*\*2000\*\*** | \`BUDGET\_EXTENSION\_SUPPORTED\_ON\_PILOT\` |

   | SWAP\_ENDS | 0.5234 | 0.9521 | 0.9971 | 1.0000 | **\*\*2000\*\*** | \`BUDGET\_EXTENSION\_SUPPORTED\_ON\_PILOT\` |

   | MIRROR\_HALVES | 0.0146 | 0.0303 | 0.2725 | 0.6875 | **\*\*null\*\*** | \`BUDGET\_LADDER\_EXHAUSTED\` |

   **\*\*Caveat on CYCLE\_FOUR\*\***: this task's own fresh 1000-step checkpoint (0.9541) does not reproduce REC-004's originally-reported 1000-step value (0.8906) -- both used \`seed=10\` and identical per-step training data (same derivation formula), so the only disclosed difference is the fresh primitive's random weight-initialization draw (Stage C constructs each of the 4 targets in isolation, not by replaying the full 16-op construction sequence REC-004 used, so global-RNG-derived initialization differs even at identical \`torch.manual\_seed\` policy). Per the task doc's own C4 table this is reported as \`ORIGINAL\_FAILURE\_NOT\_REPRODUCED\`, not treated as evidence that 1000 steps was always sufficient -- ROTATE\_TRIPLETS and SWAP\_ENDS's own fresh 1000-step values (0.9238, 0.5234) closely reproduce REC-004's originals (0.9219, 0.4736), so the divergence is specific to CYCLE\_FOUR's init draw, not a general measurement discrepancy.

2\. **\*\*MIRROR\_HALVES's gap is not a generalization gap and is not causal leakage\*\*** -- \`train\_fit\` sequence EM tracks \`budget\_validation\` closely at every checkpoint (0.0166 vs 0.0146 at step 1000; 0.7061 vs 0.6875 at step 6000), and \`none\_exact\_match\`/\`wrong\_family\_exact\_match\` are both \`0.0000\` throughout (causal gap = correct EM exactly), so the primitive genuinely is doing the work and genuinely is still converging, not stuck or shortcut-driven. **\*\*The specific mechanism is a length-dependent capacity limit\*\***: \`error\_breakdown.json\`'s per-length table at step 6000 shows length-6 inputs at 196/204 (96%) correct while length-10 inputs are only 46/206 (22%) correct, with a smooth monotonic falloff at every intermediate length -- token accuracy is already high (0.9503 overall at step 6000) but a handful of wrong tokens on longer sequences repeatedly break exact match. This is reported as the single clearest unresolved mechanism (task doc section 8.3): the compact cross-position operator's capacity/attention span for MIRROR\_HALVES's longer-range mirrored dependencies, not a training-budget or implementation defect.

3\. **\*\*ROTATE\_TRIPLETS/CYCLE\_FOUR's group-remainder strata and SWAP\_ENDS's changed-position accuracy are clean, structurally explained, and fully resolve by the selected step\*\*** (\`error\_breakdown.json\`): ROTATE\_TRIPLETS's length-mod-3 remainder-2 stratum starts weakest (179/219 at step 1000) and reaches 219/219 by step 4000; SWAP\_ENDS's changed-position accuracy (positions 0 and n-1 only, denominator 1832 fixed across all checkpoints) rises 0.774 -> 0.985 -> 1.0 -> 1.0, exactly tracking overall EM, confirming the operation's own documented contract (\`operation\_contract\_audit.json\`, cross-checked live against \`get\_operation\` in addition to the quoted source) rather than an invented rule.

4\. **\*\*Per the task's own D1 gate, Stage D (child bundle) and Stage E (independent \`recheck\_query\` + fresh-process RG3 recheck) never ran\*\***, because MIRROR\_HALVES never selected a passing checkpoint: \`calibration\_status: VALIDATION\_TARGET\_NOT\_MET\`, \`rg3\_recheck: NOT\_EXECUTED\`. No child bundle was built or published; no \`recheck\_query\` examples were ever generated or scored (verified by their absence from the run's own output list). The 3 successful operations' selections are recorded (\`selected\_recipe.json\`) as diagnostic artifacts only, per the task doc's explicit instruction not to "fill in" the failing operation with a parent value or exception to force a recheck.

5\. **\*\*Side effects and protected scope\*\***: \`side\_effect\_audit.json\` confirms all 3 tracked shared-cache hashes (\`primitive\_bank\_16\`, \`shared\_encoder\`, \`shift\_committed\_bank\_v1\`) are byte-identical before and after this task's entire run. Stage C trains each of the 4 target primitives in isolation against a bank otherwise frozen via \`bank.freeze\_all()\`/\`eval()\`, and \`\_train\_operation\_with\_checkpoints\` passes only that one primitive's own parameters to \`torch.optim.AdamW\` -- verified in \`tests/test\_incremental\_budget\_calibration.py\` both by checking Core/other-15-primitive state-dict equality before/after a real (tiny-ladder) CPU training call, and by intercepting the actual \`AdamW\` constructor call and asserting its parameter count equals exactly the target primitive's own \`numel()\` sum. Total wall-clock for Stage A-C (24,000 training steps + 16 checkpoint evaluations across 4 operations) was 123.2s on the target RTX 5060 Ti.

6\. **\*\*Two real bugs were found and fixed by the CPU test suite before this milestone run, not by review alone\*\***: (1) VRAM-tracking code checked global \`torch.cuda.is\_available()\` instead of the primitive's own tensor device, so a CPU-only construction on this CUDA-equipped machine crashed inside \`torch.cuda.reset\_peak\_memory\_stats\` -- fixed by checking \`device.type == "cuda"\`. (2) A primitive that diverges (non-finite loss) exactly *\*on\** a ladder step was silently dropped from the checkpoint list instead of being recorded \`NOT\_EXECUTED\` (the post-loop backfill used \`step > diverged\_at\`, excluding the divergence step itself) -- fixed to \`step >= diverged\_at\`. Neither bug affected the real milestone run (no operation diverged), but both were caught by \`tests/test\_incremental\_budget\_calibration.py\` before it ran.

7\. **\*\*Full-repo verification\*\***: \`python -m ruff check .\` and \`python -m mypy src/apc\` (133 source files) are clean. \`python -m pytest -q tests/test\_recovery\_pilot\_restore\_build.py tests/test\_recovery\_build\_coverage.py tests/test\_model\_bundle\_contract.py tests/test\_incremental\_budget\_calibration.py\`: 94 passed. Full-repo \`python -m pytest -q\`: \`2025 passed, 1 warning in 1560.81s (0:26:00)\` -- zero failures, up from ADR-0095's \`2004 passed\` by exactly this task's 21 new tests; the one warning is the same pre-existing, unrelated \`torch\` nested-tensor prototype-API warning noted in every prior REC ADR, not newly introduced.

**### Consequences**

\- **\*\*\`B-C005REC-005\` remains blocked\*\***, now for two independent, pre-existing reasons: REC-004's own RG3 FAIL (ADR-0095, unresolved) and this task's own \`VALIDATION\_TARGET\_NOT\_MET\` (no RG3 recheck was ever executed to potentially clear it). Neither this task nor any prior one has produced a bundle whose non-SHIFT-15 floor passes.

\- **\*\*CYCLE\_FOUR, ROTATE\_TRIPLETS, and SWAP\_ENDS's step-budget fix is empirically supported on this one pilot seed\*\*** (selected steps 1000/2000/2000 respectively clear 0.95 and hold through 6000), but per the task doc's explicit scope limit this is a **\*\*seed-10-only, one-initialization-draw finding\*\***, not evidence it generalizes to seeds 11-14 -- a future task revisiting the budget must still verify it per-seed, not assume it.

\- **\*\*MIRROR\_HALVES's remaining gap is characterized, not fixed\*\***: \`BUDGET\_LADDER\_EXHAUSTED\` with a specific, evidenced mechanism (length-dependent capacity limit, not a generalization gap or causal-leakage artifact). Per AGENTS.md's own rule against compensating with model size/RL/architecture changes inside an experimental task, no capacity change was attempted here.

\- **\*\*No historical PASS/FAIL is changed.\*\*** \`B-C005REC-001\` through \`-004\` (ADR-0092-0095) are preserved as-is; this task adds a calibration/measurement layer only and published no new bundle.

\- **\*\*No shared cache file was written\*\*** (Evidence 5). All new files are under \`src/\`, \`tests/\`, \`scripts/\`, \`configs/\`, and this task's own \`runs/phase\_b\_b2\_model\_bundle\_recovery/rec004a/run\_001/\` namespace.

\- Per the task doc's STOP rule, only \`B-C005REC-004A\` was executed; \`B-C005REC-005\` onward, \`B-C005R3-011\`, \`B-C006\`, and Task Inference remain blocked pending an explicit next user instruction. Whether to raise MIRROR\_HALVES's own budget further, investigate its length-scaling limitation specifically, or otherwise respond to this finding is not decided here -- the task doc's own budget cap (6000 steps) forbids further extension inside this task, and any response requires its own explicit next instruction.
