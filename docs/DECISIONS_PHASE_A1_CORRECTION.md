## ADR-0021 — H1b passes: an explicit task segment resolves ADR-0017/ADR-0020's non-identifiability, one shared model, all eight known operations

**Status:** Accepted

**Decision:** `apc.evaluation.shared_core_generalization` (Task A1-C004, the Shared-Core systematic-generalization gate, STOP GATE) is recorded as **PASS**. `docs/exec-plans/active/PHASE_A1.md`'s H1b ("shared-core conditional systematic generalization") is confirmed: `runs/phase_a1_shared_core_gate/report.json`/`summary.json` (config `configs/phase_a1_shared_core_gate.yaml`, 5 seeds `0-4`, RTX 5060 Ti, git commit `e693c34`) show a single `apc.core.model.DecoderOnlyTransformer` (192d, 4 layer, ~1.80M params), trained on `apc.environments.generator.build_mixed_operation_generator`'s online mixed stream over all eight `KNOWN_OPERATION_NAMES` with the model-visible task segment included (`include_task_spec=True`, Task A1-C003), reaches:

- overall mean unseen exact match **0.9946** (threshold 0.95, stdev 0.0030, min-over-seeds 0.9922, `meets_seed_policy=true`);
- every operation's mean **>=0.984** (threshold 0.90) -- `COPY` 0.9996, `SELECT` 0.9946, `COMPARE` 0.9989, `COUNT` 0.9863, `SHIFT` 0.9842 (lowest), `BIND` 0.9981, `NEGATE` 0.9977, `ACCUMULATE` 0.9982;
- zero `(seed, operation)` pairs below the stricter 0.85 per-run floor from `docs/EXPERIMENT_PLAN_PHASE_A1_CORRECTION.md` section 2 (`low_outlier_seed_operations: []` for every seed).

The paired negative control (identical config/architecture/`SharedCoreTokens` vocabulary, `include_task_spec=False`) reaches only **0.139** mean overall exact match (stdev 0.008) -- a **0.856** gap, far exceeding the predeclared 0.20 `MATERIAL_UNDERPERFORMANCE_MARGIN`. All three `docs/CODEX_TASKS_PHASE_A1_CORRECTION.md` A1-C004 acceptance criteria are satisfied; A1-C004's own `run_shared_core_gate_h1b(...).passed` is `True`.

**Reason:** This is the intended resolution of ADR-0017 (`SELECT`/`COUNT`/`SHIFT`/`BIND`'s hidden per-instance parameter) and ADR-0020 (mutual non-identifiability of which operation applies, even among parameter-free operations) -- both root-caused to "a value the model needs is never revealed to it." Tasks A1-C001 (`apc.environments.task_spec.TaskSpec`) and A1-C003 (`apc.core.tokens.SharedCoreTokens`/`encode_task_spec`, rendering `[TASK_START] op arg... [TASK_END]` between `BOS` and the content input) fixed exactly that: operation identity and every previously-hidden argument are now part of the presented input. The negative control isolates this as the causal variable, not an incidental effect of "one shared model + mixed online data" alone: it shares every other field (seed, architecture, vocabulary, training budget) and its training curves (`runs/phase_a1_shared_core_gate/negative_control/seed_*/metrics.jsonl`) show a stable plateau from step ~2000 onward (loss oscillating ~0.42-0.53, exact match ~0.09-0.18 for the whole 30000-step budget, not still improving) -- consistent with ADR-0020's mechanism, not a training-budget shortfall. Per-operation negative-control means show the expected structure: `COPY` (value-blind, needs no task information to execute correctly) still reaches 0.77 -- close to its ADR-0020 single-mechanism finding -- while every operation whose correct output depends on which operation was requested and/or a hidden argument (`SELECT` 0.0004, `COMPARE` 0.028, `COUNT` 0.0024, `SHIFT` 0.097, `BIND` 0.016, `NEGATE` 0.015) collapses far below chance-adjacent baselines; `ACCUMULATE` (0.175) is the one mild outlier, plausibly because a running-sum's first output position is position-invariant regardless of which operation is guessed. This is consistent with, not contradicting, ADR-0020's ~0.25-0.35 pooled ceiling measured on a 4-operation, all-parameter-free pool: an 8-operation pool that also includes four ADR-0017 hidden-parameter operations is strictly harder to guess correctly without the task segment, so a lower negative-control ceiling here is expected.

**Consequence:** Per `docs/exec-plans/active/PHASE_A1_CORRECTION.md` section 4 ("Routing-readiness criterion"), A1-007 is unblocked *from H1b's perspective specifically* -- H1b passing is one of that section's four conditions, not all of them. `docs/CODEX_TASKS_PHASE_A1_CORRECTION.md` still requires A1-C005 (probe whether `z_task` actually carries usable task information -- H1b passing says the *model* can condition on the task segment somewhere in its computation, not that `encode_split`'s specific `z_task`/`h_content` split routes it there usefully), A1-C006 (parameterized `PrimitiveCall` abstraction), and A1-C007 (oracle `PrimitiveCall` routing adapter) before A1-007 itself may begin; A1-C008's audit is the task that should record the combined H1a+H1b+probe verdict formally. `docs/AGENTS_PHASE_A1_CORRECTION_ADDENDUM.md`'s historical-interpretation instruction is satisfied as written: A1-006 remains H1a (per-operation systematic generalization, unmodified), and this ADR records H1b (shared-core conditional systematic generalization) as now also passed, not a replacement or reinterpretation of A1-006's own result. No STOP-discipline investigation is triggered (`docs/AGENTS_PHASE_A1_CORRECTION_ADDENDUM.md`'s "If the shared-core gate fails" branch does not apply); the only open, non-blocking observation is `ACCUMULATE`'s comparatively higher negative-control score (0.175 vs. <0.10 for most other hidden-dependency operations), which does not affect this gate's own pass/fail and is left for a future task to investigate only if it becomes load-bearing for a later conclusion.

## ADR-0022 — H1c passes: `z_task` reliably encodes operation identity and arguments at the causally content-blind `[TASK_END]` position

**Status:** Accepted

**Decision:** `apc.evaluation.task_content_probes` (Task A1-C005, the Task/Content representation-probe gate, STOP GATE, H1c) is recorded as **PASS**. `docs/EXPERIMENT_PLAN_PHASE_A1_CORRECTION.md` section 3's H1c ("task/content representation usefulness") is confirmed: `runs/phase_a1_task_content_probes/report.json`/`summary.json` (config `configs/phase_a1_task_content_probes.yaml`, 3 seeds `0-2`, CPU -- see Reason below for why this run is CPU rather than A1-C004's CUDA, git commit `976afd8`, the A1-C004 commit) freeze one shared `apc.core.model.DecoderOnlyTransformer` per seed -- trained identically to A1-C004's explicit-task variant via the refactored-out `apc.evaluation.shared_core_generalization.train_shared_core` -- and fit single-`nn.Linear` probes on its frozen `encode_split` output. Every seed's own shared core first re-confirms H1b at that seed (`shared_core_overall_exact_match` 0.9988/0.9946/0.9995 for seeds 0/1/2, all comfortably above ADR-0021's 0.95 threshold), then:

- **Probe T1 (operation identity from `z_task`, threshold >=0.95):** **1.0** for all three seeds (mean 1.0, min-over-seeds 1.0).
- **Probe T2 (operation argument from `z_task`, threshold >=0.90, per operation):** `COUNT`/`SHIFT`/`BIND` (single-value classification over the shared `arg_span`) reach **1.0** in every seed; `SELECT.indices` (masked multi-hot/set-membership probe, `apc.evaluation.task_content_probes._fit_multilabel_probe`) reaches 0.9758/0.9419/0.9592 across seeds 0/1/2 -- lowest, but still comfortably above threshold. Every `(seed, operation)` pair passes; `argument_probes_passed=true` for all three seeds.
- **Probe C1 (content-token identity from `h_content`, predeclared threshold >=0.98):** 0.9810/0.9928/0.9878 across seeds 0/1/2 (mean 0.9872, min-over-seeds 0.9810). All three pass, though seed 0's margin above the predeclared 0.98 floor is thin (+0.0009) -- see Reason.

Both optional, non-gating leakage probes behave exactly as the module docstring's causal-masking argument predicts: operation-from-`content_state`-at-`[TASK_END]` reaches **1.0** in every seed (same underlying vector as `z_task` there, modulo `task_head`'s parameter-free per-position `LayerNorm`, ADR-0015), and content-from-`task_state`-at-content-positions reaches 0.9750/0.9930/0.9874 -- close to Probe C1's own numbers, as expected since both read the same content-position vector under different (LayerNorm-related) framing. Neither leakage probe gates `passed`; `run_task_content_probes_multi_seed(...).passed` is `True` (all three seeds individually pass).

**Reason:** This is the intended target of A1-C003's `register_encode_split_probe`/`encode_split` split (ADR-0015) and directly answers `docs/AGENTS_PHASE_A1_CORRECTION_ADDENDUM.md`'s "Task/content probe rule": H1b (ADR-0021) only showed the *model* can condition on the task segment somewhere in its computation, not that `z_task` specifically is where that information ends up. The probe positions are chosen structurally, not merely empirically: the `[TASK_END]` token's causal-attention history is exactly `[BOS] [TASK_START] op arg... [TASK_END]` -- the content input has not been generated yet at that position, so no amount of training can leak content into `task_state` there; conversely each content position has seen the task segment plus every token up to itself, matching what a primitive-execution step reading `content_state` would see. This structural argument is exactly what the leakage-probe results confirm empirically (operation trivially recoverable from `content_state` at `[TASK_END]` since it is the same pre-norm vector as `task_state`; content trivially recoverable from `task_state` at content positions for the same reason) -- per the addendum, "the goal is useful factorization, not perfect disentanglement," so neither leakage result weakens the gate's PASS verdict.

This run executed on CPU (`torch==2.13.0+cpu`, `cuda_available=false` in `runs/phase_a1_task_content_probes/system.json`), not the RTX 5060 Ti / WSL-CUDA environment ADR-0013 built specifically for one earlier scale investigation and A1-C004 happened to also use -- the Windows `.venv` this session's shell tooling activates by default only has the CPU PyTorch build installed. This is why per-seed wall-clock (3124s/3238s/3681s, ~52-61 minutes) is roughly 8-9x A1-C004's ~380-400s/seed on GPU for the identical 30000-step training loop; it does not affect the measured probe accuracies' validity (same deterministic ops, same seeds, same architecture). Seed 0's Probe C1 margin (+0.0009 over the predeclared 0.98 floor) is close enough to be worth a future seed-scaling sanity check if this content-probe result becomes load-bearing for a later conclusion, but is not treated as a failure here: 0.98 was predeclared specifically as a strict bar (module docstring, `CONTENT_PROBE_TOKEN_ACCURACY_THRESHOLD`), and all three seeds independently clear it.

**Consequence:** Per `docs/exec-plans/active/PHASE_A1_CORRECTION.md` section 4, two more of the four "routing-readiness" conditions are now satisfied (H1b, ADR-0021; and "`z_task` predicts operation identity reliably" plus "required task arguments are model-visible", this ADR) -- A1-007 remains blocked on the other two (A1-C006's parameterized `PrimitiveCall` abstraction, A1-C007's oracle `PrimitiveCall` routing adapter), which are unaffected by this task. No STOP-discipline investigation is triggered (`docs/AGENTS_PHASE_A1_CORRECTION_ADDENDUM.md`'s "If probes show `z_task` contains no usable task information" branch does not apply) -- learned primitive routing work may proceed once A1-C006/A1-C007 are also done. `apc.evaluation.shared_core_generalization.run_shared_core_gate`'s own behavior and every existing test for it are unchanged by the `train_shared_core` extraction this task made (verified: all 43 pre-existing tests in `tests/test_shared_core_generalization.py` still pass unmodified).

## ADR-0023 — `PrimitiveCall` keeps `SELECT`'s real `indices` subset rather than the design doc's single-scalar illustration

**Status:** Accepted

**Decision:** `apc.environments.primitive_call.PrimitiveCall` (Task A1-C006, the parameterized `PrimitiveCall` abstraction) represents `SELECT`'s argument as `{"indices": [...]}`, matching `ProgramStep.params`/`apc.environments.task_spec.TaskStepSpec.arguments` exactly, rather than `docs/design-docs/PARAMETERIZED_PRIMITIVE_CALLS.md` section 3's illustrative `PrimitiveCall(SELECT, {"index": 3})`. `PrimitiveCall(operation="SELECT", arguments={"index": 3})` raises `ValueError` (wrong key); only `{"indices": [...]}` is accepted. This resolves the naming/shape gap `apc.environments.task_spec`'s module docstring flagged as open when Task A1-C001 landed.

**Reason:** `apc.environments.operations.SelectOp.apply` selects an `output_length(len(sequence))`-sized *subset* of positions, preserving order (`SelectOp.sample_params`/`apply`, Phase A Milestone A1) -- for a length-6 input that is 3 positions, not 1. A single scalar `index` cannot determine a variable-length subset, so adopting the design doc's illustration literally would make `SELECT` calls underspecified: `execute()` (this task's `Operation.apply` dispatch) could not reproduce `apc.environments.interpreter.run_program`'s actual output for any `SELECT` step, and the round trip to/from `TaskStepSpec`/`ProgramStep` (which already carries `indices`, established by Task A1-C001 and covered by `tests/test_task_spec.py::test_task_step_spec_round_trips_every_known_operation`) would be lossy in one direction. The design doc itself anticipates this: section 2 says "the exact concrete schema may be stricter," and section 10 scopes the correction to representing "the existing synthetic operations ... cleanly" rather than introducing a new argument shape for them. Changing `SelectOp` itself to take a single index instead would alter already-gated behavior (A1-006/H1a, A1-C004/H1b, A1-C005/H1c all trained and probed against the real `indices`-subset semantics) for no benefit within this task's scope.

**Consequence:** `apc.environments.operations.Operation.required_argument_names` (added by this task) is now the single source of truth for which argument keys each operation accepts -- `SelectOp.required_argument_names == frozenset({"indices"})` -- and `PrimitiveCall.__post_init__` validates against it eagerly, so a caller that passes the design doc's illustrative `{"index": ...}` shape fails fast with a clear message instead of silently misrouting. `docs/CODEX_TASKS_PHASE_A1_CORRECTION.md`'s A1-C006 acceptance criteria are met: `tests/test_primitive_call.py` shows one primitive family (`SHIFT`, `SELECT`, `COUNT`, `BIND` each) executing >=3 distinct argument values correctly via `PrimitiveCall.execute`, `registered_operation_names()`/family count is unaffected by 100 `PrimitiveCall`s spanning 50+50 distinct argument values (`test_registered_operation_count_is_unaffected_by_many_distinct_calls`), and both missing-required-argument and unexpected-argument construction are covered (`test_missing_required_argument_raises_value_error`, `test_unexpected_argument_on_parameter_free_operation_raises_value_error`, `test_wrong_argument_name_for_parameterized_operation_raises_value_error`). `PrimitiveCall` is a new, distinct type from `TaskStepSpec` (execution-time call vs. model-input projection, see the module's own docstring) with lossless `from_task_step`/`to_task_step` and `from_program_step`/`to_program_step` conversions for every currently supported operation; it is not yet wired into `apc.core.execution`/`apc.primitives` (that wiring is Task A1-C007's oracle routing adapter, per `docs/CODEX_TASKS_PHASE_A1_CORRECTION.md`). All 608 pre-existing plus new tests pass (`python -m pytest -q`), and `python -m ruff check .` / `python -m mypy src/apc` are both clean.

## ADR-0024 — Oracle routing forces bank selection from a `PrimitiveCall`, with no `Router` reachable from the oracle path at all

**Status:** Accepted

**Decision:** Task A1-C007 (the oracle `PrimitiveCall` routing adapter) is implemented as two additions, keeping the environment/oracle-metadata layer and the core execution/learned-path layer split the same way the rest of this codebase already does:

- `apc.environments.generator.oracle_calls_for_example`/`oracle_call_for_example` convert an `Example`'s latent `program` into the `PrimitiveCall` chain (or, for the current depth-1 `known`/`novel_operation` pools, the single call) that produced its target -- Work item 1, "Convert environment oracle metadata into `PrimitiveCall`". `oracle_call_for_example` raises `ValueError` on a multi-step (`novel_composition`) example rather than silently returning only its first step, since A1-007's own scope is single-operation ("oracle-routed K"), not A1-008's composition search.
- `apc.core.execution.apply_bank_with_oracle_calls`/`forward_logits_with_oracle_calls`/`generate_greedy_with_oracle_call`/`evaluate_exact_match_with_oracle_calls` are new, additive siblings of `apply_bank`/`forward_logits`/`generate_greedy_with_capacity`/`evaluate_exact_match_with_capacity` that force bank primitive selection from one `PrimitiveCall` per batch item (`call.primitive_id`, applied unconditionally at `gate=1.0`) instead of scoring `stable_ids` through a `Router` -- Work item 3, "Update A1-007 evaluation API to accept an oracle call provider" (`evaluate_exact_match_with_oracle_calls`'s `oracle_call_provider` parameter, defaulting to `oracle_call_for_example` but substitutable, `tests/test_oracle_routing.py::test_evaluate_exact_match_with_oracle_calls_uses_the_injected_provider`).

None of the four new `apc.core.execution` functions accepts a `Router` parameter at all (`tests/test_oracle_routing.py::test_oracle_routing_functions_never_accept_a_router`, asserted via `inspect.signature`) -- Work item 2, "ensure the learned path never receives oracle calls", is satisfied structurally, not just by not calling `Router.forward` at runtime: there is no argument slot through which a caller could pass one in. `apply_bank`/`forward_logits`/`generate_greedy_with_capacity`/`evaluate_exact_match_with_capacity`/`Router` are all unmodified.

**Reason:** `docs/design-docs/PARAMETERIZED_PRIMITIVE_CALLS.md` section 8 and `docs/EXPERIMENT_PLAN_PHASE_A1_CORRECTION.md` section 4 ("oracle routing can be represented as a `PrimitiveCall`") both specifically warn that an oracle revealing only `primitive_id` for one of the four ADR-0017 hidden-parameter operations (`SELECT`/`COUNT`/`SHIFT`/`BIND`) would reproduce A1-006's non-identifiability one level into oracle routing: knowing *that* `SHIFT` is the right family does not say *which* `amount`. `PrimitiveCall.__post_init__` (Task A1-C006) already refuses to construct an underspecified call for these four operations (`PrimitiveCall(operation="SHIFT")` raises `ValueError: ... missing required argument(s): ['amount']`), so `oracle_call_for_example` inherits that guarantee for free -- it cannot hand out an argument-less oracle call for a parameterized operation even if it tried. `tests/test_oracle_routing.py::test_oracle_call_reproduces_target_tokens_exactly` (parametrized over all eight `KNOWN_OPERATION_NAMES`) confirms this positively: executing the converted call against `example.input_tokens` reproduces `example.target_tokens` exactly for both the four parameter-free and the four parameterized operations. The bank-side wiring forces `call.primitive_id` directly as the bank lookup key (no separate id-remapping layer): `apc.environments.task_spec.operation_id` was already designed as "a function of `operation` alone" (`PrimitiveCall.primitive_id`'s own docstring), so an A1-007 experiment that registers one bank primitive per operation at `operation_id(name)` gets oracle routing "for free" from this adapter, without this task needing to invent a second id-assignment scheme.

**Consequence:** Per `docs/exec-plans/active/PHASE_A1_CORRECTION.md` section 4, all four "routing-readiness" conditions are now satisfied (H1b/ADR-0021; `z_task` operation-identity and argument decoding/ADR-0022; the parameterized `PrimitiveCall` abstraction/ADR-0023; and this ADR's oracle routing adapter) -- **A1-007 is unblocked**, pending A1-C008's audit recording the combined verdict. What this task deliberately does *not* provide: a bank pre-populated with operation-aligned primitives (an A1-007 experiment-setup concern, not this adapter's), argument-conditioned neural primitive execution (`apc.primitives.primitive.Primitive.forward` still takes no `arguments` input at all -- `PrimitiveCall.arguments` is carried through `OracleRoutingOutput.calls` for bookkeeping/future use but not yet consumed by the low-rank transform itself; this remains a real limitation any future argument-sensitive oracle-routed gate must account for), and chained multi-call oracle execution (`apply_bank_with_oracle_calls` requires exactly one call per batch item and raises on a length mismatch; `oracle_calls_for_example` returns the full multi-step chain for a `novel_composition` example, but nothing here executes it -- that is Task A1-008's Composition Library). All 653 pre-existing plus new tests pass (`python -m pytest -q`, `tests/test_oracle_routing.py` adds 46), and `python -m ruff check .` / `python -m mypy src/apc` are both clean.
