# AIコーディング実行指示 — ManiSkillトラック

## 方針と適用範囲

このディレクトリと本トラックを案内するルート文書に適用する。
旧AGENTSのSTOP GATE、フェーズ承認、全件pytest/mypy、強制ADR、RL禁止、旧Python依存は
本トラックに適用しない。古い研究の結果や規定自体は変更しない。

ユーザーが指定した研究範囲で、実装と実環境の試行を往復する。
仮説が弱い、成功率が低い、予想と違う、という理由で研究全体を停止しない。
成功率の閾値・複数seedでの合格・事前証明・文書承認を次の作業の条件にしない。
ただし、実行不能、壊れたデータ、数値発散、予算超過は当該runの障害として正直に記録する。
これらを「科学的ゲート」に拡張しない。動く部分・小さい設定から試行を続ける。

## 1回の作業

1. README、実験メモの直近部分、変更する機能だけを読む。旧研究文書を全読しない。
2. 今回変える点と試行予算を短く記す。計画書の更新だけで一日を終えない。
3. 最小限の縦切り機能を作り、既存の環境で実際に試す。実験はpytestではなくrunnerで行う。
4. 失敗を含むrunパス・config・seed・結果・未実行事項を残し、次に変える一点を選ぶ。
5. 差分を確認してコミットする。pushはユーザーが許可した場合のみ実行する。

初期の目安は1環境・3〜10エピソード、学習を実装した後もまず少量のステップ予算で試す。
予算はユーザーの指示を優先し、必要に応じ変更する。長い網羅探索、分散学習、
巨大なシーン/アセットの一括取得は初期既定にしない。他プロセスを停止しない。

## テストを最小限にする規定

- **一つの大きな機能を実装した時点で、その機能全体の入口から成果物までを対象に
  統合テストを原則1本だけ追加する。** 例: 環境起動→複数episode→保存→集計。
- 関数・クラス単位の細切れunit test、getter/設定値/モック呼出し回数/文書文字列の検査、
  網羅率目標、テストケースの組合せ爆発を導入しない。
- バグ修正は可能なら既存の機能テストに反映する。小変更ごとに新規テストを増やさない。
- 試行中は実環境の短いrunと成果物の確認を優先する。大きな機能がまとまった時点で
  該当テストだけを実行する。無関係な旧APC全体テストを要求しない。
- タスク成功率や学習曲線の良否を自動テストの合格条件にしない。ゼロ成功も有効な実験。
- 実シミュレータを起動できない場合は未実行と書く。skipや代替fixtureでの確認を
  実環境テスト成功と呼ばない。そこで架空のデータを研究結果として作らない。

現在の機能テストは `tests/test_rollout_feature.py`、
`tests/test_fetch_reach_feature.py`、`tests/test_bc_feature.py`、
`tests/test_sequence_feature.py` の各機能1本。
実環境での実行方法:

```bash
# このディレクトリで、専用venvを有効化して実行
APC_RUN_MANISKILL_TEST=1 python -m pytest -q tests/test_rollout_feature.py tests/test_fetch_reach_feature.py tests/test_bc_feature.py
```

## 実装上の約束

Python 3.11/3.12の独立venvを使い、ルートのuv.lock/pyprojectや旧coreを変更しない。
まず状態観測・単一ロボット・閉ループ制御を使う。既存ManiSkillの身体とタスクを流用する。
RL/模倣学習は利用可能だが、未測定の最適化や複雑な抽象化を先に作らない。

旧プリミティブの内部演算と時間を持つ行動スキルを区別する。目標は入力してよい。
正解スキル列やteacherを使った場合は、手動/教師ありであることを記録する。
銀行の増加、スキルの再利用、temporaryモデルの解放は実測して初めて主張する。

runは必ず新しいディレクトリに保存する。チェックポイント、動画、アセットはgitに入れない。
同じ設定/seedでの比較を使い、探索に使ったデータを独立評価と呼ばない。
ネットワーク/GPU/外部サービスがない場合は、実行できた範囲と不足を引き継ぐ。
文書はREADME・計画・設計・短い実験メモを中心に維持し、承認文書の連鎖を増やさない。
